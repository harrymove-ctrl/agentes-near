# 0096. Each agent reaches its own local ports, and only its own

- Status: Accepted (built: core's runner). The agentes.chat Cloud takes it with a new runner pin, after the acceptance run in §7
- Date: 2026-11-01
- Amends: ADR 0057 (Consequences: the two paragraphs on browser ports and loopback listeners, and the launcher's environment), ADR 0058 §1 (an agent's display lock is in its own /tmp), ADR 0060 (the server's own computer needs systemd with `BPF_FRAMEWORK` too)
- Code: `apps/server/runner/loopback-guard.ts`, `browser-bind-policy.ts` (`applyBindPolicy`, `ensureBrowserBindPolicy`, `prepareAgents`), `browser-bind-check.ts`, `browser-ports.ts` (`browserBand`), `agent-users.ts` (`systemLauncher`, `adbServerPort`, the cron and at deny), `service.ts` (`AGENT_RAM_ROOT`, `AGENT_TMP_ROOT`, the tmpfiles lines), `supervisor.ts` (a start that fails), `desktop-session.ts` (`abstractDisplays`), `config.ts` (`services`), `main.ts` (`agentes-runner services`, `bind-check`), `install-script.ts` (`ISOLATION_APT_PACKAGES`, the `BPF_FRAMEWORK` check), `packages/setup` (`computerOffer`); the root test `apps/server/test/runner/isolation.root.test.ts` and CI's `isolation-root` job (`scripts/isolation-vm.sh`)

## Context

An agent couldn't build an Android app on its computer. System mode's bind policy (ADR 0057) denied every TCP `bind(0)`: Gradle's daemon and workers bind port 0 on loopback, so `./gradlew` never started, and the Kotlin compile daemon's 17001-17999 sat inside the denied 10000-29999. Every agent's adb wanted 5037, and a second agent's adb reached the first agent's server.

The loopback table that kept agents apart polled `ss` every 2 s, so a new listener was open to every agent until the next scan, a port reused by another agent kept its old owner for up to 2 s, and two agents on one port number locked each other out. It matched the connecting socket's uid, so a setuid-root program an agent ran counted as root. Root's and the computer's own listeners (a Postgres, an Ollama, the app's 127.0.0.1:3000 on the server's own computer), UDP and the shared /tmp (a Postgres socket on `trust`, mode 0777) were open to every agent.

## Decision

### 1. Who opened a connection, and where it goes

- The runner's table (`inet agentes_runner`) marks each new TCP or UDP connection that goes out on `lo` with its sender, in the conntrack mark: the agent whose slice the socket was made in (`socket cgroupv2 level 2`, mapped from `agents.slice/agents-<uid>.slice`), root, an agent's uid outside `agents.slice` (an agent that owns nothing: its cron or at jobs), or another local user. A mark carries `0x41` in its top byte, so a mark another tool wrote never reads as root's or an agent's.
- On the way in, the kernel's own lookup finds the socket the packet goes to (for a SYN, the listener; the lookup TPROXY uses), and a connection from an agent gets in only when that socket was made in the agent's own slice, at any level below it: its worker, Chrome, AI CLIs, terminals, desktop, tasks. A connection across `lo` keeps its conntrack entry and loses its socket, so the way in reads the mark the way out set.
- The sender is its socket's cgroup, never its uid: a setuid-root program an agent runs stays in the agent's cgroup, so it is that agent. The uid counts only outside `agents.slice`.
- Root reaches everything. Another local user reaches anything but an agent's listeners. Agents reach the computer's own listeners only for DNS (TCP and UDP 53) and what `config.json`'s `services` lists (`sudo agentes-runner services allow tcp/11434`, `list`, `remove`), plus, automatically, the loopback ports of the proxies and the Claude endpoint in the runner's own environment (what it hands the AI CLIs) and of the server it is paired with.
- Only new connections are judged. Ports don't matter to the table, so the `ss` polling and the per-port sets are gone.
- An agent sends nothing but TCP, UDP and ICMP across `lo`, and nothing untracked. A new connection of an agent routed into a bridge or a veth with no default route (a container's or a VM's network on this computer) is refused; so is one sent to loopback and DNAT'ed anywhere else (a port published on 127.0.0.1 into a container), told by its conntrack entry, since in the output hook `oif` is where the route went before DNAT. Ports published on the computer's other addresses stay reachable, as they are from anywhere. Interfaces with a default route (a bridged uplink, an LXC container's veth) are no guest network.
- The table is loaded again whenever what it is made of changes (an agent, a slice made anew, `agents.slice` made anew, the services, the uplinks) or it is gone, checked every 2 s (a stat per slice and `nft list tables`; listing the table itself would walk the whole cgroup tree), and right after `systemctl start` makes a slice, before any process of the agent runs. A load that fails keeps the table loaded before; a slice gone between the look and the load is looked at again once. Without `nft_reject_inet`, refusals are drops.
- `start()` loads `nft_ct`, `nft_socket` and `nft_reject_inet` (an explicit `modprobe`, whatever `kernel.modprobe` says), starts every listed agent's slice, then loads the table, or stops the runner: "System mode needs Linux 5.13 or later with nft_socket, and nftables 1.0 or later".

### 2. What an agent may bind

- Each agent's slice denies TCP binds only in the band, the browser pairs of the computer's uid range, its own pair excepted (`SocketBindDeny=tcp:<band>`). `bind(0)` matches no rule with ports, so it binds, and Linux's ephemeral range must stay outside the band (read again at every start). The Cloud's 20000-20999 gives 10000-11999, which leaves the Kotlin daemon's ports free; the default 20000-29999 keeps all of 10000-29999. On the server's own computer the band is the whole computer's range, not an organization's block.
- Before each worker starts, root starts the slice, maps it, sets the policy and runs `agentes-runner bind-check` as the agent, launched as every agent process is. That needs systemd built with `BPF_FRAMEWORK`, checked first: without it `SocketBind*` is ignored. On 127.0.0.1 and ::1 it proves: other agents' pairs at both ends of the band are refused; its own pair and a port on each side of the band bind; `bind(0)` binds outside the band; it reaches its own new listener (tried every 100 ms for 5 s: on the server's own computer the host's guard maps a slice at its next check); and root's listeners refuse it (root's own on port 0, while root waits: a completed connect fails the check, a reset or no answer in 2 s passes). It prints its /tmp, which root compares with the agent's own folder. A bind that comes out other than the policy says (a refusal for a taken port proves nothing either way) exits 3: the kernel still enforces another policy on that slice.
- systemd up to v258 neither re-attaches an active slice's bind programs when `set-property` changes its policy (that branch of `bus_cgroup_set_property` invalidates nothing) nor detaches the programs it replaces whenever it realizes the slice again, as it does when the slice's first process starts or its last one ends (fixed upstream after v258, "core: Don't leak BPF links when realizing a cgroup again"). So a slice with processes keeps the earlier policy, the earlier runner's `SocketBindDeny=tcp` or a wider band, plus a copy for each time it was realized again, all enforced. A `daemon-reload` replaces only the latest copy; re-executing systemd drops every copy (their descriptors close on exec) and attaches each slice's program from its policy, stopping nothing. At the runner's start (`prepareAgents`) root sets every listed agent's policy, then probes each; when probes exit 3 it runs `systemctl daemon-reexec` once and probes those agents again. An agent whose probe still fails is logged and left out, and the others serve; its processes stay refused, since each proves its isolation again before it starts.

### 3. Each agent's own temporary folders

- The launcher first mounts, as root on the computer, the agent's own tmpfs at `/run/agentes-runner-tmp/<uid>` (mode 0700, up to half the RAM, each page counted in the agents' shared memory; once after each boot, under a lock so two first launches don't stack two). Then it runs each agent process in a mount namespace of its own (`unshare --mount --propagation slave`) where root binds that tmpfs's `tmp`, `shm` and `lock` (mode 1777) over `/tmp`, `/dev/shm` and `/run/lock` (where it is world-writable), and `/var/lib/agentes-runner-tmp/<uid>/var-tmp` on disk over `/var/tmp`, all in folders only root reaches, then becomes the agent. So they are in memory and empty after a reboot, or on disk and kept, as the computer's own are, and each agent has its own room. Every launch of the agent binds the same folders, so its processes share one /tmp. Inside it root only creates `/tmp/.X11-unix` and `/tmp/.ICE-unix` (`mkdir`, never a `chmod` an agent's link could aim). tmpfiles lines remove what is 10 days old (30 in /var/tmp).
- cron and at would start an agent's jobs in the computer's own mount namespace, outside its slice: with the shared /tmp, while on the network such a job owns nothing (§1). The runner lists each agent's user in `/etc/cron.deny` (made where missing: without it or `cron.allow`, cron takes everyone's jobs) and in `/etc/at.deny` where it is (without it or `at.allow`, at takes root's alone), at the agent's first request after each start. An allow file, where one is, already leaves agents out; the Cloud keeps both root's.
- An agent's X server keeps its display lock in that /tmp: root reads it there (never through a link or a pipe), and a display is taken while anyone holds its abstract socket `@/tmp/.X11-unix/X<n>`, an X server or an agent squatting the name.

### 4. adb

- The launcher sets `ANDROID_ADB_SERVER_PORT` to 30000 + uid mod 2768: outside every band and Linux's ephemeral range, one per uid in any range of up to 2768 uids. adb, the Android Gradle plugin, Expo and React Native read it.

### 5. Install

- `install.sh --system` installs `nftables` and `iproute2`, and refuses a systemd without `BPF_FRAMEWORK` (Ubuntu's), where no agent process could start. `service install --system` writes `/etc/tmpfiles.d/agentes-runner.conf`. The setup skips the server's own computer there, saying why.

### 6. The Cloud

- Its guard's table keeps accepting agents on `lo` and leaves loopback to this table, as before; its traffic table marks only connections that don't go out on `lo`. Its stack step loads `nft_socket` with `nft_ct` and `nft_reject_inet`, runs the runner with `--agent-uid-range 20000-20999` (refusing to narrow it while `agents.json` lists a uid above 20999; the runner refuses such a uid too), and moves the runner pin only after §7.

### 7. Proof before production

- `isolation.root.test.ts` runs as root on real kernels in CI's `isolation-root` job, each booted in QEMU from a dated image checked against its published checksum: Ubuntu 24.04 (its own kernel; its systemd has no `BPF_FRAMEWORK`, so the bind policy is left out there) and Debian 13, the Cloud's release (Debian's kernel, systemd with `BPF_FRAMEWORK`), both with real Gradle, the Kotlin daemon, adb and Xtigervnc as two agents at once (Debian's JDK and adb, a checked Gradle distribution), and Chrome on Ubuntu. It ran first against the code before this change, with that code's results as its expectations, holes included, then this change turned them. Each case runs on 127.0.0.1 and ::1: own listener (port 0 too) yes, another agent's no, one port number on two addresses, another agent's browser port, root's listeners and DNS, UDP, a setuid-root copy of python3, an agent's uid outside its slice, a slice made anew, the table deleted by hand, loopback made untracked, a container network with DNAT from a public and from a loopback address, UDP-Lite, the bind check with reject and with drop, the private /tmp and /dev/shm in memory, an in-place upgrade from the earlier runner's policy on a slice with processes (and the copies systemd leaves attached) and its rollback, cron and at refused, and the abstract Unix sockets the agents' programs hold.
- Before a production rollout: an Android build (an Expo or React Native template, prebuild, `./gradlew assembleDebug`) as one agent while another runs a dev server on the same port, on a disposable Debian 13 machine; then `nft list tables`, `ss -tlnpe` and `lsmod | grep nft_socket` there; and an in-place upgrade from the current pin on a computer whose agents have processes running (a task, a desktop): the runner comes up, re-executes systemd once and every agent's probe passes.
- On every computer, the probe proves at every worker start, on that kernel, that `bind(0)` works, that the agent reaches its own listener, that root's refuse it and that its /tmp is its own, before the worker exists. It has no second agent, so that other agents' listeners refuse it rests on the table's rules (another agent's listener and an unmapped one in `agents.slice` take the same rule) and on `isolation-root`, which must pass before any runner pin moves.

## Consequences

- Gradle's daemon, its workers and its single-use daemon start. The Kotlin daemon runs where the band leaves 17001-17999 free (the Cloud's range, or a self-hosted computer installed with `--agent-uid-range 20000-20999`); elsewhere it falls back to compiling inside Gradle, and builds still succeed. Each agent has its own adb server. A dev server an agent starts, on any port, is its own at once. No emulator: a Contabo VPS has no `/dev/kvm`. Expo's default debug build (four ABIs, 2 GB heaps) used all the agents may use of an 8 GB computer, 5.8 GB and 1.9 GB of swap, in 13 minutes, once agents shared the computer (2026-11-02, ADR 0057); at 60% each it was stopped for memory.
- Self-hosters lose agents' access to services they run on the computer itself (a Postgres or Redis they installed, an Ollama, a native web server reached through a local address) until they list them. On the server's own computer agents keep the app (the address the runner connects to, and Docker's published ports through their DNAT) and lose Postgres and the containers' network.
- UDP between agents and to the computer's services is closed too (statsd, syslog and OpenTelemetry collectors need `services allow`).
- System mode needs Linux 5.13 or later with `nft_socket` and nftables 1.0 or later (Debian 12 and 13, Ubuntu 22.04 and 24.04 have them), and systemd with `BPF_FRAMEWORK` for every agent process, browser or not (since ADR 0057; Debian 13's has it, Ubuntu's lacks it, so system mode doesn't run on Ubuntu).
- A worker that can't start (its probe failed) fails the request waiting for it at once with the probe's words, not with the start's 20 s timeout. Showing it on the computer's page waits for a protocol field.
- Upgrading: the old table stays until the new one replaces it in one transaction; the guard loads before any slice's policy is relaxed, and the runner's start re-executes systemd once where a slice with processes keeps the earlier policy (§2). Tasks that survived the runner's restart are covered from the first new table and keep the shared /tmp until they end; what agents left in the shared /tmp stays until it ages out. Rollback: an older runner puts back its own table and `SocketBindDeny=tcp`, but on a slice with processes systemd keeps the newer programs, so that runner's probe (which wants `bind(0)` refused) fails and it restarts every 5 s until `systemctl daemon-reload` (its policy is the stricter, so a reload is enough) or a reboot; nothing to migrate.

### What stays open

- **Abstract Unix sockets** are still shared between agents, a known limit: they belong to the network namespace and have no permissions, so any agent reaches another's abstract listener and can take a name before it. Of the agents' programs, `isolation-root` finds one that listens on one: each desktop's X server, on `@/tmp/.X11-unix/X<n>`, which takes the X cookie (another agent, without it or with a wrong one, is refused). An agent that holds a display's name first keeps an X server from starting there (Xtigervnc: "Cannot establish any listening sockets"), and holding all fifty would keep every other agent's desktop from starting. Gradle's daemons, the Kotlin daemon, adb and Chrome hold none. By their code, not run here: the desktop's session manager (xfce4-session, through libICE) also listens on `@/tmp/.ICE-unix/<pid>`, behind the ICE cookie in the agent's home; the session and accessibility buses are path sockets in the agent's own /tmp with D-Bus 1.15.2 or later (Debian 13), and admit their own uid alone anyway; Python's multiprocessing uses path sockets in a private folder. What stays open is a program an agent starts on an abstract name without checking its peer, and denial of service by names taken first. Closing it takes a network namespace per agent (egress keyed on `meta skuid`, the Cloud's counters and quarantines, DNS and every launcher path change with it) or one Landlock domain per agent (Linux 6.12's abstract-socket scope is per launch, and libxcb doesn't fall back from EPERM to the path socket, so the desktop's session couldn't reach its X server without a per-agent zygote). Neither is built, and whether to close it is not decided.
- **A non-loopback listener** an agent binds (0.0.0.0) is reachable from outside the computer wherever the host's firewall lets it be (an operator's guard may close inbound), so another agent can reach it through an outside relay. Agents should bind private servers to 127.0.0.1; SELF_HOSTING.md says so.
- **`agents.slice` stopped and started by root** while the runner runs: until the next check (2 s) the table names the old cgroup, agents fall back to their uid (owning nothing), and a setuid-root program inside counts as root. Root-triggered and narrow; `setpriv --no-new-privs` in the launcher would close it, and the Cloud guard's uid-keyed egress with it, at the cost of FUSE mounts and rootless podman.
- **Another tool writing `ct mark`** on `lo` after this table makes that connection read as another local user's: it can reach root's listeners, never an agent's. Nothing does by default; the probe's check of root's listener catches it at the next worker start.
- **TIME_WAIT**: a SYN on a 4-tuple still in TIME_WAIT finds no full socket and is refused, where the kernel would have handed it to the listener: one client cycling every ephemeral port to one server port within 60 s of the server closing first. Keep-alive in load tests.
- The uid range must hold only agents: a non-agent user with a uid in it counts as an agent that owns nothing.
- A root-created socket handed to an agent would count as root's. The runner hands none.
