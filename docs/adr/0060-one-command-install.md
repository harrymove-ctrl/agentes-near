# 0060. One-command install, native mode, and the server's computer

- Status: Accepted. Built: the installer, the server's computer, plain words, the usage report (§5), the setup's questions for the server's computer (§3) and the usage report (§5), native mode's server and its packages (§2), and the first account by an owner link or key (§6), with the desktop app's server on the same computer running on its owner key (ADR 0066 §7); the setup doesn't hand out its owner link yet. Not built yet: the installer's native path (`install.sh --native`, which uses those packages), so, from a terminal, a Mac without Docker installs the package by hand for now (the desktop app runs it with no terminal, ADR 0066 §7). Superseded in part by ADR 0077 (2026-10-28): in §3, a row's first token gives the computer to the organization's agents that have none, with no exception for servers with cloud computers.
- Date: 2026-10-24. Revised 2026-10-25: the usage report is built, on by default with a way to turn it off (§5); the setup asks about the server's computer and the usage report, and ends with the link the phone and desktop apps open (§1, §3, §5); native mode, the first account and the desktop app's server here are built (§2, §3, §6)
- Extends: ADR 0003 (PGlite), ADR 0025 (connected computers), ADR 0030 (isolation on computers), ADR 0036 (one runner per organization), ADR 0041 (accounts on a computer)
- Out of scope for now: Windows as the server (the desktop app is a client there, ADR 0066; WSL2 follows the Linux path), a container image as the agents' computer, native mode as a server database at scale

## Context

Self-hosting starts with the setup wizard (`npx @agenteschat/setup`, which needs Node.js, or the same wizard from the app's image) and needs Docker with Compose ≥ 2.23.1. Distribution packages differ: Debian 13's `docker.io` has no Compose plugin, and Debian 12's `docker-compose` is Compose v1. Most Macs have no Docker, and installing a VM just to try an app is the friction that stops people.

After the install, agents still need a computer, and on a fresh server nobody has connected one yet (ADR 0025). And the screens about computers (onboarding, preparing, the computer's page) are read by people who aren't developers.

## Decision

### 1. One command

`curl -fsSL https://agentes.chat/install | sh`. The script is `install.sh` at the repository root (POSIX `sh`, short enough to read), served by every instance at `GET /install` and `/install.sh`, and attached to each release. It only bootstraps, then hands off to the existing wizard, which keeps every check and fix:

- **Platform:** macOS or Linux on x64 or arm64. Anything else (32-bit, Windows) gets a message and a link to `SELF_HOSTING.md`; WSL2 follows the Linux path.
- **Cut-off downloads:** the whole script is one `main` function, called on the last line, so a partial download runs nothing.
- **Terminal:** it uses `/dev/tty` only when it opens (`(exec </dev/tty) 2>/dev/null`). `[ -r /dev/tty ]` is true with no controlling terminal (cloud-init, CI), where opening it fails. Without a terminal the wizard gets `/dev/null` (defaults plus flags), because under `curl | sh` stdin is the rest of the script.
- **Docker (Linux):** Docker's own install script runs only after a yes (or `--yes`), and never when `docker` exists. When Compose v2 ≥ 2.23.1 is missing, it installs the official plugin binary, pinned with its SHA-256 in the script, instead of relying on package names (in Docker's system plugin folder as root, in the user's own otherwise). Without root, and without access to Docker or with `--computer yes` (the agents' computer needs root on Linux), it runs itself again with `sudo` before anything else: the same file under `sh install.sh`, or, under `curl | sh` where there is no file, the published installer. An install that user has in `~/agentes` stays there, since root's default folder is another.
- **Bun:** a pinned version with its SHA-256 in the script, unless a new enough `bun` is on `PATH`. On x64 it's the `-baseline` build, because server CPUs may lack AVX2. musl systems are refused with a clear message.
- **Hand-off:** `cd` to the install folder, then `bun x --bun @agenteschat/setup@<version>` with the flags passed through.
- **Flags:** `--dir`, `--yes`, and `--plan` (or `--dry-run`), which prints each decision and the commands it would run and runs nothing (what the tests assert). `--native` comes with the installer's native path (§2); until then it says so and stops. Every other flag goes to the wizard, and a test checks the wizard accepts every option the installer hands it; with its `--json`, the installer's own lines go to stderr. `AGENTES_INSTALL_SETUP` points at a local build of the wizard. A version is held the compose file's way, with `AGENTES_IMAGE` in `.env`.
- **Folders:** `/opt/agentes` as root, `~/agentes` for a user who can already use Docker, `~/.agentes` in native mode.
- **The wizard's last questions,** after the way in and email, each a yes/no with its default and a flag: the agents' computer (§3, `--computer`, and `--computer-commands` for a Mac) and the usage report (§5, `--telemetry on|off`, yes by default, in the words of the web app's switch, which a test keeps equal). The usage answer goes into `.env` as `TELEMETRY=on|off` either way, so it's visible there and a run again doesn't ask; the wizard never prints the report. Which question comes next and what `.env` gets are pure functions of the flags, `.env` and the answers so far (`decideComputer`, `decideTelemetry`), tested like the plan.
- **The compose file** is served by every instance at `/install/docker-compose.yml` (the one it was built with), and the wizard downloads agentes.chat's (the build agentes.chat Cloud runs, from `main`) into a folder that has none. It saves only a compose file: an instance older than the route answers that address with its web page, which the wizard refuses with the fix.
- **The end:** the address, the link the phone app opens on it (`agenteschat://connect?server=…`) with its QR code, and what to do next. Only for an https address: the phone app opens no http server, and a phone reaches only its own localhost, so `local` has neither. The desktop app opens the same link (ADR 0066 §3). `--json` gives the same as `appLink` (and `phoneLink`, kept; `null` without https), with `computer` (`on`, `off`, `skipped`) and `telemetry` (`on`, `off`).
- The docs also show "download, read, then run".
- The desktop app shows the command where a person needs it (ADR 0066): under Connect, as "Don't have one yet? Run this on it", for a server without a screen (a VPS, a Mac mini over SSH); on Windows, the WSL 2 form `… | sh -s -- --network local`, whose server the PC then finds at `localhost`. Both stay hidden until the command works from a clean machine (the repository, the setup package and the image public). The app connects to an install by its address, by what it finds on this computer or the Tailscale network, or by the link the setup prints at the end; an install on the same computer opens at the address it gives itself (`PUBLIC_URL`, `http://localhost:3000` with `--network local`), the only origin it accepts sign-ins from.

### 2. Docker or native

- **Linux:** Docker and Postgres (the compose file).
- **macOS:** Docker when an engine answers within 5 seconds (Docker Desktop, OrbStack, Colima). When Docker is installed but doesn't answer, it says "start Docker, or pass `--native`", because moving from native to Docker later is a dump and restore. With no Docker at all it goes native and says why. Until the installer's native path is built, a Mac without a Docker that answers is told to install or start one, and nothing else runs.
- **Native mode** is Bun plus PGlite, selected by `DATABASE_URL=pglite:///absolute/folder`. It's the same WASM Postgres with pgvector the tests run on (ADR 0003), so the migrations and the SQL are the same, with no native binaries. Embedded Postgres binaries have no pgvector, and Homebrew or Postgres.app are one more install. Built: `agentes-server` (below).

**PGlite's limits, and what the adapter does about them:**

- One process, queries one at a time, small teams and data, 0.5 to 1 GB of memory (measured: about 1.1 GB at the peak of the first start's migrations, 0.4 GB once it runs). Servers should use Docker; moving there is a dump and restore.
- PGlite answers within the same turn of the event loop and hands the next waiting query its turn at once, so queries queued together (a page's requests, the workers, a run's streaming) would run back to back and hold timers and sockets until they all end. The adapter starts each query and each transaction a turn (`setImmediate`) after the one before it, and each query inside a transaction too (measured: 200 queries queued at once, the longest wait for a timer 6 ms instead of the whole batch's 300 ms). Queries made while PGlite still starts skip that order (PGlite itself holds them until it has started): its own start-up queries go through the same methods, and queued behind an early one they would wait for a start that waits for them.
- Two processes open the same data folder without an error, and two Postgres engines writing one folder corrupt it. So whoever opens a folder's database (`openPglite`: the server, every `agentes-server` command, `main.ts`) holds the system's own lock on the file `db.lock` beside it, SQLite's for an open write transaction (`bun:sqlite`), which the system drops however the process ends: a crash, `kill -9` or a power cut leaves nothing stale behind. Beside the folder, never in it: Postgres opens every file of its folder when it recovers, and closing any descriptor of a file drops the process's lock on it. `agentes-server` also takes the folder's pid lock (`server.lock`, the runner's lock helper, shared) before anything else, for the message that names the other process: written whole and then linked into place, stale when its process is gone or when it was taken in an earlier boot (its pid may be another process's after a restart), and taken over only if it is still the lock judged stale.
- PGlite's data format changes when it moves to a new Postgres major version. PGlite is pinned exactly, and what wrote the folder is stored next to the data (`db/agentes.json`: `{ pglite, pgMajor }`). A version whose Postgres major differs refuses the folder before opening it (exit 4). The upgrade, run by whoever installed it with the server stopped: the previous version's `db dump`, then the new version's `db restore`, which builds the new database in `db.new/`, renames it `db.restored/` once complete, moves the old folder to `backups/db-pg<major>-<date>/` and puts the new one in its place. A restore that fails leaves the folder as it was, and one stopped between the last two renames is finished by the next command. A copy of the data is only ever taken with the server stopped.
- A dump and a restore hold the whole database in memory several times over: PGlite's `pg_dump` writes into its WebAssembly memory and hands back a string, and a restore runs as one batch of statements. Measured: dumps of 200 and 300 MB peaked at 2.8 and 4 GB, and the first one's restore at 2.2 GB, so a database over about 500 MB needs more than 8 GB of memory to move or to upgrade (on a bigger computer, from a copy of the folder).
- One process means the in-memory pub/sub.
- PGlite starts Postgres with `fsync` off (`-F`), and its Node filesystem has no fsync, so a commit reached the system's cache with no promise of reaching the disk; Postgres documents that as a risk of corruption after a power cut, not only of lost writes. The adapter starts Postgres without `-F` and with `wal_sync_method=fsync` (PGlite's `fdatasync` does nothing), and gives the filesystem an fsync that reaches the system (`fs.fsyncSync`, folders included), so a commit is synced before it's answered, as Postgres does. A crash of the process loses nothing it answered either: twenty `kill -9` while messages were being posted lost none, and every restart passed `db check`.
- Native mode has no backup job of its own: a backup is a copy of the folder, or `db dump`, taken with the server stopped (both need the folder's lock).

**The program, `agentes-server`** (`apps/server/src/native.ts`):

| Command | Does |
|---|---|
| `agentes-server [--data <dir>]` | Runs the server until SIGTERM or SIGINT (it drains like `start.ts`, 20 s). `--data` defaults to `~/.agentes`. |
| `agentes-server migrate` | Migrates and exits. |
| `agentes-server db dump [--out <file>]` | Plain SQL of the whole database, with `INSERT`s, no owners and no grants, so `psql` restores it into the Docker install's Postgres 18 with pgvector. |
| `agentes-server db restore --in <file>` | Into a folder with no database; or, for an upgrade, over one of another Postgres major (moved to `backups/`). Never over a database this version opens. |
| `agentes-server db check` | Opens it and prints `{ ok, pgMajor, pglite }`. |
| `agentes-server telemetry` | Prints the next usage report (§5), exactly, as `main.ts telemetry` does, and sends nothing. With the server stopped: the web app's "See what is sent" shows it while it runs. |
| `agentes-server version` | Prints `{ version, pgMajor, pglite }`. |
| `agentes-server service install\|uninstall\|status` | A launchd agent (macOS) or a systemd user unit with lingering (Linux), for installs from a terminal. |

Exit codes: 0 stopped cleanly, 1 an error (one line on stderr), 3 another `agentes-server` holds the folder (its pid in the message) or another program has its database open, 4 the folder needs the upgrade, 5 the port is taken. Every command that opens the database takes the folder's lock.

**The folder** (`--data`, mode 700):

- `.env` (600): only what is chosen or generated. A new folder gets `AGENTES_SECRET` and `PORT` (4310, or the next free port up to 4329: not 3000, which the Docker install and developers' tools use); an installer adds what it decides (`PUBLIC_URL`, `HOST_COMPUTER_TOKEN`, `OWNER_CLAIM_SHA256` or `OWNER_KEY_SHA256`). Variables already in the environment win over it. Native mode itself is not a setting: `DATABASE_URL=pglite://<dir>/db`, `FILES_DIR=<dir>/files`, `HOST=127.0.0.1` and `NODE_ENV=production` always; `WEB_DIR` is the package's `web/`; `PUBLIC_URL` defaults to `http://127.0.0.1:<PORT>`, and `INSTALL_MODE` (§5) to `native`, so the usage report says so even in a container.
- `db/` the database, `files/` uploaded files, `logs/server.log` the log (5 MB × 3, rotated; the console gets the same lines).
- `server.lock` the pid lock: a second start exits 3, a lock whose pid is gone or that an earlier boot left is taken over. `db.lock` the database's own lock (above).
- `server.json` `{ pid, version, url, publicUrl, startedAt, pglite, pgMajor }`, written once it listens and removed when it stops. Ready means `GET /api/health` answers 200.
- `backups/` the databases an upgrade's restore moved aside.

It listens on `127.0.0.1` only and answers only requests whose `Host` is `127.0.0.1:<PORT>`, `localhost:<PORT>` or `PUBLIC_URL`'s host (421 otherwise), so a web page that points a name of its own at 127.0.0.1 (DNS rebinding) gets nothing. Sign-in and saving accept only `PUBLIC_URL`'s origin, so a page opened at one of its other names (someone typing `localhost:4310`) is sent there with a temporary redirect (`PUBLIC_URL` changes with Tailscale); its API answers at all three, for the desktop app and the agents' computer on `127.0.0.1`.

**Packages** (`scripts/native-package.ts`): the server bundled with Bun into `server/lib/native.js` (entry `server/native.js`), PGlite, pgvector, PGlite's `pg_dump` and libpg-query beside it (they load WebAssembly from their own folders), the migrations, the PDF fonts, the built web app in `web/` (with `runner/agentes-runner.mjs`, which every server offers for download), the launcher `bin/agentes-server`, `LICENSE`, `NOTICE` and `licenses/` (Bun's, and every bundled package's). Source maps and drizzle-kit's snapshots stay out. The server is JavaScript and WebAssembly, so one Linux machine builds every package: only `runtime/bun` differs, the version install.sh pins with its SHA-256 for each computer (darwin-arm64, darwin-x64, linux-x64, linux-arm64).

- A `v*` tag's release carries `agentes-native-<version>-<os>-<arch>.tar.gz` (66 MB for Linux x64), `native.json` (`{ version, pgMajor, pglite, files: { "<os>-<arch>": { name, sha256, size } } }`) and `native.json.sig`, its minisign signature with the desktop updater's key (`tauri signer sign`). The installer checks the signature with that key, pinned in it, then each archive's SHA-256, before it extracts anything.
- They are fetched through agentes.chat, like the desktop app's builds (ADR 0036 §9): `GET /api/native/latest` answers the newest `v*` release's `native.json` and its signature, `GET /api/native/download/<version>/<file>` one of its assets, read with the same token and cache as the desktop app's. A `desktop-v*` release is never taken for one of these. The signature makes the route untrusted.
- A package extracts to `~/.agentes/app/<version>`, with `current` as a symlink and the previous version kept.
- The desktop app carries the same `server/` and `web/` and runs `server/native.js` itself, as its child, with the program it already ships for agents' work on that computer acting as Bun (`BUN_BE_BUN=1`; that program, compiled for `bun-linux-x64-baseline`, runs it): its own copy in `~/.agentes/app/<version>`, updated with the app, and no service, which is for installs from a terminal (ADR 0066 §7). Anything on this computer can listen on a loopback port, so `server.json`'s `pid` is what tells a program that started the server its own answer from another's: the app trusts health only from the pid it spawned.

**Service:**

- The service is a launchd agent on macOS, or a systemd user unit on Linux (with `loginctl enable-linger`): `agentes-server service install` writes it with the same unit and plist writers as `agentes-runner service install`. A Mac mini that must come back after a power cut needs automatic login or a LaunchDaemon; the docs say how.
- It isn't started again after exit 4, which retrying can't fix: systemd by `RestartPreventExitStatus`, and launchd, which starts an agent again after anything but 0, because under it (`AGENTES_SERVER_SERVICE=launchd`, in the agent's environment) that exit is 0, its reason in `logs/server.log`. A folder or a port in use can free up, so exits 3 and 5 start again, every 5 s (systemd) or 10 s (launchd).
- The service starts the launcher of the version that installed it (`app/<version>/bin/agentes-server`), so a new version extracted beside the old one takes over once its own `service install` runs (the installer's upgrade does both).
- With `PUBLIC_URL=http://localhost`, the phone's QR code can't reach the server, and the wizard says so. When the Tailscale CLI is there, it offers `tailscale serve` and writes the `ts.net` address.

### 3. The server's computer

The machine that runs agentes.chat is also a computer for its agents, "Computador deste servidor". It's on by default: the wizard asks, saying what it adds, and `--computer no` skips it. Set up by hand, it's the token in `.env`, then the runner's install (`SELF_HOSTING.md`).

**The wizard's question:**

- **Default:** yes on Linux, as root with systemd (built with `BPF_FRAMEWORK`, since ADR 0096: Ubuntu's isn't, and the setup skips it there saying why), apt-get and 4 GB of memory or more (3.5 GB counts: a 4 GB server reports a little less); no under that, or without apt-get (the installer then can't install the screens' and browsers' packages), saying why; yes on a Mac, with commands off unless the person says yes (they run as the person there). Skipped, saying why and what to do instead (as a user other than root on Linux, the installer's command that runs it as root in the same folder), while sign-up is open or with `MACHINE_PROVISIONING=external` (the server refuses `HOST_COMPUTER_TOKEN` with either; `hostTokenConflict`, checked against the server's config by a test), on Linux without root or without systemd, inside the image, and on a machine already connected as a computer (its runner's `config.json` has a token): its service would be replaced, and its server would lose that computer. Without a terminal, the defaults; `--computer yes` where it can't be fails with the reason before Docker or any question, and so does a run with a token kept from a yes once either is set, since the server wouldn't start.
- **Yes:** `HOST_COMPUTER_TOKEN` (48 random bytes, base64) in `.env` and in `host-computer-token` beside it (mode 600, written again from `.env` on every run). Once agentes.chat answers, the wizard runs the server's own installer for computers at the address the compose file publishes the app on (`BIND_ADDRESS`, `HOST_PORT`): loopback, unless it's published on one other address only, where loopback would reach nothing, or another program, whose script root would run: on Linux with `--system --desktop --server <that address> --host-token-file <file>`, on a Mac with `--server … --host-token-file …` alone (the runner as the person, a launchd agent, `--no-exec` unless commands are on). The installer's own output shows only when it fails. Then the wizard waits up to 90 seconds for the runner's first sync, read from the runner's own log (the unit's journal, or `runner.log` on a Mac), and says "Agents' computer: this machine"; on a timeout it names that log, and a failure still ends with the address and links, with `ok: false`.
- **A run again** asks nothing: `.env` has the answer, and whether commands are on is read back from the installed service's arguments. The installer runs again only when the computer isn't running and answering, or its runner differs from the one the server serves (a new release), or a flag asked for a change: reinstalling restarts the service, which interrupts its agents.
- **No:** `HOST_COMPUTER_TOKEN=` left empty (the server reads it as unset), so a run again asks nothing. A no after a yes also removes `host-computer-token` and prints the command that removes the service (`agentes-runner service uninstall --host`).

- **Linux:** the runner is installed on the host in its system mode: a root supervisor that runs no agent code, and each agent as its own OS user with its own folder, the agents sharing the computer's memory and CPUs (ADR 0057 §2). A container isn't used, because Chrome's sandbox doesn't start in a container with dropped capabilities and the default seccomp and AppArmor profiles, `--no-sandbox` next to every organization's tokens is not acceptable, and a container can't hold one OS user and one desktop per agent.
- **macOS:** the runner on the Mac. Agents run as the person there, so the wizard keeps their commands off until the person says yes ("they run as you and can reach this server's files"). A dedicated macOS user is the safer yes (ADR 0030). Run by hand, `agentes-runner host` turns commands on unless given `--no-exec`. Its homes go in `~/.agentes-runner/host/orgs`, apart from the homes the agentes app runs in `~/.agentes-runner/orgs`. The desktop app's own server here starts its homes with commands on instead, like any computer paired from the app (ADR 0165 §7).
- **What a new organization's home allows** with `agentes-runner host`, on Linux and macOS: the browser, Claude Code and Codex, and commands unless `--no-exec`. Later changes (`agentes-runner tools`, the site) stay.
- **The desktop app's server here** (macOS and Linux, ADR 0066 §7): agents run as the person, on a Linux desktop too (`host --once`, below, writes single-user homes there with every tool off, and the app runs them), with the app's first tools: the browser, Claude Code and Codex when found, and commands off until the person turns them on.

**How it joins organizations:**

- `HOST_COMPUTER_TOKEN` (generated by the wizard, at least 32 characters) is given only to the runner. It's compared with `safeEqual`, never logged and never sent to browsers.
- The runner calls `POST /api/machines/host/sync` (no session, rate limited). The answer has one machine row per organization, with `machines.kind = 'host'` (the values are `connected`, `host` and `managed`). Each row has its own ordinary machine token, stored as a SHA-256.
- The runner (`agentes-runner host`) keeps one runner home and one child runner per organization (as the desktop app does, ADR 0036), syncs every minute and starts a child again with a backoff when it stops. Each child speaks the normal protocol, so outages, accounts and brains work unchanged.
- On Linux each child is a system-mode runner. Each organization's agents take uids from a block of 100 of their own, so two children never hand out the same uid, and the host keeps one loopback guard for all of them (one per child would replace the others' rules). That allows 100 organizations in the default range.
- A row with no token gets a new one at the next sync (after it's turned back on, say). A child whose token is refused makes the runner ask for a new one at once. A server started with another `HOST_COMPUTER_TOKEN`, or none, retires every row's token: each row keeps a hash of the one it was issued under.
- The runner turned off on the server (404) or refused (401) stops its children and waits. A server it can't reach leaves them running.
- Installing it on Linux, as root: `install.sh --system --server http://127.0.0.1:<port> --host-token-file <file>`. `--server` is where this machine reaches the server, since people may use an address the machine itself can't reach, and the service reads the token from the file (root only). Elsewhere: `agentes-runner service install --host --server … --token-file …`. The installer refuses `--host-token-file` on a computer already connected (its runner home has a token), on Linux and on a Mac alike: the host's service would replace that connection's.
- For a program that runs each organization's connection itself (the desktop app, for the server it runs on the same computer), `agentes-runner host --once` does one sync and starts nothing: it writes each organization's home where that program keeps its own (`~/.agentes-runner/orgs` unless `--state` says otherwise, on a Mac too), with `managedBy: "host"`, every tool off (that program turns on its own) and its workspace in `~/agentes/<organization>`, takes `--rotate <orgId>` for a token the server refused, and prints one JSON line, `{ status, homes: [{ orgId, orgName, machineId, home, new }], gone: [orgId] }` (`gone`: homes of this server it no longer serves, left for that program to remove). It runs as the person on Linux too and writes single-user homes there: the system mode stays the root service's.

**Which organizations it serves:**

- Only organizations the installation's first account (the person who set it up) made and is still an owner or an admin of. Its rows are paired by that account.
  - So that person is the computer's owner for ADR 0041: they add the Claude and ChatGPT sign-ins on it, and pick them per agent. For ADR 0059 §1 it is a computer someone paired, so only they add accounts there, and their plans think only for their own agents (ADR 0059 §3); other members' agents there think with a key.
  - Someone who joins through an invitation and then creates an organization of their own doesn't get agents on the operator's machine. A role isn't enough on its own, since an organization's owner can make anyone an admin or an owner there; who made an organization is recorded on its #general, which can't be renamed or archived.
  - The server refuses to start with `HOST_COMPUTER_TOKEN` and `ALLOW_SIGNUP=true` together: with open sign-up, a stranger could be the installation's first account. Nor with `MACHINE_PROVISIONING=external` (ADR 0065 §5): every workspace there gets a computer of its own, and no other computer joins it.
  - Serving more organizations is a later, explicit choice.
- In an organization it serves, the row is created with the organization, so onboarding's computer step lists it first (selected once it's connected: a computer that never comes up would leave agents waiting), and the runner picks up its token at the next sync (60 seconds).
- When a row gets its first token (new, or turned back on), the organization's agents with no computer start using it, unless the server has cloud computers. New agents start on it.
- Admins turn it off per organization ("Parar de usar nesta organização" soft-deletes the row) and back on.

**Guards:**

- The runner's state (`/var/lib/agentes-runner`) and the native `~/.agentes` are secret folders for agents' reads, like `~/.agentes-runner`. They hold every organization's machine token, and natively the database. `host-computer-token`, anywhere, is a secret file like `.env`: on a Mac the install folder (`~/agentes`) is also where the organizations' folders go.
- Files any computer uploads go to the server it's paired with, at the path the server gave. `PUBLIC_URL` may not be reachable from the host itself (a tailnet name served from a container).
- The token of the runner's `--token-env` is taken out of its environment, so neither the children nor the agents' commands see it.

The Cloud never sets `HOST_COMPUTER_TOKEN`: each Cloud workspace has a machine of its own (`kind = 'managed'`).

### 4. Plain words about computers

The onboarding, preparing and computer screens never name the system (Linux, Debian, Ubuntu), an address (IP), virtual CPUs, or the tools installed (Chrome, git, Node, Python, Rust, Docker, kernel). Sizes ("4 CPUs · 8 GB de memória · 75 GB de disco") and "um usuário para cada agente" stay.

- A computer's internet address appears only under an "Avançado" section of its page that only admins see, because firewall allow-lists need it.
- `packages/i18n/test/plain-computer-copy.test.ts` checks every string under `onboarding.computer.*`, `computer.*` and `machine.*` in both languages. A new screen about computers adds its namespace there.
- The steps for connecting your own server (Settings → Computadores) still say "Linux": that person needs it.

### 5. The usage report

A self-hosted server sends agentes.chat an anonymous usage report about an hour after it first starts and then once a day. It is on by default, and whoever runs the server can turn it off. agentes.chat's own servers always send theirs.

- **Counts and sizes, never content.** A random id made at the first start; the version, edition, install mode (`docker`, `native`, `desktop`: `INSTALL_MODE`, else a container means `docker`), system and uptime; the host's size and load; organizations, people and people active in the last 1, 7 and 30 days; agents; the computers seen in the last 30 days, one line per kind, system and size with how many are alike, their agents, their combined load and how much data the agents' browsers on them sent and received (the 50 largest lines); and for the last day, runs, tool calls, minutes of desktops watched or controlled and of terminals, and per provider and model the calls and input and output tokens, from the usage records every model call writes (the 50 most used). Never messages, files, names, emails, hostnames, paths, prompts, IP addresses, the sites agents' browsers visit, or ids of organizations, people or computers; a model outside the model catalog (`catalogModelOf`: a typed name, a deployment, a fine-tune or an ARN can name a company or carry an account id) goes as `other`. Both caps keep a report well under the 32 KB the receiver takes. `SELF_HOSTING.md` lists every field.
- **Sizes and load.** Self-hosters run anything from 2 CPUs and 4 GB up, so every machine says how big it is and how busy it gets. The host: the whole machine's logical CPUs (`os.cpus()`) and memory, the disk holding the files (`FILES_DIR`, else the working folder) and whether it runs in a container, rounded; in a container with limits, `limit` adds what the process may use (`availableParallelism()`, `process.constrainedMemory()`), since the load average and the memory figures stay the whole machine's. Load: the 5-minute load average per logical CPU of the machine and the share of its memory in use (`MemAvailable` on Linux, `vm_stat` on macOS, run without blocking the server; the page cache counts as free), sampled every 5 minutes, then the average and the highest over the last day. The server keeps its host's summary and the samples behind it in its own database row (`instance_telemetry`), so the report printed elsewhere has it and a restart keeps the day.
- **Computers (machine protocol 22).** The runner's `hello` carries `size` (its workspace's disk, and `limit` as above), and its next `pong` after each sample carries the last day's `load`; both are stored on the machine. Nothing new goes to the runner, so an older one sends neither and its computer is reported with its size unknown. A provisioned computer that hasn't said falls back to the provisioner's size (`machine_provisioning.specs`). The server's own computer has a row per organization it serves and counts once. A load older than a day is left out.
- **Browser traffic (machine protocol 23).** Only the agents' browsers are counted, never the rest of the computer. The runner opens one DevTools connection to each agent's Chrome it starts, attaches to every page, frame and worker (browser-level auto-attach, Chrome's own UI left out, nothing paused, service and shared workers once at the browser level and not again under each page they serve) and turns on network events with no bodies kept. Received: each finished response's encoded size, headers included, what a failed one had received, and nothing for a response a service worker served, whose own fetch counts. Sent: each request's headers and its `Content-Length`. WebSocket frames: their payload. URLs and headers are never kept or logged. Not seen: Chrome's own background requests, WebRTC, TLS and TCP/IP overhead, an upload without `Content-Length` (its headers only), a file Chrome saves as a download (its request only), a response until it finishes, and the page Chrome reopens when it moves to or from the agent's desktop, so the count runs under what the network carried. The runner adds a sample every `LOAD_SAMPLE_MS` (in system mode each agent's worker counts its own Chrome and root sums them), keeps the last day and sends it on its next `pong` (`browserTraffic`: `up` and `down` in bytes, the `hours` counted), like the load. The server keeps it on the machine (`browser_traffic`), and the report sums a line's fresh ones in MB, with their hours averaged and how many said (`computers`). The server's own computer runs a runner per organization, each with its own browsers, so its rows are summed into one computer.
- **Turning it off.** `TELEMETRY=off` in the server's settings, or the switch in Settings → General, which only the installation's first account sees (stored in the database). `TELEMETRY=off` wins, and the card says so. A development server (`NODE_ENV` not `production`) never sends. On agentes.chat's own servers (`PUBLIC_URL` on agentes.chat) it is always on and nobody has the switch: there, the first account is a customer.
- **Sending.** The JSON in a POST to `TELEMETRY_URL`, with a 10-second timeout. The due time is kept in the row (`next_report_at`): a restart waits out the rest of the day, a report that came due while the server was off goes 10 minutes after it starts again, and the first one comes an hour after the first start even across short runs (the desktop app). A failed send is tried again after 5 minutes, 30 minutes and 2 hours, then the next day's report takes its place: nothing queues up. Failures go only to the debug log; nobody sees them and nothing waits on them.
- **`TELEMETRY` is read when the server starts.** Whatever writes it (the wizard, the desktop app) restarts the server, or turns a running one off with the owner's switch (`PUT /api/app/telemetry`). That owner is pinned: nobody inherits the switch once the first account is gone, until no account is left (ADR 0073).
- **The desktop app's server here** writes `TELEMETRY=on|off` from its switch (on by default) and `INSTALL_MODE=desktop` into `~/.agentes/.env`, and starts it again when the switch changes (ADR 0066 §7).
- **The wizard** asks one yes/no question with one plain line saying what it is, and never prints the report. `agentes telemetry` (through the image, `docker compose run --rm agentes telemetry`) prints exactly the next report, on or off, and sends nothing.
- **Settings** shows a card with its title, the switch and "Ver o que é enviado" (the next report, as is), and a line only when `TELEMETRY=off` holds it off.
- **Copy** says what is sent, never why: "Send anonymous usage statistics to agentes.chat: counts such as people, agents, machine sizes, AI tokens used and how much data the agents' browsers send and receive. Never messages, files, names or sites."

The terminal and the card stay short, and the full explanation lives in one public place.

### 6. The first account: a claim or the owner key

"The first account owns the installation" lets whoever reaches a new server first take it, which on a public domain meant keeping it on localhost behind an SSH tunnel until the owner signed up. An install that leaves a secret for its owner closes that gap; an install by hand keeps the first-account rule.

- **A claim, from the setup:** `OWNER_CLAIM_SHA256` in `.env` is the SHA-256 of a one-time token (32 random bytes, base64url). The setup prints it as a link, `<server>/owner#claim=<token>` (and in the apps' `agenteschat://connect?…&claim=`), and keeps the token in `owner-claim` (mode 600) beside `.env` to show the same link again. `POST /api/auth/owner-claim { token, name, email, password }` makes the owner once, with a password, and signs them in (201); a wrong token is 401 and an existing account 409, so the claim is inert afterwards. The password is required: whoever opens the link is on another computer or a phone, and nothing else could sign that owner in again once the session ends (7 days without use). The web's `/owner` page reads the token from the fragment, which browsers never send to a server, and drops it from the history at once. The link works once and is kept like a password.
- **The owner key, from the desktop app** (the server it runs on the same computer): `OWNER_KEY_SHA256` is the SHA-256 of a key only the app holds (`~/.agentes/owner-key`, mode 600, in the 700 folder that already holds `.env` and the database). `POST /api/auth/owner-key { key, name?, email? }` makes the owner the first time, with no password, then, on every call, answers a one-time sign-in for the installation's first account (single use, 3 minutes), which a window trades at `POST /api/auth/sign-in/one-time-token` for a session of its own. So the app signs its owner back in whenever the session ends, and the key never reaches a web view; **Add a password** in the account menu (`POST /api/app/me/password`, only for an account without one) is for signing in from other browsers.
- While either is set and no account exists, every other way to the first account is refused, e-mail and social sign-up alike (`isSignupAllowed`, which runs in the user-create hook too), with `OWNER_CLAIM_REQUIRED`; `GET /api/instance` and `GET /api/app/auth-config` say `ownerClaim: true` for a claim, and the sign-in screen says where the link is instead of offering a form.
- Both write the account in one transaction holding an advisory lock, so two requests can't both find the installation without accounts. After the first account, the ordinary rules apply (ADR 0006).
- An account with neither a password nor Google or Apple (the run-here owner) is told on the sign-in screen that it signs in from the app on the computer that runs the server, instead of meeting a dead end.

## Consequences

- One line installs agentes.chat on a Linux server, or a Mac with Docker; with native mode, on a Mac without Docker too. With the server's computer, agents have a computer from the first minute.
- Two database engines in production: every migration must also run on PGlite (the tests already do), and a PGlite upgrade across a Postgres major needs the dump-and-restore path.
- On Linux, the server's computer runs agents' commands on the host. Their isolation is the system mode's OS users, not a container.
- The server's computer holds the agents of every organization it serves, and so of different people, on one machine. Fixed browser debugging and stream ports are guarded before any worker starts. Other local listeners are still discovered every 2 seconds; their startup and stale-port windows mean arbitrary local ports are not a hard boundary between agents.
- The first install is longer: the agent browser and the command-line tools come with the computer.
- The installer needs `@agenteschat/setup` on npm; until then, `AGENTES_INSTALL_SETUP` and locally built images are how it's tested.
- The wizard's compose download needs agentes.chat to run a release that serves `/install/docker-compose.yml`, so the wizard ships after agentes.chat does.

## Alternatives considered

- **`npx @agenteschat/setup` as the one command:** needs Node.js, which many servers and Macs don't have.
- **A container as the server's computer:** Chrome's sandbox needs seccomp and AppArmor exceptions there, and per-agent users, slices and desktops don't fit in it.
- **Embedded Postgres binaries, Homebrew or Postgres.app for native mode:** no pgvector, or one more install.
- **The server's computer for every organization, with the server refusing to start while sign-up is open:** invitations and creating an organization still let other people's agents onto the operator's machine.
