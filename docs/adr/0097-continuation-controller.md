# 0097. One controller decides how every turn ends

- Status: Accepted (built: the server, the web and the phone app). Amended by ADR 0109: a new `untried` verdict (the judge reads `means` and `tried`), a routine's untried `hand_off` held once; no routine only looks and tells any more. Amended 2026-11-07: §9's notice never starts a run (below).
- Date: 2026-11-01
- Amends: ADR 0089 (the follow-through check becomes the controller's judgment; its once-per-run flag becomes a shared budget), ADR 0095 (rolled-up hand-offs count as reported; the reply block shows the work in progress), ADR 0034 (a chain may go 4 agents deep), ADR 0053 (an agent's event routine that nothing can fire is refused)
- Code: `packages/engine/src/continuation.ts` (`decideTurnEnd`, `continuationVerdict`, `reportRunFailure`, `reportDroppedMentions`), `executor.ts` (the final-answer block, `askWithCard`, `parkOutage`, the `finished` hook), `notification-producers.ts` (`notifyRunFailed`), `dispatch.ts` (`dropped`), `jobs.ts`, `messages.ts` (`unreachedAgents`' `handedTo`), `consultations.ts` (`MAX_CONSULTATION_CHAIN`, `progress`, `handBack`'s `reported_at`), `schedule-tools.ts` (`neverFires`), `routines.ts` (`missingEventSource`), `packages/client/src/lib/consult-group.ts` (`consultProgress`), the web and phone `ConsultGroup` and notice lines, `packages/engine/test/autonomy/*`

## Context

Every autonomy case so far had the same shape: some gate between "something needs an agent" and "the agent did it" defaulted to nothing, and nothing noticed. The end of a turn had four such gates, each with its own flag and its own exceptions: the decision nudge, the answer nudge, the follow-through check (once per run, never for routines, never in an agents' DM unless it owed an answer, offers counted as done, a status list of what's missing counted as waiting), and the mission's ask nudge. A failed run published `run.finished` and nothing else. The autonomy invariants (I1 to I7) and their scenario suite state what must hold for every run kind instead.

## Decision

1. **One function, one call site.** `decideTurnEnd` runs where a turn has its final answer, for every brain and run kind (conversation, agents' DM, mission, routine). It returns continue (with the nudge to read), waiting, done, or ask with a card, and the run records it on a `continuation` step. Every run that ends `done` records one (the `finished` hook writes `ended` for paths that end otherwise), which the suite checks on every scenario.
2. **Cheap rules first, then one judgment.** In order: a bound already hit (stuck, the step backstop, the turn cap) or a quiet end (pass, the silence word, a reaction, a report card) ends it; a decision ended without a word, or a reply addressed to it that says nothing, continues; anything that brings it back (`wakesLater`: a follow-up, work handed off, a reminder, a detached wait, a mission card asking a person) waits, unjudged. Only then one judge call, kind `follow_through` so its metrics carry on, with three choices: `done`, `continue` (it said it will do more, offered reversible work inside the request, or stopped midway, or handed work by @mention to an agent outside the conversation, listed in the judge's `unreached`) and `ask` (it needs what only a person can give and described it instead of asking). `continue` at p ≥ 0.45 and at least p(ask), `ask` at p ≥ 0.45, else done; a judge error is done. A `continue` on a reply that named an unreached agent goes on with the "not delivered" note, so it hands the work over with `tell_agent`; a reply that only names one ends as judged (no extra turn, no second post).
3. **One budget.** The decision, answer, unreached and continue nudges share `CONTINUE.maxPerRun` (2), plus one ask nudge: at most 3 extra turns and 4 judgments per run. The review of the first draft counted 5 worst-case extra turns with separate budgets; one budget makes it 3. A second continue needs progress: more tool calls in the run (engine-run and bridged, `transcript.executedCalls`) than at the first; without it the run is told to ask. Told to ask and still describing, its reply becomes the question, also when the budget is spent (the turn right after the ask nudge is judged past the cap): the same `agent_questions` row and card `ask_user` posts, the run waits on it, the accountable person is notified, and the answer resumes the run as text.
4. **A person's answer starts the budget over; an agent's doesn't.** Answering the card (or any person deciding what the run waited on, or writing into it) is new input from a person, and a person acting is the bound: the count resets. Another agent's answer resuming the run keeps it.
5. **Run kinds.** A routine's run may continue once and never asks (its report reaches a conversation whose run can). An agents' DM run is read only while it owes an answer, and never asks (its answer carries what's missing back to the asker, whose controller decides). A mission's ask nudge keeps its mission wording.
6. **Judgments are recorded like every judgment**: the judge records usage with the org, the agent and the run, not billed to the agent's budget.
7. **A failed run reaches someone** (`reportRunFailure`). A conversation run that fails for good (not archived, no AI, a standing hold, a routine's) sends `run_failed` to the person accountable for it, else the agent's owner, once per agent and conversation, resolved by the agent's next good run there. A run another agent's @mention woke also tells that agent ("It couldn't finish what your mention handed it"), as a `consult_reply` note, so it tries another way or tells the person. Mentions get no hand-off rows: their answer is in the same conversation, and only the failure was ever lost.
8. **A provider outage parks the run.** Past the job's own retries, a retryable provider failure (or a retryable brain failure) no longer ends `gave_up`: the run waits (`transcript.outage`) and its job comes back at 2, 15, 30 and 60 minutes, then hourly, resuming the same turn with nothing repeated. After 24 hours it fails and is reported. Any other error fails at once. The first park posts one `provider_unavailable` note where it answers, and the readers of a waiting run (hand-off lines, the coordinator's context, the agent's status) tell the park from a wait on a person (`outageParkedSql`). A routine's continue keeps the earlier turns' record for its ledger and report.
9. **A skipped wake is said.** When dispatch can't wake an agent an @mention selected because only certain people may talk to it and the person behind the message isn't one (nobody, for a run without one), the message's routing decision says so (`audience: @x`, the reason vocabulary `settleReach` uses: `not_in_channel`, `audience`, `routine_creator_reach`) and the author gets a `wake_skipped` line people see too, telling it to have someone who may talk to that agent hand it over.

   *Amended 2026-11-07:* a run whose every message named an agent it couldn't wake woke itself through this notice, once per message, until the stretch's run limit (49 messages in 4 minutes). A notice about the run's own work (`SELF_REPORT_NOTICES`: `wake_skipped`, `work_check_in`, `run_stopped`, `talker_reply`) now joins that run while it is live and otherwise waits for the agent's next turn: `deliverNotice` never starts a run for one. The same agent left out again in the same stretch is told nothing more (`tellWakeSkipped`, which the not-callable skip of ADR 0131 §8 shares), the notice names the real cause (an owner's plan that answers only its owner, ADR 0059 §5, keeps everyone out, consultations too) and says to hand it over once, without the @, and stop. A mention a consultable agent takes still goes as a note (`settleReach`). An agent whose mention its colleague couldn't finish twice in one stretch hears the second failure without being woken.
10. **Work handed off shows moving.** The consultations list carries `progress` for open hand-offs (how many messages the consulted run posted in the agents' DM, the start of the latest, when); the reply block's line shows it ("12 mensagens até agora · …") on the web and the phone, reloads every 10 seconds while open, and an interim answer the consulted run posts announces the change at once. The count reads only the hand-off's agents' DM since the hand-off (the `(channel_id, created_at)` index and partition pruning). A hand-off's run that fails sends no `run_failed` into the agents' DM: the asker and the failed line carry it.
11. **Chains go 4 deep.** `MAX_CONSULTATION_CHAIN` is 4 (it was 2: a lead → a dev → a reviewer was refused at the third). Cycles are refused anyway, and the stretch limits bound the runs and budget a deep chain spends. A sub-result rolled up into the answer of the agent that handed it on is marked reported.
12. **A routine that can never fire is refused.** `create_routine` and `update_routine` refuse an event whose webhook the workspace doesn't have, with the setup step. A routine whose webhook goes away later still shows `needs_webhook`.

## Consequences

- The judgments grow by the agents' DM runs, routine runs and re-judgments after a continue; turns that end with a live waker are no longer judged. Measure continues per 100 runs and the share of continues whose next turn executed nothing.
- The suite's known violations are S01 and S02 (the router's answer-by-default) and S40 (handle-follows-name, not on main).
- A mission keeps going between turns through its own keep-going job (on main before this); the controller doesn't add the design's "mission contradiction" rule, and a mission's last verdict `ask` still holds that job (`followThroughVerdict` `waiting`).
- A router chain failure still gives nobody; the person is told at once that only a mention reaches an agent (S44 holds either outcome). The fallback to the last-talked-to agent belongs to the router.

## Addendum (2026-11-01): default-allow

Product direction: when a safety rule would make an agent go silent or not deliver, let the work happen; if it shouldn't have, people say "don't do that again" and the agent learns. Hard limits stay only for real security: permissions, audience, credentials, and outside text turning into actions.

1. **A routine set to act wakes the agents its message mentions.** Its own message (`hand_off`, no run behind it) now roots in the routine's run (`messageRoot` follows `meta.routine.runId`), so its mentions go through the same path as any agent's, minus the mention judge (the routine was told to name only agents that must act, so each one it names wakes): `dispatchMentions` with the routine's creator as the requester (`routineCreatorOf`), the runs it wakes keeping the routine's bounds (`fedByRoutine`). An agent outside that conversation gets it as a note (`meta.unreachedAgents` is written with the message, `settleReach`), an agent the creator can't talk to shows its line and its owner is told, and an agent the routine's run already handed it to (`tell_agent`) isn't woken a second time. The router stays out of a routine's message. A routine set to only look and tell still wakes nobody (text it read must not become actions); the line under it and its prompt say a person can set it to act.
2. **A provider outage reads as one.** A run parked on a provider outage (`outageParkedSql`) is `provider_down` in the agent's status, `outage` in a hand-off's wait (`ConsultationWait`), and `outage: true` on its receipt (`agent.run`, `run.finished`, `message.handled` and the list receipts): "The AI provider is down · retries by itself", never "working" or "waiting for your answer", on the web and the phone.
3. **Out-of-channel mentions go on from any conversation.** `settleReach` hands an agent's mention of an agent outside the conversation to it as a note from a DM or a private channel too (it used to forward only from public channels and show "wasn't passed on"). The receiving agent still needs the person behind the run, or the acting routine's creator, to be allowed to talk to it. Only the agents' DM hands nothing on.
4. **"Don't do that again" is remembered.** The `remember` tool reads a person telling the agent not to do something again, or to do it another way, as a request to remember: the agent saves it as a preference of its own with `everywhere: true` (no channel, worded without private details), which every later run reads in any conversation (`retrieveForRun`'s own items). Reflection (`reflectThread`) still turns corrections into lessons over time.


## Addendum (2026-11-03): a step that needs the person is never a blocker

An agent asked to read a person's messages on a service with no connector said it couldn't, then that the service's web version needs a QR code scanned with the phone, so it couldn't either. The rules gave a sign-in or a code as an acceptable reason to stop, the judges called that stop `done`, and the question check read "only if you want" as an optional offer, so the turn ended on a refusal. A step that needs the person (sign in, scan a QR code, type a code sent to them, solve a captcha, approve, grant a permission, give a key, a file or a fact only they have) is now handed to them, never a reason to stop, in every language:

1. **One rule, said once** (`HAND_OVER_STEP`, `tools/directory.ts`): do everything up to that step, hand it over with its request (`browser_ask_person` or `desktop_ask_person` once the page or app is at that step, `request_secret`, `request_approval` only for an approval someone else gives, `request_permission`, else `ask_user`), then go on. `HOW_YOU_WORK` carries it in place of the "real blocker" line, and the `untried` nudge (also the routine report's hold) ends with it. The agent stops only when nothing it has can hand the step over, and then says the one step and where.
2. **Consent**: a person asking for something of their own (their messages, account, files) consents to the access it needs; the agent asks first only when the way is unclear, and then offers to start ("you'll scan a QR code. Shall I start?"), never refuses. Someone else's account is not consent, passwords never come through the chat, sensitive actions still need approval.
3. **Means**: `turnMeans` describes the browser as using any website or web app signed in with the person's help (the way to a service with no connector but a web version), and names the hand-off requests the run has. The prompt's "Your means", `find_tools` with no match and both judges read the same lines; the `find_tools` capability line adds the web version when no connector exists.
4. **Judges**: `done` needs the person-only step already requested (or no way in `means` to request it); a reply that says it can't, stops or only offers in passing because of such a step is `untried`; one direct question offering to start a named way with the person's step, when the request left the way open, is `done` (it matches the consent rule), and so is a refusal because the account is someone else's; for `ask` and the question check's `none`, a way to do the request itself is never optional extra work, however it is worded.
5. **Asking**: `ASK_NUDGE`, the mission nudges (`MISSION_ASK_NUDGE`, `KEEP_GOING_PROMPT`) and the mission brief send a sign-in, a QR code or a code to the screen hand-off, not to a question card. The `ask_user` description (the rule in the prompt leaves the how to it): a way to do what was asked is never an optional offer.
6. **One reply, the last attempt**: the live view no longer keeps a held reply's text as narration when the next model call starts (narration already leaves the body with `agent.narration` or a tool call), and OpenCode's posted text is the text after its last tool call, not every text part of the turn. Claude Code's and Codex's posted text was already their final result.

Tests: autonomy scenarios S65–S68 (Portuguese, English, Spanish, French; fake provider, a judge that reads only means and tried) send the "can't, it needs your QR code" back with the hand-off and post only the final reply; unit tests pin the rule in the prompt, the means, the nudge and both judges' criteria. The DM "oi" size ceiling in `turns-eval` goes from 43,000 to 45,000 characters (44,076 measured).

## Addendum (2026-11-10): a held reply is never lost, a kept promise waits

Two turns went wrong at the same rules. In one, an answer that gave what was asked, with a caveat, was read as a give-up (`untried`): the reply was held back for another try, the next turn called `pass` ("nothing to add: already answered above") and the run ended quietly, so the person never got the answer. In the other, a status that promised to come back was nudged although a follow-up and the agent's own long work already covered it, and the nudge posted a second status a minute later.

1. **A held reply goes out unless replaced** (`Transcript.held`). The reply an `untried` verdict holds back is posted with the run's next words, or alone when the run ends without any: a pass, an empty turn or the silence word, the step limit or stuck line (the held reply goes first), a failed turn (the run ends done on it). The next words go through one judgment (`held_reply`): they stand on their own (they replace it), they build on it (both go out, in one message), or they add nothing ("nothing to add", "see above": the held reply alone). A judge error keeps both. A reply that asks for a secret in the chat is still never held nor posted.
2. **The run reads it as unseen.** The `untried` nudge after a held reply starts "Not posted yet: nobody has seen your reply above" and says to end without any text when that reply already answers, so the next turn never answers "already answered above" about words nobody saw.
3. **`untried` must beat `done`.** It holds a reply back, so it now also needs a higher probability than `done`. The criteria say an answer that gives what was asked is done with its caveats, and `untried` applies only while what was asked is still missing.
4. **A promise something already keeps waits** (`comes_back`). A `continue` in a conversation where something already brings the agent back (a follow-up still to come there, a reminder that runs it there, its long work still running there, whatever run set it: `comesBackHere`) ends `waiting` with no nudge, recorded as `waiting`, not `unkept`. A long work counts in the conversation its updates go to (`updatesThreadOf`): one asked in the main timeline talks in its own thread, so a new request in the main timeline beside it still gets its nudge. Until now this was read only after a repeated promise.

Tests: `kept-replies.test.ts` (the autonomy harness: the real engine, the fake provider), `pointless-ask.test.ts` (a follow-up set earlier keeps a repeated promise with no nudge; a new request beside long work talking in its own thread is still nudged) and a unit test on the verdict's probabilities and criteria in `web-tools.test.ts`.

## Addendum (2026-11-11): a question card asks a question

After a long status reply that ended with what was left for the people (a merge, an access), an agent posted a question card, with Responder and Pular, whose text asked nothing: it said it had nothing pending, pointed back at that list and repeated it. Nothing checked that a card asks. The judges read such a list as a need only a person can fill, so the run was told to ask (§3), the controller turned the next reply into the card whatever it said, and `ask_user` took any text the question check let through. A card now always asks, judged by its text and its choices together, in any script: a question mark (`?`, `？`, `؟`, `¿`; `hasQuestionMark`) or choices to pick from.

1. **`ask_user`** refuses text with neither, before any judgment, as a tool error (`NOT_A_QUESTION`): put it in the reply, or end the turn when the reply already says it, or ask again with one direct question.
2. **The controller's card** (§3): told to ask, a reply that asks in its text still becomes the card; one with no question mark (a need still only described, a promise repeated, "nothing pending") is posted as the answer it is, rule `not_a_question` (the verdict kept, as `ask_long` keeps it), and nobody waits on it. One that only repeats its last message word for word, with no memory change, file or receipt to show, isn't posted again.
3. **`ASK_NUDGE`**: needing nothing from the person, the run ends its turn without another word, since its reply above stands. It used to be told to give its answer again, with no question, which the controller then turned into the card.

Tests: `pointless-ask.test.ts` (the statement refused, real questions in four scripts and a choice list with no question mark asked, the controller's path ending with no card), the follow-through tests and scenarios S18, S32 and S46: a need still described or a promise repeated after the ask nudge is posted, not carded (a word-for-word repeat not at all); one asked in the text is.
