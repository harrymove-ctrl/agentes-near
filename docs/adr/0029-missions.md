# 0029. Missions: long work driven by the executor on the agent's computer

- Status: Proposed. Superseded in part by ADR 0077 (2026-10-28): the `cloud_computer` reason and missions on the agent's cloud computer. Amended 2026-10-31: §8 (the computer is named only where the workspace has more than one)
- Date: 2026-10-16
- Extends: ADR 0025 (connected computers and the runner), ADR 0015 (tools, approvals, resumable runs), ADR 0008 (agent runs)

## Context

People want to hand an agent work that takes days: "build our mobile app with Claude Code on my Mac". That work is many steps, many decisions, prototypes and PRs, and several iterations with the person. Today it doesn't fit:

- **A run is short.** At most `AGENT_MAX_TOOL_TURNS` (25 then, a backstop of 200 since the ADR 0015 addendum of 2026-10-31) model calls; a multi-hour task ends in `too_many_tool_calls`.
- **Tool calls are sequential and blocking.** `run_code` on a connected machine can run an hour (`machineMaxTimeoutSeconds`), but the run waits on it; three Claude Code sessions can't run side by side, and nothing wakes the agent when one finishes.
- **A long command is tied to the socket.** If the connection drops or the machine sleeps, the result is lost.
- **No place for decisions.** `ask_user` asks one question at a time; nothing collects provisional decisions, reviews or what was decided and why.
- **Continuity lives in the executor.** The Claude Code session (`--session-id <thread>`) is on the machine's disk; a new session, another executor or another machine starts from nothing.
- **A new message in a busy thread starts a second, unaware run** in parallel with the first.
- **Anyone who sees a thread can trigger the agent in it**, and on a connected machine that means running commands on someone's computer.

The coding agent on the machine (Claude Code, Codex) is already a strong planner and implementer with its own loop and subagents. Re-doing that intelligence in our model would cost us tokens and do it worse.

## Decision

**The executor on the machine is the brain. Our side is the interface and the guard: it shows, stores, asks for approval and delivers, mostly with code and without a model.** The executor never grants anything: approvals, reviews, access and merges stay with the server.

**A mission is the control layer of long work: what the agent plans, what is running, what waits for you, what was decided and delivered, and the controls (start, pause, stop, approve).** It always lives in a thread; the conversation stays there.

### 1. The ladder

```
conversation in a channel → thread → mission (a thread with a plan) → own channel
                              └─ long task (a thread with work running, no plan)
```

Each step is offered, never forced.

- **Thread from a conversation** ("Criar thread a partir daqui", or a suggestion when a subject runs long in a channel): one click creates the thread with the suggested range as context (a reference; messages stay in the channel), an automatic title, and opens it. Toast "Thread criada com N mensagens · Ajustar · Desfazer". The context block on top of the thread offers "Ajustar trecho" (selection in place on the channel) and "Tirar do canal" (move: messages leave the channel, a stub stays; reversible). The thread stores `context_from` (range in the source channel); the context builder uses that range instead of the fixed "before the root" window, with the thread summary when it is long. A range can only come from a channel everyone in the destination can see.
- **Long task**: one thread is the project. Each round ends in a result to react to (screens, diff, preview); the next round resumes the same executor session. A message sent while a round runs is queued into that round ("incluir nesta rodada" by default, or "depois desta"), never a parallel run.
- **Mission**: a thread with a plan (section 2), its participants (section 9), decisions, reviews and tasks.
- **Own channel**: "Mover para canal novo" when a project grows several subjects.

### 2. The plan is a living checklist kept by the executor

No fixed phases. Fixed phases fight how the executor works (it re-plans, runs items in parallel, finds work that belongs "later"), and a "phase 2 of 5" label goes stale.

- The plan is a list of items (`todo | doing | waiting_you | done | dropped`) in `mission.md`, kept by the executor through `update_plan` (section 6), never edited by hand. Every change posts one line in the thread ("Plano atualizado: + Build de desenvolvimento · − Drawer lateral"), and each version is stored on our side.
- **Reviews instead of gates:** the executor asks for a review when it has something to show (`request_review`: "Pronto para você ver: protótipos de navegação", with artifacts and PR). Approve or ask for changes; the answer resumes the session. A review is a database record like an approval.
- The plan has no authority (it is the executor's intention), so it may live in the file. Decisions and reviews do have authority and live in the database.

### 3. Who starts a mission

The agent **proposes**, the person confirms; nothing becomes a mission silently.

- Signals in a request (needs a computer, several deliverables, days of work, product decisions): a cheap judge (Jev, like the router) scores it; above a threshold the request goes to the executor in plan mode, and the thread gets a plan card: "Plano do Claude Code", title, one sentence, the first items, "No MacBook do Walter · online", **Começar** / **Mudar algo**. Nothing else on the card.
- Explicit: `/mission` in a composer, a DM with the agent, or "Nova missão" on the Threads page. A mission started anywhere gets a home thread created where it started (channel or DM).
- From a thread: "Montar plano nesta thread" (a long task that grew).

### 4. Background tasks on the machine (runner)

The runner protocol gains tasks that outlive a request:

- `task.start { taskId, executor, session, worktree, prompt }`: the runner spawns the executor detached, in the task's own git worktree and branch, writes a local task journal and streams events. `task.status`, `task.cancel`.
- The executor runs with structured output (`claude -p --output-format stream-json --verbose`, `--resume <session>`); the runner reads every event (tool use, files changed, messages, final result with time) and forwards it. This works even if the model never calls our tools.
- Executor hooks (Claude Code `--settings` with hooks calling `agentes-runner hook`) give reliable stop and subtask events.
- On exit the runner always sends `task.done { exitCode, result, seconds }`. The server records it through the outbox and **wakes the conversation** (new run, or a code path that posts the card with no model at all).
- Slots: a per-machine limit of concurrent tasks (default 3); extra tasks queue ("aguardando vaga").
- While tasks run on macOS the runner holds off sleep (`caffeinate -i`) and releases it after.

### 5. Recovery when the machine goes away

- The server already marks a machine offline when its socket closes. Running tasks become `interrupted` after a short grace; the thread gets one message ("MacBook offline desde 14:32"), not one per task.
- On reconnect, `hello` carries the runner's task journal. The server reconciles: every task that should be running and whose process is gone is resumed with `--resume <session>` and a note ("you were interrupted; check `git status` in the worktree and continue"), automatically, or after asking if the mission says so.
- Executors are told to make work-in-progress commits per step and push the task branch periodically, so a crash loses minutes and a dead disk loses little.
- A machine that doesn't come back: the mission waits ("esperando o computador") and can be moved to another machine; the new session starts from the mission files (section 7).

### 6. The `agentes` MCP server: how the executor talks to us

The runner exposes a local stdio MCP server per task (`agentes-runner mcp --task <id>`), passed to the executor (`--mcp-config`, and the equivalent for Codex). Its calls travel over the runner's existing WebSocket. Tools:

- `report(summary, status)`: the agent's message in the thread and the live card.
- `update_plan(items)`: the checklist (section 2).
- `ask_decision(question, options, recommendation, why, impact, blocking)`: a decision card. Blocking: the tool answers "recorded, stop and wait"; the answer resumes the session (`--resume <session> "Decision: …"`) with no model on our side. Non-blocking: the executor proceeds with its recommendation as a **provisional** decision, collected for review.
- `request_review(title, summary, pr, artifacts)`: a review card.
- `request_approval(action)`: merge, deploy, rollback; same approval cards as ADR 0015.
- `upload_artifact(path)`: to the Drive through `pushFile` (ADR 0025), never through a model.
- `get_context(query)`: org decisions, wiki and memory the agent may see (ADR 0017, 0023).

An `--append-system-prompt` (and a `CLAUDE.md`/`AGENTS.md` line) tells the executor to read `.agentes/` first, keep the plan with `update_plan`, report milestones, ask decisions only through `ask_decision`, ask for a review when there is something to show, and never merge directly.

### 7. Mission files in the repository

```
.agentes/
  mission.md     objective, plan (checklist), rules, origin, pending items
  decisions.md   approved decisions with the why            (server writes)
  notes.md       the executor's notes: learnings, next steps (executor writes)
```

- The **database is the source of truth** for anything with authority (decisions, reviews, participants). `decisions.md` and the non-plan parts of `mission.md` are generated from it and written by the runner on every change; local edits are overwritten on the next sync and noted quietly ("Editado no Mac — mantivemos a versão aprovada · Ver diferença").
- The plan section of `mission.md` reflects the last `update_plan`.
- `notes.md` belongs to the executor; the runner sends it back, so we keep a copy if the machine dies.
- "Origem" in `mission.md` is the summary of the thread's context range (section 1).
- Committed in the mission branches by default, so a PR shows which decision produced which change; can be git-ignored per mission.
- Any new session (another executor, another machine) starts by reading these files.

### 8. Our agent's role and context

- The agent (e.g. Dev) routes and relays: decides whether a request goes to the executor or is a short chat reply, answers non-code questions, and speaks in the thread when a person addresses it. Cards from executor tools are rendered by code; they read "via Claude Code no MacBook do Walter". *Amended 2026-10-31:* the computer is named only where the workspace has more than one (`namesComputers`); with one (always on the Cloud) they read "via Claude Code", and the same holds for the mission's chip, its plan card, its sessions, a task's end in the chat and Nova missão.
- When the agent runs, its context gets a **compact mission brief** (plan progress, running tasks, decisions taken and pending, links) instead of the whole thread; the thread summary covers the rest. Artifacts are referenced by id. A mission's context only enters runs in its own thread.
- A finished mission can become a memory summary or a wiki page ("App mobile: decisões e lições").

### 9. Who sees and who acts

**Seeing is inherited; acting is explicit.**

- **Who sees** a thread or mission: whoever can see where it lives (public channel: the org; private channel: its members; DM: its participants). Never wider than its home. Lists and search filter by it (ADR 0017).
- **Who acts** in a mission: its own participant list, independent of the channel. By default only the owner.

| Role | Can |
|---|---|
| Owner | Everything, including the computer it runs on, sharing and handing over |
| Can decide | Decide, approve reviews, ask for work, pause and stop |
| Can comment | Comment and give an opinion on decision cards ("Ana prefere tabs"); triggers nothing |
| Not a participant | Read only, when the home allows it; controls hidden; mentioning the agent in the thread starts nothing ("Pedir para participar") |

- "Compartilhar missão" adds people with a role. "Levar para #canal" changes where it lives (and who sees), not the roles.
- Work on a person's computer only starts from the owner or someone who can decide. A request from anyone else in the thread becomes a suggestion ("Ana sugeriu: dark mode · Aceitar / Recusar").
- Merge, deploy and rollback approvals follow ADR 0015 (agent owner and org admins); the mission owner is notified.
- Handing a mission over does not move the computer: the new owner points it at a machine of theirs, or the previous owner keeps lending theirs, explicitly.
- A plain thread (no plan, no work on a computer) has no owner: whoever created it or an admin can close or archive it; everyone in the channel talks as usual, within the agent's audience.
- Every change of participants, role, owner or computer, and every pause or stop, is audited.

### 10. No mission budget

A mission has no budget. What runs on a connected machine (Claude Code, Codex) uses the owner's own plan and costs us nothing, so it is not recorded as usage (ADR 0025). Our agent's own model calls in the thread (routing, replies) count against **the agent's budget**, as any run (ADR 0026). The UI shows time and progress, not money.

### 11. Threads page, closing and archiving

- A "Threads" screen (sidebar) lists the threads you can see: Todas, Com trabalho, Missões, Fechadas, Arquivadas; search and filters (channel, agent, "precisa de você", "minhas"). "Missões" in the sidebar opens the same screen on that tab. A channel header has "Threads (N)" for that channel.
- **Fechar**: resolved; collapses to one line in the channel; reopens when someone replies. **Arquivar**: hidden from lists and search by default, read only, can be unarchived. Both with undo.
- Closing or archiving with work running asks: stop now, let it finish and close after, or cancel. Closing a mission asks Concluída or Cancelada, with "salvar decisões e lições na wiki".

### 12. Data

- `threads` gains `context_from` (source channel, first and last message), `state` (`open | closed | archived`), `closed_by/at`, `archived_by/at`. Built in migration 0047; see "Threads as built" below.
- `missions` (`org_id`, agent, owner, home thread, objective, status `active | paused | done | canceled`, machine, executor, slots, timestamps). One mission per thread.
- `mission_participants` (`org_id`, mission, user, role `decide | comment`, added by, at).
- `mission_plan_versions` (`org_id`, mission, items JSON, by the executor, at).
- `mission_tasks` (`org_id`, mission or thread, title, executor, session id, worktree, branch, status `queued | running | waiting | interrupted | done | failed | canceled`, exit code, seconds, last line).
- `mission_decisions` (`org_id`, mission, question, options, recommendation, why, impact, blocking, status `pending | provisional | taken`, chosen, by whom, when).
- `mission_reviews` (`org_id`, mission, title, summary, PR, artifacts, status `pending | approved | changes_requested`, by whom, when).
- `mission_events` (append-only feed: reports, plan changes, task events, wake-ups) driving the thread, the pinned card and the Threads page in real time.

### Threads as built (sections 1, 9, 11, 12)

- **Threads stay implicit.** Replies keep `messages.thread_id` = the root message id. The new `threads` table (migration 0047) has one row per thread that has state of its own (title, `open | closed | archived`, a context range), keyed by `(org_id, root_message_id)`; an implicit thread gets its row the first time it is closed, archived or renamed. `context_from` became columns: `context_channel_id`, `context_first_message_id`, `context_last_message_id` (plus their exact times), `context_excluded_message_ids`, `context_moved` and `context_moved_message_ids` (exactly what moved, so returning never touches real replies).
- **The root of a thread made from a range is a new message.** No message of the range can be the root (the range can change, can come from another channel, and its first message may already have replies). `createThreadFromRange` writes a top-level message in the thread's channel, by the person who created it, with the title as its text and `meta.threadStart` (`title`, `contextChannelId`, `firstMessageId`, `lastMessageId`, `count`, `moved`, `movedCount`). It is written directly, without the outbox: it routes to no agent. The web draws it as the context marker and, after "Tirar do canal", as the stub. The automatic title is the first message of the range on one line (≤ 60 chars).
- **Moving** sets the range's messages' `thread_id` to the root (only for a range of the thread's own channel; a message with replies of its own can't move: `thread.range_has_replies`). Returning sets it back for exactly the moved ids. Adjusting a moved range returns it and moves the new one. Undo of creation (`DELETE`) works while nobody replied.
- **Another channel's range** is accepted when it is public or every member of the destination (people and agents) is a member of it; otherwise `thread.context_not_visible` with `params.userIds` and `params.agentIds`.
- **Who manages a plain thread:** who created it, the root message's author, and admins (`thread.not_allowed` otherwise).
- **Close and archive.** A person's reply in a closed thread reopens it inside the message insert statement (one conditional update by root id). Posting by a person in an archived thread is refused with `thread.archived` (409); an agent's run already going still posts its reply. Unarchiving returns to closed or open.
- **Who sees** a thread in lists: the people who read its channel. In this codebase reading a channel needs membership (public channels too, like search for people), so the Threads page lists threads of the channels and DMs the person is in.
- **Context:** a run in a thread with a range reads the range (minus exclusions, oldest first) instead of the channel before the root; moved messages are read once, as replies. A range longer than the window loses its oldest messages (the thread summary covers the thread, not the range), and the prompt says the thread came from that part of the conversation.
- **Not yet:** per-thread unread counts (reads are per channel) and the close-with-work-running choices (the web asks; the server closes). The "Missões" tab is `tab=missions` (see "Missions as built").

### Background tasks as built (sections 1, 4 and 5)

- **Runner:** protocol 4, detached tasks under a small wrapper, a journal, `task.done` until acknowledged, Claude Code with `stream-json`, optional worktree per branch, slots, `caffeinate`: ADR 0025 section 5a.
- **`machine_tasks`** (migration 0048): `org_id`, agent, machine, channel, `thread_root_id` (null: a flat DM), the run that started it and the person behind it (`requested_by_user_id`), title, executor, command, prompt (kept to resume), `session_id` (the thread id for Claude Code), branch, folder, status `queued | running | interrupted | done | failed | canceled`, exit code, signal, seconds, last line, files (≤ 50), result (≤ 8000 chars), `canceled_by`, the resume chain (`resumed_from_id`, `resumed_task_id`, `resume_count`), `woke_at`, times. `interrupted` with `ended_at` null means "the machine went away; it may come back"; with `ended_at`, final. `machines.resume_tasks` (default true) turns auto-resume off per machine. Not `mission_tasks` yet: missions will point at these rows.
- **Agent tools** (`sandbox:run`, only on a connected machine with commands allowed and protocol 4): `start_task(title, prompt | command, executor?, branch?)` answers at once with the id and "you'll be woken; don't poll"; `list_tasks`, `task_status`, `cancel_task`. Claude Code is the default executor when there is a prompt, in the conversation's session. `run_code` tells the agent to use `start_task` with Claude Code for anything longer than a couple of minutes. Audited: `machine.task_started`, `machine.task_canceled`.
- **Frames → rows.** The replica holding the socket persists `task.event` (last line, files, seconds; an event also flips an offline-interrupted task back to running) and `task.done`, then sends `task.ack` (not on failure: the runner sends it again later). Every change publishes `machine.task` (ADR 0010).
- **Waking the conversation.** A task's end (done, failed, canceled by a person, or interrupted for good) enqueues `machine.task_done` in the same transaction. The job posts one notice in the task's thread, written as the agent with no run (`meta.machineTask` with the result, `bodyCode` `machine_task_<status>`), and starts a run of that agent on it (trigger `mention`, hop = the starting run's hop + 1) when the hop limit and the agent's audience for the task's person allow and the agent is still in the channel. If the agent already has a run in that thread, the notice joins it as a new message. The model reads the notice as news: `[Background task <id>]: …` with branch, files and the final output marked as data. A task the agent canceled itself wakes nobody. Budget: the woken run is an ordinary run of the agent (ADR 0026); the task itself costs us nothing.
- **Offline.** When a machine's socket closes, `machine.tasks_offline` is enqueued for 60 s later (`TASK_OFFLINE_GRACE_MS`). Still offline then: its running tasks become `interrupted` (not final) and each affected thread gets one notice (`bodyCode` `machine_offline`: computer, since, count). A replica that dies without closing its sockets schedules nothing; those tasks stay `running` until the runner reconnects and the journal says what happened.
- **Reconnect.** On `hello` the server compares its open tasks with the journal: running there → running here; ended there → its `task.done` follows; missing there, or `task.done { interrupted }` → final `interrupted`. A Claude Code task with a session, on a machine with `resume_tasks`, at most 3 resumes in a row, starts again right away as a new task (`claude -p --resume <session>` with "You were interrupted (the computer went offline). Check git status in your folder and continue where you stopped.") and the thread gets "resumed" (`machine_task_resumed`). Anything else wakes the agent with the interruption so it tells the people.
- **Mid-round queueing** (section 1) is how runs already worked: a person's message in a conversation where the agent has an active run (queued, running or waiting) joins that run inside the message insert statement (`agent_runs.pending_message_ids`, `meta.steeredRunIds`) and is read at the next model call as "New message from … while you were working"; a plain "stop" cancels the run instead. One that arrives after the run's last check gets a run of its own when the run is done, and now also when it fails. A person writing to the agent while its task runs gets an ordinary run (the agent can queue a follow-up task).
- **Join or stop and send (2026-10-20).** While an agent works, the composer offers "join" (the default above: read at the next step) or "stop and send" (`steer: "now"` on the post): the run's current model call is aborted (cross-instance via `system:run-interrupt`, a per-process map of the turn's `AbortController` in `cancel.ts`), its text so far stays in the transcript as narration and the loop reads the message at once; a running tool finishes first, waiting runs and computer brains read it at their next step. Read receipts: the engine publishes `agent.run.read` once messages are in the conversation, and the active-runs lists carry `pendingMessageIds` for reloads. The stop judge no longer delays the post: `agent.run.steered` goes out at once and a `stop` follows after the judgment. A person's stop can be continued (`POST …/runs/{id}/continue`): a new run whose trigger is the stopped reply picks up the transcript.
- **Receipts are marks, never lines (2026-10-30).** What became of a message sent into a run (waiting for the next pause, stopped to read, handed over, held by an approval, read) shows where the message's receipt check goes, at the end of its first line (the name's line, or a grouped message's first text line, which wraps before it), never as a line under it, so a receipt never changes a message's height or the room before the next one: the reader's face once read, else the phase's small mark, in place of the check. Its words are the mark's label, said to screen readers as they change, and a line of its popover, under the agents. While the author's own plan picks who answers, the mark is the clock, and "Call an agent" is in its popover: the state lasts as long as the plan's call, so a line would come and go. "Seen" in a DM between people is the reader's face in the same place, on the newest message they read: a button whose popover says who read it, in a slot each of the author's messages there keeps, so the face moving on never rewraps a line. Only a receipt that asks something of the person (send it again, connect an AI, nobody will answer) keeps a line of words under the message. The phone keeps the same rule: the mark stands in the room beside the person's own bubble, on its last line, or at the end of the name line of someone else's turn, and a tap says its words.
- **Not yet:** executor hooks (`--settings` with `agentes-runner hook`), tasks queued while slots are full ("aguardando vaga": today `task.no_slot`), "incluir nesta rodada" vs "depois desta" (a message always joins the active run), and Codex beyond what "Codex" below describes. (The `agentes` MCP server and `GET …/threads/{id}/tasks` came with missions.) Windows: the wrapper, `taskkill` and the `cancel` file are written for it, but only Linux and macOS are tested in CI.

### Missions as built (sections 2, 3, 6 to 12)

- **Data** (migration 0049): `missions` (home `thread_root_id`, unique per org; agent, owner, machine and `machine_lent_by`, executor, title, goal, status `proposed | active | paused | done | canceled`, `main_session_id`, `repo_dir` relative to the agent's folder, `resume_tasks`, denormalized plan counts, `inbox`, `files_dirty_at`, close fields, `wiki_page_id`), `mission_participants` (`decide | comment`), `mission_plan_versions`, `mission_decisions`, `mission_reviews`, `mission_files`, `mission_events` (append-only). `machine_tasks.mission_id` replaces the planned `mission_tasks`. `approvals.run_id` became nullable, with `mission_id` and `mission_task_id`. No money fields anywhere.
- **Main session.** Each mission has one executor session (`main_session_id`, a UUID) on its machine, in `repo_dir`. It planned the mission, hears what people send and splits the work: per-item sessions are new machine tasks on their own branch (own worktree, new session id) started by the main session's `start_task` MCP tool. Talking to any session = a machine task that resumes it (`claude -p --resume <session>`) in that session's folder with the text as prompt. A session whose task still runs, a paused mission, an offline or full computer: the text waits in `missions.inbox` and goes out when that session's task ends, the mission resumes or the computer reconnects (`hello`). That is also how `send_to_mission` queues while the main session works.
- **Proposal.** The agent's `propose_mission(title, goal, folder?)` (scope `sandbox:run`, only when its computer allows commands and runs protocol 5) or `POST …/missions` (`/mission`; the caller must be able to talk to the agent) creates the mission `proposed` (owner = the person who asked), the thread's `threads` row (titled), starts the main session in plan mode (a prompt: explore read only, `update_plan` with the first items, `report` the goal, end the turn; Claude Code runs with its usual permissions, plan mode is the prompt's) and posts the plan card (`meta.missionPlan`). In a flat DM the home thread is made from the message that asked. Start is the owner's only (`mission.not_owner`): `active`, and the main session is resumed with "proceed" (queued while the planning turn still runs).
- **Who acts** is checked in the message insert itself (still one statement): in an open mission's thread, a person who is neither the owner nor `decide` addressing the mission's agent starts no run, joins no active run and answers no question of it; the message gets `meta.missionSuggestion { status: pending, missionId }`. `message.posted` skips such messages, and the router skips the thread for them. The owner or a decider accepts (forwarded to the main session as "Suggestion from X, accepted by Y: …") or declines. Decision opinions are open to `comment` participants; choosing is the owner's and deciders'. Close is the owner's or an admin's; participants and hand-over too. Merge/deploy/rollback stay ADR 0015 approvals (agent owner and admins); the mission owner gets `mission.approval_requested`.
- **Hand-over** keeps the computer: the new owner's own machine, or `lendMachine` (the previous lender keeps lending), otherwise the mission pauses and the response says `code: mission.needs_computer`; the new owner then `PUT …/machine` with a computer they paired (a new main session, which starts from `.agentes/`). The previous owner stays as a decider.
- **Commands** (the web composer calls the API; nothing is posted): `/stop` → `POST …/stop` (cancels the mission's running tasks, pauses), `/pause` and resume (pause refuses the executor's `start_task` with `mission.paused`; running tasks go on), `/summary` → `GET …/summary` (text from the database, no model), `/plan` → `GET …/plan` (latest version and history).
- **`agentes` MCP tools** (protocol 5, ADR 0025 §5b), bound to the calling task and its mission: `report` (an agent message in the thread, `meta.missionReport`, and the task's last line), `update_plan` (versioned; from the second version on one line per change, `meta.missionPlanChange { added, removed, changed }`), `ask_decision` (card `meta.missionDecision`; blocking: "Recorded. Stop now and wait…"; else provisional with the recommendation), `request_review` (files uploaded to the Drive first; card `meta.missionReview`), `request_approval` (ADR 0015 card `meta.approvalId`; the decision resumes the task's session through the job `mission.approval_decided`), `upload_artifact`, `get_context` (search over what the agent may see), `start_task` (main session only). Every call is audited (`mission.tool_*`). A decision taken, a review answered or an approval decided resumes the asking session: `Decision: <question> → <chosen> (by <name>)`, `Review approved: …`, `Changes requested on "…" (by …): <note>`, `Approval for …: approved by …`.
- **A mission task's end** wakes no agent run (the executor reports through the tools): a failure or a final interruption posts the task notice; then `.agentes/notes.md` is read back into `mission_files`, an item's end is told to the main session (with its final output) and the inbox is delivered. Interrupted mission tasks resume in their own folder when the mission is open and `resume_tasks` is on.
- **Files.** Every change (plan, decisions, participants, status) marks the files dirty and schedules `mission.sync_files` (debounced 2 s). It writes `<repo_dir>/.agentes/mission.md` (goal, checklist of the latest plan, rules, people, origin, what waits for people) and `decisions.md` (taken, then provisional) through the runner's `write`; before each write it reads the file there and, if it differs from what we last wrote, records `file_edited_on_machine` (both versions, a small diff) and writes ours again. Offline: written on reconnect.
- **Context.** A run in a mission's thread gets a compact brief (plan counts, items in progress and waiting, running tasks, pending decisions and reviews, who can ask for work, commands, "pass requests on with `send_to_mission`"). The mission is found by the same read as the thread's range, so threads without a mission pay nothing.
- **Threads list.** `ThreadInfo.mission` (`{ id, status, planDone, planTotal, waitingYou }`) from one join, and the tab `missions`; `GET …/missions` lists missions with counts for the Missões tab.
- **Close** cancels running tasks; `saveToWiki` makes the page "<title>: decisions and lessons" from the decisions and the last notes.
- **Gaps closed** (migration 0050): **"Ver saída"** is `GET …/tasks/{taskId}/output?tail=N` for whoever reads the task's conversation: online (runner protocol 6) the computer answers its log's human lines (`task.output`, ADR 0025 §5c); otherwise the last ≤ 50 lines kept from `task.event` (`machine_tasks.recent_lines`, throttled like the events; the same line twice in a row once). The web appends `lastLine` from `machine.task` events while it runs. **Pull requests:** `machine_tasks.pr_url` (first one wins) from the runner's `prUrl`, a GitHub/GitLab URL in a line, the final result, or the executor's `report`/`request_review` `pr_url`; in the task DTO as `prUrl`. **Requests to join** (`mission_join_requests`, one pending per person): `POST …/missions/{id}/join-requests` by someone who sees it and takes no part (nothing posted; owner and deciders get `mission.needs_you { kind: join_request }`), `GET` (all for those who can answer, else one's own), `…/{userId}/accept { role }` (adds the participant) or `/decline` by the owner or deciders; the asker gets `mission.join_answered`. Adding someone by hand answers their request. The view has `pending.joinRequests` and `joinRequested`. **Plan in the view:** `plan.doing` and `plan.items` (`{ id, title, status }`, ≤ 40, in order) from the latest version (one `distinct on` for the whole list). **Who can run one:** `GET …/missions/eligible-agents` (connected computer, commands on, protocol ≥ 5, the caller in the audience; offline computers listed with `online: false`). **List:** `status` (also `waiting_you`), `channelId`, `agentId`, `q` (title or goal), and `counts { active, waitingYou, closed }` with the same filters in one query; "waiting for you" = you own it or decide, and a decision (pending or provisional), review, plan item, suggestion or request to join waits.
- **Not yet:** the Jev judge that offers a mission by itself (the agent decides to call `propose_mission`), per-mission slots, the daily digest, `.agentes/` committed or git-ignored per mission (we only write the files), and Codex beyond what "Codex" below describes.

### Executor agent and the fix round (migration 0051)

- **`executor: "agent"`.** Besides Claude Code and Codex, a mission can be programmed by our agent itself, with its own tools on the connected computer (no CLI there). `missions.executor` is text validated in code (`claude | codex | agent`); `POST …/missions` and `propose_mission` take `executor?`; the default is Claude Code when the computer has it, else the agent. Agent mode needs only a connected computer with commands on and runner protocol 4 (not 5). `GET …/missions/eligible-agents` lists protocol 4+ computers with `executors`, `defaultExecutor` and `codexTooOld`; the mission view's `machine.executors` feeds the plan card's "Quem programa" switch (`PUT …/missions/{id}/executor`, the owner's, before Start: the planning stops and starts again with a new main session).
- **Which CLIs exist.** Runner protocol 7: `hello.executors` (`claude`, `codex` on the runner's PATH, the first line of `--version`, cached 10 min) → `machines.executors` (with `detectedAt`). A runner that doesn't say is treated as before (Claude Code assumed). Codex counts only from `CODEX_MIN_VERSION` (0.163.0, the release verified on a real machine).
- **The main session is the agent's own runs in the home thread.** Whatever would resume the executor's main session (people's messages, `/mission` Start, accepted suggestions, decisions, reviews, approval outcomes, the inbox) posts an agent-facing notice in the thread (`meta.missionInbox { missionId, from, text, requestedBy, kind }`, `bodyCode: mission_inbox`; the model reads it as `[Mission, from …]: …`) and starts a run of the agent on it, or joins the run already working in that exact thread (pending messages). Paused, closed or without a computer: the text stays in `missions.inbox` and goes out on resume or reconnect. Proposing in agent mode starts no machine task: the agent is woken with a read-only plan prompt and writes the plan with `update_plan`.
- **The agent's mission tools** (scope `sandbox:run`, only in its open mission's thread with executor `agent` and `mission.agentId` = the run's agent): `update_plan`, `report`, `ask_decision`, `request_review` (files go to the Drive first with `upload_file`; the review takes their artifact ids), `request_approval` (sensitive: an ADR 0015 approval of the run, tagged `approvals.mission_id`, so the normal resumable approval works; the owner gets `mission.approval_requested`). Each call needs the person behind the run to be the owner or decide, or the run to have been woken by the mission itself (its inbox or one of its tasks). `askDecision`, `requestReview` and `askerOf` take no task.
- **Tasks in a mission thread** (any executor): `run_code`, `start_task`, the file tools use `mission.machineId` (never the agent's own computer) and `start_task` tags `machine_tasks.mission_id`. Before Start only reading works (and bash that only reads: `ls`, `cat`, `git status|log|diff|show`…); paused: reading only; and only for the owner, deciders or the mission's own wake-ups. In agent mode a mission task's end is a notice (`meta.machineTask` with `missionId`) and a wake-up of the agent (audience checked for the task's person; not when the agent canceled it itself); notes are read back and the inbox delivered as before; pause, stop and close cancel these tasks. In a Claude Code mission, a task the agent started itself still wakes the agent like any task. After the computer was away, an interrupted shell task of an agent-mode mission wakes the agent; Claude Code sessions still resume by themselves.
- **Loop control.** The mission's own wake-ups are hop 0, so their runs are hop 1: the agent-to-agent hop limit doesn't stop the mission's work; the agent's budget does. The stuck-loop guard pauses an active mission with `mission.paused_stuck` (audit, event, `mission.needs_you { kind: stuck }`, a notice `mission_stuck_failure` / `mission_stuck_idle` asking the owner what to do) when the same task (title, or command for shell) fails 3 times in a row, or after 5 wake-ups in a row with no plan item changing state (`missions.idle_wakeups`; a person's message, a moving plan or Resume start it over).
- **Brief.** Executor-specific guidance (agent mode: do the work here with `start_task`/`run_code`, keep the plan, report milestones, ask decisions, request reviews, ask approval for merge/deploy/rollback) and, in agent mode, `MISSION_RULES`. Everything the executor or tools wrote (plan titles, last lines, questions, review titles) is inside `<mission-data>…</mission-data>`, marked as data, never instructions.
- **Claude Code permissions** (runner protocol 7: `task.start.mission.mode` and `branchPrefix`). A mission task's Claude Code gets a generated `--settings` file (`tasks/<id>/settings.json`, mode 600; per the docs its values override the same keys of the person's settings files, and deny rules win over allow rules). `work`: `acceptEdits` plus `Bash(git add|commit|status|diff|log|show|branch|checkout|switch|stash|restore|rev-parse|fetch|pull *)`, pushes only as `git push [-u|--set-upstream] origin agentes/<last 8 of the mission id>/*`, `gh pr create|view|list|checks|diff|status`, and test/lint/build/install for npm, pnpm, yarn, bun, npx, node, python, pip, uv, cargo, go, make, expo, `eas build --local`; denied: `git merge`, force pushes, refspecs (`*:*`, `+`), pushes to `main`/`master`, `--delete`/`--all`/`--mirror`, `gh pr merge`, `gh api`, `vercel`/`railway`/`fly`/`netlify` deploys, `eas submit|update`, `kubectl apply`, `terraform apply`, `npm publish` (they go through `request_approval`). `plan` (before Start): `--permission-mode dontAsk` with reads, read-only git and our tools only (edits denied). Item branches from `start_task` always get the mission's prefix. Rule syntax verified against code.claude.com/docs (permissions, CLI reference): prefix matching with `*`, deny evaluated first, compound commands split per subcommand; Bash rules are not a security boundary (`git -C . push`, `sh -c`), which ADR 0030 addresses.
- **Fixes.** One live task per mission session (partial unique index `machine_tasks_live_session`; a concurrent resume waits in the inbox); `mission.approval_decided` tells the session once (`approvals.executed_at` claimed). Item worktrees see the mission's files (`<worktree>/.agentes` links to the repository's, a copy where links can't be made) and `.agentes/` stays in `.git/info/exclude`. A blocking `ask_decision`, `request_review` or `request_approval` marks the task (`machine_tasks.waiting_for`), and its end is told to the main session as "waiting for …", not done. Absolute paths in `upload_artifact`/`request_review` are resolved on the runner (inside the task's folder: relative; elsewhere in the agent's folder: `@folder/…`; outside: refused). Session resume looks for `projects/*/<id>.jsonl` under `CLAUDE_CONFIG_DIR` or `~/.claude`, and a start refused at once ("already in use", "No conversation found") is retried once with the other flag. The systemd unit gets the install-time `PATH`.
- **Security fixes.** `list_tasks`, `task_status` and `cancel_task` see only the conversation's channel, and a mission's tasks only in its thread; `cancel_task` of a mission task needs the owner or a decider, and a mission task canceled by the agent still gets its end handled. Granting `decide`, handing over and talking to a session need the agent to answer that person; lending the computer is the pairer's or current lender's; `sendMissionMessage` is audited (`mission.message_sent`). Another agent's mention can't make the mission's agent work for someone who isn't owner or decide. While a mission is open only its owner and admins close, archive, move or re-range its thread; a mission made in someone else's thread adds that thread's author as `decide`. The runner masks the agent's secrets in MCP arguments and the server masks anything that looks like a key before writing cards or approvals. A context range from another channel is re-checked at run time (cached 30 s) and dropped when not everyone in the thread can see it any more. Mission tools are rate limited per task (or per agent in agent mode): `report` 30/h, `update_plan` 60/h, `ask_decision` 10/h, `request_review` 10/h, `request_approval` 5/h, `upload_artifact` 30/h, `start_task` 30/h (`mission.rate_limited`). Re-ranging a moved thread checks the new range for messages with replies first. A plain reply by someone who takes no part in an open mission's thread becomes a suggestion card too.
- **Known risk until ADR 0030.** The MCP token of a task is in its folder (`tasks/<id>/mcp-token`, mode 600) and in the executor's environment: any process of the same OS user on that machine can read it and call the mission's tools while the task runs (bounded by the rate limits and the mission's state).

### Codex (experimental)

Verified with codex-cli 0.163.0 on a real machine (two turns captured) and against the Codex source (`codex-rs/exec`):

- **Command.** First turn: `codex exec --json --skip-git-repo-check -C <cwd> --sandbox workspace-write -c sandbox_workspace_write.network_access=true <MCP -c …> [-c developer_instructions=<rules as a TOML string>] -o <task dir>/last.txt -`, the prompt on stdin. Next turns: the same global options (same `-C`), then `resume <thread_id> -` (options before `resume`; always by id, never `--last`; per-turn context goes in the prompt, `developer_instructions` stay from the first turn). A mission's plan turn uses `--sandbox read-only`. `--full-auto` no longer exists: `exec` forces `approval_policy=never`, so anything outside the sandbox is rejected and workspace-write with network is the unattended setting. We never pass Codex's own `--worktree` (we keep ours) nor `-p` (it is `--profile`).
- **Session.** Codex picks its thread id (`thread.started`). The runner keeps our session id → that thread in its journal (`codexThreads`) and resumes by it; the server keeps our session ids as for Claude Code. A runner that lost its journal starts a new thread, which reads `.agentes/`.
- **Events** (`--json`, JSONL): `thread.started { thread_id }`, `turn.started`, `turn.completed { usage }`, `turn.failed { error.message }`, `error { message }`, `item.started|updated|completed { item: { id, type, … } }` with `agent_message { text }` (a human line and, last one wins, the result; only when completed; several per turn), `reasoning` (skipped), `command_execution { command, aggregated_output, exit_code, status }` ("Running: …" with the login-shell wrapper removed, a failure line, a pull request URL from its output), `file_change { changes: [{ path, kind }] }` (files), `mcp_tool_call`, `todo_list`, `error`. `-o last.txt` is the result when the stream had none. Stderr is never a failure by itself (the person's own MCP servers from `~/.codex/config.toml` start too and a failing one only logs there): exit code and `turn.failed`/`error` decide.
- **MCP.** `-c mcp_servers.agenteschat_agentes.command=…`, `.args=[…, "mcp", "--task", <id>]`, `.env_vars=["AGENTES_MCP_TOKEN","AGENTES_MCP_SOCKET","AGENTES_RUNNER_HOME"]` (names only: the values are in the task's environment), `.default_tools_approval_mode="approve"` (without it, under `approval_policy=never`, every tool without `readOnlyHint` is denied as "requires approval"), `.startup_timeout_sec=60`, `.tool_timeout_sec=300`, `.required=true`. A unique server name, so one of the same name in the person's config isn't merged. `get_context` carries `readOnlyHint`.
- **Version.** `hello.executors.codex.version` (`codex-cli X.Y.Z`); missions offer Codex only from `CODEX_MIN_VERSION` = 0.163.0 (the verified release); an older one shows "Codex (experimental)" with "update it there". The UI always labels it experimental.
- **Auth.** We don't touch keys now: `CODEX_API_KEY` in the runner's environment takes precedence over the person's ChatGPT login in `exec`. *Amended 2026-10-31 (ADR 0041 §5.1):* a task of an agent with its own account signs in with that account's folder alone, as its turns: no key in the runner's environment reaches it.
- **Risks.** No token streaming in `exec` (only completed messages, so the live line moves per item); network is on for every command when the work needs to push or install; the sandbox is Codex's own, not ours (ADR 0030); untested on Windows (quoting of `-c` values).

### Command approval policy (migration 0052)

- **Plain reads need no card.** A deterministic check (no model; `@agenteschat/adapters/command-policy`, `readOnlyCall`) lets the runner's prompt tool allow at once, with nothing posted: `ls`/`cat`/`head`/`tail`/`find` (no `-delete`/`-exec`)/`stat`/`file`/`wc`/`du`/`df`/`which`/`uname`/`sw_vers`/`system_profiler`/`fc-list`/`mdls`/`sips -g`/`identify`/`exiftool` reads anywhere except secrets (`~/.ssh`, `.env`, keys, the runner home), read-only git in any repository, and `curl`/`wget` GET or HEAD that save only into the mission folder. Every part of a pipeline must pass: `| sh`, `xargs`, `$(…)` and redirections outside the folder never do. The runner gets the task folder and the mission folder through `AGENTES_MCP_CWD` / `AGENTES_MCP_FOLDERS` and sends them with each prompt (`scope`).
- **Per mission: Autonomia** (`missions.command_approval`; shown as "Pergunta sempre" / "Só o que é arriscado" / "Não pergunta"): `always` (every command off the allow list gets a card), `low_risk_auto` (default for new missions; missions made before 0052 stay `always`) or `never` (everything but the deny list). The owner or a decider changes it (Nova missão, the plan card, "Configurações da missão"); audited as `mission.command_approval`. New missions start with the agent's default (`agents.mission_command_approval`, migration 0055, null = `low_risk_auto`), set with "Usar como padrão" by the agent's owner or an admin (`PUT …/agents/{id}/mission-command-approval`, audited `agent.mission_command_approval`); asking for one at creation wins.
- **"Configurações da missão"** (`GET …/missions/{id}/settings`): the rules in force with who and when, the command counts (`command_auto` = allowed automatically, `command_prompt` = asked, a card answered Recusar plus the commands a task was refused = blocked) and the agent's default with whether the caller may change it. A rule is taken back with `DELETE …/missions/{id}/command-rules/{ruleId}` (owner or deciders; the rule's id is its `command_rule` event; a `command_rule_removed` event names it, audited `mission.command_rule_removed`): the command asks again, and the next task's `allow` list drops it. "Retomar sozinho quando ele voltar" is `PATCH …/missions/{id}` with `resumeTasks` (owner or deciders, audited `mission.resume_tasks`).
- **Order for a prompt:** deny list (refused, never judged, never shown) → plain reads (allowed silently) → the mission's "Aprovar sempre" rules → the policy. `never`: allowed. `low_risk_auto`: code first (`forbiddenReason`: sudo, deletes or writes outside the mission folder and `/tmp`, chmod/chown outside it, launchctl/systemctl, uploads, ssh/scp/rsync to hosts, global installs, anything with `$(…)` or `| sh`); if code allows it, the shared judge (Jev, cheap model as fallback, usage recorded like other judge calls) answers "is running this command low risk and needed for the work?" with the command, the tool, the goal and the current plan item. At `LOW_RISK_THRESHOLD` (0.85) or more it runs; below, on an error or after 8 s, it is the card (fail closed).
- **Every automatic approval** posts one quiet line in the thread ("Aprovado automaticamente: `cmd` · baixo risco"; several within a minute fold into one line) with **Revogar**, which sets the mission back to `always`; `mission_events` `command_auto` and an audit entry keep the record.
- **A deliberate exception to "the judge never grants a permission".** Here the owner grants the policy for the mission; the judge only classifies commands inside what code already allows. The deny list and the code rules stay hard: no judge answer can run a merge, a deploy, a publish, sudo or a write outside the mission folder.

### Delivery and awaiting_close (migration 0054)

- **Status `awaiting_close`.** An active mission whose latest plan has items, all `done` or `dropped` (at least one done), with no task of it queued or running, no blocking decision, no pending review or command card and (agent mode) no run of its agent going in the home thread, waits for its owner to conclude it. It counts as open everywhere (lists, the Missões tab, tools, the brief) and as waiting for the owner and deciders (`waitingYouSql`, the thread row's `waitingYou` +1). Pause, stop and close work from it. New work sets it back to `active` (`reactivateMission`, event `reactivated`, `mission.updated change: status`): a message from the owner or a decider in the home thread (the `message.posted` job), any text to a session that comes from a person (`tellSession`/`wakeMissionAgent` with `requestedBy` or `kind: person`), a plan version with something left to do, `start_task`. The mission's own notices (an item's end) reach the session without reopening it.
- **The check** (`checkMissionDone`, idempotent): job `mission.check_done` 30 s after a plan version that finishes the plan and after Resume (agent mode: also after a task's end, and it looks again up to 10 times while the agent's run still goes, so the agent can deliver itself); inline after a Claude Code/Codex task's end. With a pending delivery it only sets the status; otherwise it posts the automatic card.
- **`mission_deliveries`** (`auto`, `summary`, `artifact_ids`, `paths`, `checklist [{id, text}]` with ids `c1…`, `checks` user id → item ids, `status pending | accepted | changes_requested | superseded`, `note`, `save_to_wiki`, `decided_by/at`). The card is the agent's message `meta.missionDelivery { missionId, id }` (`bodyCode: mission_delivery`, or `mission_all_done` for the automatic one); a new delivery supersedes pending ones. The owner and deciders get `mission.needs_you { kind: delivery }`.
- **`complete_mission(summary, checklist?, paths?)`** (executor MCP, main session only, 5/h; files uploaded like `request_review`) and the agent-mode tool with `artifact_ids`: the delivery, status `awaiting_close`, audit `mission.tool_complete_mission`, answer "Delivered. Stop now and wait for the person to check it." `MISSION_RULES` (both variants, also in the agent brief): when every plan item is done, call `complete_mission` and don't keep working; plan items never carry tool names.
- **API.** `GET …/missions/{id}/deliveries` (array, newest first, who reads the conversation); owner or deciders: `PUT …/deliveries/{id}/checks/{itemId} { checked }` (their own check), `POST …/deliveries/{id}/accept { saveToWiki? }` (`concludeMission` as done, so a decider can conclude; lessons page as on close), `POST …/deliveries/{id}/changes { note }` (active again; `Changes requested on the delivery (by <name>): <note>` to the main session or the agent). `pending.deliveries` in the view. Answering twice is `mission.delivery_decided`.
- **Plan titles** lose known tool names server side (`stripToolNames`: snake_case names anywhere, one-word names like `report` only as code, with "via/with/using/call/com/usando/pelo…" and a wrapping "(…)"); a title left empty keeps its text without backticks.
- **Command cards** also notify the owner and deciders (`mission.needs_you { kind: command, promptId }`) when opened and answered. `POST …/commands/retry` takes `commands[]` (up to 20 blocked commands of one task, one resume) besides `command`, and refuses with `mission.paused` while paused.
- **Runner finding.** Claude Code leaves its `--permission-prompt-tool` out of the init event's tool list; the tool is advertised and called (a test pins the name). The denials seen on a real item task were the cards-per-task cap, now 30 per task in 10 minutes (was 10).
- **Items use the mission folder** (approved by the person). An item running in its own worktree or `work/<item>/` gets `--add-dir <absolute mission folder>` and `Read|Edit|Write(//<mission folder>/**)` in its settings (plan turns: `Read` only), so it reads and writes `.agentes/` and shared inputs there. Nothing outside that folder changes: other paths still go through the prompt tool and the policy; the deny list is the same. The main session (which runs in the mission folder) gets nothing extra. Codex items: not yet.
- **Reconnects never refuse a call.** While the runner reconnects (an update, a dropped socket) the MCP bridge keeps a new call waiting for the connection (bounded by its own timeout) instead of answering "not connected"; a `permission_prompt` or `get_context` in flight when the link drops is sent again on the next connection (others fail as transient: the server may have done them). The prompt tool keeps asking through transient errors (the runner restarting, the local socket gone) until its 30-minute wait, never a silent deny.

- **Working indicator.** `PixelSpinner` (a 3×3 pixel orbit with a fading trail, the agent's `bodyTones` or the text's ink, still under reduced motion, one shared clock); `Icon name="spinner"`, `Spinner` and `Chip` (`lead`) render it everywhere; `AgentSpinner` in the web picks the agent's color.
- **Aprovações** lists the missions' pending command cards (mission, agent, who programs where; Aprovar / Recusar / Aprovar sempre as in the thread; counted in Pendentes) and "Esperando você em missões" (pending decisions and reviews linking to their cards: threads take `?m=`).
- **The mission header is the thread header.** For a thread with a mission: back, the agent, the title once, the state, the executor mark and computer, "Missão · DM com Theo" / "Missão · #canal" (plain threads say "DM com <nome>" / "#canal", never "thread numa mensagem direta"), people, Arquivos, ⋯ (actions only, each with one line: Pausar / Retomar, Parar agora, Compartilhar, Fechar missão; then "Configurações da missão…" with the current autonomy); a second row with the plan strip, what runs (the agent's orbit; nothing when nothing runs, no pause icon), what waits for you, the elapsed time and "N sessões ›". Reading back through the conversation folds it into one row (title, state, strip). It is the column's header: the floating pinned card is gone.
- **Sessions dialog.** "N sessões" opens the sessions in the details dialog: Todas / Rodando / Concluídas / Falharam with counts; a session opens "O que mudou" and "Ver saída" (live) in place.
- **Delivery card.** `meta.missionDelivery`: like an approval — the summary, the delivered files (Drive thumbnails), "O que conferir" checked by each person, "Concluir missão" (with "Salvar decisões e lições na wiki") and "Pedir ajustes" (an inline note) for the owner and deciders; the automatic "Tudo pronto" card is the same, smaller; a superseded one is one quiet line. `awaiting_close` reads "Esperando você concluir" for whoever concludes it and "Pronta para concluir" for the others.
- **Blocked commands.** A task's refused commands are one line ("4 comandos bloqueados · Ver"); the details dialog groups them by first word, cuts each to two lines, and allows the picked ones in one call ("Liberar selecionados e continuar", `commands[]`); the line then says "N comandos liberados · retomando a sessão" with the orbit, and a paused or closed mission says why first.
- **Plan-change line.** The icon sits on the text's first line (the shared `mi-evt` line), "Ver plano" flows inline, more than three parts fold into "+N itens editados".

### 13. UI

- **Thread from context, and a code task end to end**: one-click thread, context block with "Ajustar trecho" / "Tirar do canal", private-channel block, plan card, pinned card (as built: the thread header, see "UI round") with the checklist as a pixel strip in the agent's tones ("4 de 12 itens · 2 rodando · 1 esperando você"), sessions as one human line each ("O que mudou", "Ver saída"), decision and review cards, mission files, recovery after the Mac goes offline.
- **Threads page**: tabs, rows, mission cards, close/archive dialogs, details panel, "Threads (N)" in a channel.
- **Long task**: live work card, rounds with versions and compare, queued mid-round requests, inline question, PR with merge approval.
- No internal terms in the UI (stream, hooks, MCP, runner, exit code, tool names). Slash commands are English (`/mission`, `/stop`, `/summary`, `/computer`).

## Order

1. Background tasks + `task.done` wake-up + journal and reconnect recovery (unlocks long tasks).
2. Mid-round message queueing in a busy thread (fixes the parallel unaware run, useful alone).
3. Threads: one-click thread from a range (`context_from`), close and archive, Threads page.
4. `agentes` MCP server and the executor prompt (report, update_plan, ask_decision, request_review, upload_artifact, request_approval).
5. Missions: tables, plan card, participants and roles, suggestions, decisions, reviews, `.agentes/` sync, mission brief in context.
6. Parallel worktrees and slots, daily digest via routines.

Runner isolation (ADR 0030) interleaves: its level 1 before parallel tasks, short-lived GitHub tokens before reviews and merges matter.

## Out of scope here

- **Runner isolation**: ADR 0030. Until it lands, "merge needs approval" is enforced by instructions only on connected machines, since the executor may hold the owner's own git credentials.
- **Missions on the agent's cloud computer** (ADR 0021): the same model works once that computer runs an executor (the person signs Claude Code in through the computer's terminal); it needs longer command limits there and counts computer time against the agent's budget.

### Missions run only on the agent engine (2026-10-17, ADR 0032 §6)

This supersedes the parts above where the executor's main session is a machine task. The main session is now the agent's run in the home thread with the mission's brain (the API model, Claude Code or Codex); proposing, Start, people's messages, suggestions, decisions, reviews and items' ends are notices that start or join its run (the executor-agent flow, now for every brain). Item sessions stay machine tasks (work mode only) with their own MCP tools, without `request_approval` (merges, deploys and rollbacks are the main session's ADR 0015 approvals). `send_to_mission`, the `plan` mode of `task.start`, the task-bound approvals (`mission.approval_decided`) and the `MISSIONS_ON_ENGINE` flag are gone. MVP decision: missions open before this change are not migrated (they may stop or need a new message). Details in ADR 0032, "Missions on the engine".

### One worktree per mission (2026-10-21, ADR 0044)

This supersedes "the task's own git worktree and branch" in section 4, the item branches and `work/<item>/` subfolders in "Missions as built" and "Polish round", and `start_task`'s `branch`. At Start the runner makes the mission's own copy of the project (`.worktrees/m-<short id>` on `agentes/<short id>/<slug>`, from the branch checked out in `repo_dir`; migration 0086: `missions.branch`, `base_branch`, `base_sha`, `worktree_path`, `worktree_state`, `worktree_error`); setup runs there first; the main session and every item work in it. `start_task` takes `mode` (`write`, one at a time, each ending in a commit with `machine_tasks.start_sha`/`end_sha`; `read`, in parallel) and items that can't start wait in a queue (`machine_tasks.start_request`) instead of failing with `no_slot`. Runner protocol 14 is required for missions. Details in ADR 0044.

## Consequences

- Long work costs us almost nothing in model tokens: the executor thinks, our code renders and guards.
- Swapping Claude Code for Codex changes the runner's launch command and MCP config, not the product.
- Progress never depends on the model's cooperation (stream events, hooks, exit), but its quality does (summaries, plan and decisions come through MCP calls).
- No fixed phases means progress is "items done", which the executor can re-plan; plan changes are visible in the thread and versioned.
- Approvals only bind actions that pass through us; on a machine with the owner's credentials that is a policy until runner isolation lands.
- Only explicit participants can make work run on someone's computer.
- The machine's disk keeps the executor's session; mission files and `notes.md` make that loss survivable.
