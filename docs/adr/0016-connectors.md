# 0016. Connectors in two layers over MCP

- Status: Accepted
- Date: 2026-10-14

## Decision

**Layer 1, the organization connects once.** `connector_connections` holds an org's connection to an MCP server: connector id (from our catalog), server URL (https), auth type and the credential (OAuth tokens or an API key, as JSON), envelope-encrypted like provider credentials and bound to `(org_id, id)`. One active connection per connector per org; reconnecting replaces it and moves the agents' grants over. Disconnecting deletes the grants. Secrets are never returned by any API.

**Layer 2, each agent gets a subset.** Grants live in `agent_scopes` with the connection id. A grant is accepted only if the connection is active in the org and the scope exists in that connector's catalog (`connectorGrantValidator`). Giving an agent a grant is an admin's call (`manage_agents`), on every path: `PUT …/agents/{id}/scopes`, `PUT …/agents/{id}/access` and a `request_permission` approval. The agent's owner, when not an admin, may only narrow its access (drop grants it has, add tool denials), so whoever an admin made responsible for an agent can't hand it the org's connectors.

**Catalog** (`CONNECTOR_CATALOG`, code we own): for each connector (seeded: GitHub, Sentry, Linear, a Drive-like server) the scopes with labels, and a map from each MCP tool name to one of our scopes, with `sensitive` and an approval-title template. A tool the server lists but the catalog doesn't is never exposed. Merge, deploy and rollback stay sensitive regardless (0015).

**MCP client.** The connector `ToolSource` lists each connected server's tools with the official TypeScript SDK (`@modelcontextprotocol/sdk`, streamable HTTP, bearer token), caches the list for a minute, keeps catalog tools, and exposes them as `<connector>_<tool>` with the server's JSON Schema. Calls open a session through `McpConnect` (tests plug an in-process server via `InMemoryTransport`) and go through the Tool Gateway like every other tool. An unreachable server hides its tools for that turn.

**OAuth.** `startOAuth` (admins, `manage_connectors`) creates a single-use state (only its SHA-256 is stored), a PKCE verifier (sealed) with an S256 challenge, a 10-minute expiry and the person who started it, and returns the provider's authorize URL. The callback (`GET /api/app/connectors/oauth/callback`, session cookie) checks the state is unused, unexpired and the same person (still an admin), exchanges the code with the verifier and stores the tokens sealed, then redirects to the web app. Tokens expiring within a minute are refreshed before a call. Provider OAuth apps come from `CONNECTOR_*_CLIENT_ID/SECRET`; without them a connector can still be connected with an API key.

## Consequences

- Adding a connector is a catalog entry (and optionally OAuth endpoints); no migration.
- Tool output from MCP servers is untrusted content; it reaches the model only as a tool result.

## Addendum (2026-10-14): MCP-native OAuth and custom servers

**Custom MCP servers by URL.** An admin connects any https MCP server. The URL (and every URL learned from it: protected-resource metadata, authorization server endpoints, registration) passes the SSRF guard of ADR 0019. With an API key it is stored sealed; without one we probe the server: an open server connects at once; a `401` leads to OAuth discovery; otherwise the app asks for a key (`needs_key`). Each custom server is its own `connector_connections` row (`connector = custom:{id}`).

**MCP-native OAuth.** Discovery from `WWW-Authenticate: Bearer resource_metadata=…` or `/.well-known/oauth-protected-resource` (with and without the path), authorization server metadata by RFC 8414 (path insertion) then OpenID discovery, Dynamic Client Registration (RFC 7591, public client, `token_endpoint_auth_method: none`) stored per org and issuer in `oauth_clients` (a secret, if issued, is sealed), and the authorization code flow with state, PKCE S256 and the `resource` indicator (RFC 8707) on both the authorize and token requests. Refresh uses the registered client's token endpoint. Catalog connectors with a fixed OAuth app (GitHub, Sentry, Linear, Google Drive) keep using that app; a catalog entry without one would use the native flow. API keys stay as the last resort.

**Tools of custom servers are hidden until classified.** Every listed tool is stored in `custom_tools` with the server's `readOnlyHint`; an admin classifies each as `read`, `write` or `approval` and gives it a label in Portuguese. Only classified tools are offered, with scopes `custom:{connectionId}:read` (read) or `custom:{connectionId}:write` (write and approval); `approval` tools are sensitive, so every call is an approval request titled "{server}: {tool label}". Re-listing (`refresh`) adds new tools unclassified and marks removed ones.

## Addendum (2026-10-16): tools come classified; sensitive tools only ask or stay off

Listing a server's tools classifies each (`connectors/classify.ts`): the server's annotations first (`readOnlyHint` → read, `destructiveHint` → approval and sensitive), then the verb in the name (read verbs, write verbs, and sensitive verbs: delete, remove, send, pay, publish, transfer, refund, unbind, share, merge, deploy, rollback…), and for ambiguous names the shared Judge suggests a level and a reason code, in batches, cached per connection and tool name (`suggestion_source = judge`); judge failures suggest approval with reason `unknown` and are asked again on the next listing. A tool stays "pending" until a person confirms it (`confirmed_at`). Sensitive tools may only be `approval` or `off` (the API refuses read/write; the tool source marks them sensitive whatever is stored, and a re-list turns a stored free level back to approval). `write` tools run without approval and each call is audited (`connector.tool_changed`). The API returns readable name parts and a subject per tool; the web says them in the person's language.

## Addendum (2026-10-27): a custom server's own icon

A server connected by address shows the icon it lists in `serverInfo.icons` (MCP 2025-11-25, from `initialize`), read on every listing of its tools (`connectors/server-icon.ts`). We follow the spec's security rules for icons: only a `data:` URI or an https URL on the server's own origin, through the SSRF guard of ADR 0019, without credentials or redirects, with a 5 s timeout and at most 256 KB; only PNG, JPEG or WebP (no SVG: it can carry script, and the phone app can't draw it), typed by its bytes (a declared type must agree), at most 1024 px a side, and stripped of metadata. The icon is kept in the platform store (S3, `FILES_DIR` or Postgres) under the org's prefix (`orgs/{orgId}/connector-icons/…`, so in Postgres it goes with the org) and a content-hash name and served to the org's members by `GET /api/app/connector-icons/{orgId}/{connectionId}/{file}` (`connector_connections.icon`), so no browser loads anything from the server, and nothing about who uses it reaches the server or a third party. A catalog brand icon wins when there is one. A server that stops listing icons gets the monogram again; when all its icons fail, the last good one stays. We don't guess an icon from the server's website: that would mean fetching pages the server didn't point us to.


## Addendum (2026-10-30): a new connection is every agent's

Agents start with the basics and people take access away where they want. A first connection of a catalog connector (`storeConnection` with no active one to replace) and a new server by address (`storeCustomConnection`, not the same address again) give every active agent the whole connection (`connector:*`, "Ler e escrever") in the same transaction, each grant an `agent.access_changed` audit row by the person who connected (`grantToEveryAgent`). Connecting is an admin's call (`manage_connectors`), and so is giving grants (`manage_agents`): both are admin permissions. The same holds for every client: the web's dialog, the phone and the API. The dialog's last step ("Quem pode usar") starts from these levels, with "Todos os agentes" on top, so an admin confirms or lowers them. Reconnecting keeps the grants as they are. Nothing else changes: sensitive tools ask for approval at any level (0015), a server's tools reach agents only once classified, and mailboxes (0038) and databases (0039) keep their own grants, none given by default.

## Addendum (2026-10-30): reads through Composio's executor

Composio's MCP server runs every app through a few meta tools, marked `destructiveHint`, so each call asked a person, reading pull requests too. The custom source now knows four of them by name. `COMPOSIO_MULTI_EXECUTE_TOOL` says which actions a call runs (`composioActions`: only the documented input, 1 to 50 slugs, no `COMPOSIO_` slug inside, anything else asks as before): when every action only reads, the gateway runs the call as the connection's read (`custom:{id}:read`, when the agent may read the server), so policy, scope, audit and team actions all see a read. A slug reads (`actionLevel`) only when the verb right after its app is get, list, search, find, fetch, check, download, count, describe, view, lookup or read, no other word is a verb, `query` or `replace`, nothing in it is open-ended (`openEnded`: GraphQL, SQL, a mutation, a proxy, a query it runs) and no word sends, deletes or pays in any form. So `GITHUB_LIST_PULL_REQUESTS` reads, while `SHOPIFY_GRAPH_QL_QUERY` (mutations too), `GOOGLEBIGQUERY_QUERY` (any SQL), `GOOGLESHEETS_FIND_REPLACE` and `GITHUB_MARK_NOTIFICATIONS_AS_READ` ask. A wrong guess only makes a call ask. Any other call asks, its card titled by its actions, and may be approved for good per action (ADR 0015). `COMPOSIO_REMOTE_WORKBENCH` and `COMPOSIO_REMOTE_BASH_TOOL` run code that can call any action, and `COMPOSIO_PROXY_EXECUTE` sends any HTTP request to a connected app's API, so they always ask and are never remembered, whatever their annotations or stored level.

## Addendum (2026-10-31): what MCP OAuth asks for, how it authenticates, one refresh at a time

Servers that refused or broke our OAuth showed what the native flow missed. Scopes: when the protected-resource metadata at the server's path lists none, we ask for the root metadata's, if it names the same authorization server (Square refuses an authorization without a scope), and `offline_access` goes with the scopes we ask for when the authorization server lists it (Vercel gives a refresh token only for it), never alone, since no scopes means the server's defaults. The scope is worked out on every authorization (`oauthScope`), not taken from the registered client, so a client still in use that was registered without `offline_access` asks for it on the next one. Client authentication: the registration asks for `none` (a public client with PKCE) when `token_endpoint_auth_methods_supported` lists it or is absent, else `client_secret_post`, else `client_secret_basic`, and the method the registration answer names wins; an answer that gives a secret for `none` without naming a method is kept as `client_secret_post`. The method is kept on the client (`oauth_clients.token_auth_method`, null for clients registered before, which keep sending any secret in the form), and the secret stays sealed and goes the way the method says, at the code exchange and on every refresh, by HTTP Basic with each part form-encoded first (RFC 6749 §2.3.1). A refused registration keeps the server's own `error` and `error_description` (one line, at most 200 characters, nothing else from the answer), returned as `detail` with `not_approved` and shown under our message. A connection's tokens are refreshed once at a time, so two calls never spend the same refresh token (servers that rotate it would refuse the second, and the connection would break), and no transaction stays open while the provider answers: native mode's PGlite runs every query through one transaction lock, so the whole server would wait, and on Postgres each waiting call would hold a pool connection. The call that takes the connection's lease (`connector_connections.refreshing_until`, 30 s, a conditional UPDATE on the tokens it read) asks the provider; the others read the row until the tokens change, or until the lease ends and one of them takes it over. Within a process, calls that need the same refresh share it. The new tokens are written only over the ones refreshed, so a reconnect meanwhile keeps its own, and the token request gives up after 15 s, well inside the lease. The refresh of an MCP OAuth connection sends the resource it was authorized for (`connector_connections.resource`), since the MCP authorization spec wants it on every token request. One-click presets can say how their server takes an API key (`keyScheme`: Semrush's is `Apikey`, the others `Bearer`) and that the Cloud offers no key for it (`cloudOAuthOnly`, Intercom's US and EU servers). Intercom's server does take an access token, but its terms forbid an app asking its users for theirs, and on the Cloud agentes.chat is that app. Self-hosted, a workspace connects its own data, which is what those tokens are for, so the key stays.

## Addendum (2026-10-31): several accounts per MCP server

Amended by ADR 0099. A server's address connected again is another account of it, not a new sign-in: "Reconectar" names its connection (`connectionId`). Every account is every agent's. Tool names start with each connection's stored `tool_prefix`, set once, not with its label, so renaming never renames tools. Catalog connectors keep one connection each.

## Addendum (2026-10-31): no native Google Drive; services through Composio

Amended by ADR 0107. The catalog is GitHub, Sentry and Linear: the Drive-like entry, its address field (`needsServerUrl`), its Google OAuth app (`CONNECTOR_GOOGLE_*`) and the `serverUrl` override of `startOAuth` and `POST …/connectors` are gone, and migration 0156 disconnects any native Drive row. A preset may carry a `composio` way, on Composio's own OAuth app only (no key to paste, no app of ours): the service connects as a server by its toolkit's address (`https://backend.composio.dev/api/v3.1/toolkits/<toolkit>`, never fetched), through Composio's Connect Link and Composio's account instead of tokens of ours, with the explicit actions the entry lists. Each service appears once, by the first way that works on this server: our connector, the vendor's MCP server, Composio, "Em breve", else unavailable.

## Addendum (2026-11-03): GitHub's current tools, Projects and Actions, and what a sign-in lacks

GitHub's remote MCP server renamed its tools (`issue_read`, `issue_write`, `pull_request_read`, `actions_list`, `projects_write`…), and a tool our catalog doesn't name is never exposed, so agents couldn't create an issue or read a pull request through the connector and fell back to signing the person in to gh on their computer, which leaves the person's own token there, outside the scopes, approvals and git proxy.

- **The catalog follows the server's current names** (its README, read 2026-11-03), with new scopes `actions.read`, `projects.read` and `projects.write` (on with the connection, like the rest). `pull_request_review_write` (it can approve) and `actions_run_trigger` (it can deploy) are sensitive.
- **Toolsets and scopes.** The remote server loads only context, repos, issues, pull_requests and users unless asked, so the catalog entry carries `headers` (`X-MCP-Toolsets: …,actions,projects`), sent with the sign-in. The OAuth sign-in asks for `project` too (Projects v2 needs it).
- **What a sign-in lacks.** `connector_connections.oauth_scopes` keeps what a catalog sign-in granted (the token's `scope`, else what we asked for; sign-ins from before were backfilled with the catalog's scopes of that time). A connection whose sign-in lacks some of what the catalog asks for now shows a line saying what Reconectar adds ("Reconecte o GitHub para os agentes também poderem usar o GitHub Projects"), on the web and the phone, and keeps working as it is until then.
- **Agents are told** (`GITHUB_GUIDANCE`, with GitHub only): the connector and git through our proxy, read-only gh runs without asking where gh is already signed in, never sign the person in to gh nor ask for a GitHub token, and when the connector lacks something say what and that an admin can reconnect.
- Reconectar moves the connection's "Aprovar sempre" rules to the new connection with the agents' grants, so asking everyone to reconnect for Projects never makes them approve again.
