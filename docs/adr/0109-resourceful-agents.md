# 0109. One permission model, the web for every agent, and giving up needs evidence

- Status: Accepted (built: the server, the runner, the web and the phone app)
- Date: 2026-11-01
- Amends: ADR 0053 (§2 and §3 and the addendum of 2026-10-31: a routine's `read` access is gone, no run gets the read-only computer profile for who woke it), ADR 0097 (a new `untried` verdict, a routine's report held once, the judge reads `means` and `tried`)
- Code: `packages/engine/src/routine-brief.ts` (`routineAccessOf`), `tools/run-policy.ts`, `mission-worktree.ts` (`missionTurnPermissions`), `apps/server/src/engine.ts` (`turnPermissions`), `apps/server/runner/mcp.ts` (`PLAN_DENY`), `apps/server/runner/brain.ts` (`PLAN_BUILTIN_TOOLS`), `web-tools.ts`, `browser/tools.ts` (`readPage`), `context.ts` (`HOW_YOU_WORK`, the routine block), `capabilities.ts` (`## Your means`), `tools/directory.ts` (`turnMeans`, `find_tools`), `continuation.ts` (`untried`, `triedCalls`, `untriedNudge`), `hand-off.ts` (`holdUntried`, `handOffHolds`), `executor.ts`, `autonomy-report.ts`, `packages/config/src/schema.ts`, the web and phone routine forms

## Context

A weekly routine asked an agent to research the news about a company and summarize it. The routine had been created to only look and tell, so its run had no web: the runner's `plan` profile removed Claude Code's `WebSearch` and `WebFetch`, the run policy held the browser back as "it can send data out", and the prompt said "no web". The agent called `find_tools` once, found nothing, and handed the problem to a person. The continuation judge graded that hand-off done ("said plainly what it couldn't do"), and a routine whose `hand_off` already posted was never judged at all.

Two causes, both general: the run had no means, and nothing made it use the means it had. Other agent products keep reading the web even in their most restricted profiles, tell the model that an empty result means vary the attempt, and define a blocker narrowly. Research and design: the owner's evidence folder (`resourceful-agents-research.md`, `resourceful-agents-design.md`).

## Decision

The owner's decision: **one permission model, the agent's own.** It overrides the design's links-only rule, URL caps and read tiers for routines.

1. **No more read-only runs.** Every run of an agent can do what the agent can do, whatever started it (a person, a routine, a webhook, a task's end, another agent). `routineAccessOf` reads every routine as `act`; the column stays (no data migration) and an old client's `read` is accepted and ignored. The access choice is gone from the routine form on the web and the phone and from `create_routine`/`update_routine`. The computer's `plan` profile is only a mission's (before Start and while a write item runs, ADR 0044): routine and unattended turns work. Governance stays at the agent: its tools and connectors, scopes, computer, audience, and each tool's approvals; sensitive or outward actions still ask a person; a routine still never manages routines, reminders, channels, secrets or permissions and still reaches only its creator's rooms and agents; text a routine read (`fedByRoutine`) keeps credentials refused and masked and every connected-app write and mail send asking; injected text never grants permissions. A routine's prompt now may be changed only by its creator (anyone else takes it over first), since every routine reaches what its creator reaches.
2. **Web reading for every agent.** A core `web` source, no scope, so every agent has it and a person can still deny one tool (`deny:web_fetch`): `web_search` (titles, links, snippets) and `web_fetch` (one GET through the public-URL guard on every redirect hop, 10 s, 2 MB, HTML to text, a block or captcha said as such with the alternatives). Both are `external` (their output reaches the model as data). Search providers, the first that answers: `BRAVE_SEARCH_API_KEY`, `SEARXNG_URL`, the agent's own browser when it may use one (Google, then Bing, then DuckDuckGo on a captcha, a block or a page that didn't open, a site off the agent's list included), DuckDuckGo's HTML page. Computer brains reach them through the engine's MCP bridge, and Claude Code's own `WebSearch`/`WebFetch` are allowed in `plan` too. Every call is a run step (the Tool Gateway's) and a usage row (`kind` `agent`, provider `web`, cost 0, `billedTo` `platform`: never the agent's budget; the readers of model calls, the model line under a reply, the usage summary, plan usage and telemetry, leave provider `web` out). Provider-native search (a model's server tools) is not used.
3. **The browser** is every run's wherever the agent has browser access; no routine-specific hold.
4. **One prompt for every brain.** `HOW_YOU_WORK` says: an empty or blocked result means change the words, the source or the tool; check your tools, computer, browser, terminal and teammates before saying you can't; a real blocker is only something a person must give (a code, a sign-in, a payment, a permission, a decision); say what you tried. A generated `## Your means` block lists what the run really has (`turnMeans`: web, browser, terminal, tool directory, teammates), never a means it lacks.
5. **`find_tools`** with no match, or only weak ones (the best match has under half the query's words), lists the general means, with the teammates the person behind the run (or the routine's creator) may talk to and their roles.
6. **The controller's `untried` verdict.** The judge reads `means` and `tried`: each tool call of the run with its argument and outcome, from the gateway's run steps (API brains, and computer brains' calls to our tools through the bridge) and from a computer brain's own tools. Those arrive as `brain.event` frames of type `tool_call` with `executed` (Claude Code's `Bash`, `WebSearch`… since the runner's parser forwards Claude Code's own tools, an older runner sends only ours; Codex's commands), which the executor keeps in `transcript.harnessTried`. "Couldn't" is done only after several different attempts or a person-only blocker; otherwise `untried` continues once with a nudge listing the means and the attempts (a second "couldn't" with no new tool call ends). A routine's `hand_off` judged untried is held once, before anything posts and outside the delivery's transaction: the tool answers with the nudge and the next `hand_off` always posts. The bounds are the existing ones (2 extra turns per run, 1 per routine; a hold uses the routine's one), and every judgment is recorded like any other (`follow_through`). The autonomy report counts untried nudges and those that acted after it and ended done.

## Consequences

- A routine that used to only look can now change things inside the workspace and reach its creator's agents. Existing "read" routines start acting on their next firing; approvals still guard what is sensitive or outward.
- DuckDuckGo's HTML page may answer the Cloud's addresses with a bot check, and its terms don't welcome automated use: the Cloud should set `BRAVE_SEARCH_API_KEY` or `SEARXNG_URL`. A self-hosted server works with no key.
- Runner change (`PLAN_DENY`, `PLAN_BUILTIN_TOOLS`): only a mission's planning turns notice it; a Cloud pin follows. No protocol bump: an older runner's `plan` keeps the web out, which is only a mission's planning now.
- Resilience is measured by `bun run eval:resilience` (real models, manual) and the autonomy suite's scenarios (fake provider, CI).

## Addendum (2026-11-01): asking a person goes through the same check

A second production case: asked to pull its owner's spend on one product from an external API with no connector, an agent on a computer with a browser searched the tool directory and the workspace, found nothing, and asked the person for the API's address and what the product's name meant. Both were on the web; only the API key was the person's to give.

1. **`ask_user` is judged like giving up** (`holdAsk` in `hand-off.ts`, wired in `questions.ts`). Before the card posts, one judgment (`ask_check`, recorded like every judgment) reads the question, the task, the run's `means` and `tried` and answers `findable` (what its means could find: an API's address or docs, what a name the person used refers to, a public fact, something in the workspace), `secret` (a password, key, token or code typed in the chat) or `person` (a decision, a preference, an approval, a payment, an access, a request ambiguous beyond finding, or `tried` already shows the search). A `findable` question is held once: the tool answers with the means and what it tried (`findableNudge`) and the run goes on; the next findable question is asked. A `secret` question is turned to `request_secret` (or, with no secure request at hand, the agent says which key it needs without asking for it in the chat). A findable question is held at most once; a `secret` question is refused every time (it is a refusal, not a nudge, so other holds don't spend it), and when the judgment fails a question naming a key, a token or a password is refused while any other goes.
2. **The controller's question card**: the turn-end judge's `untried` now covers asking a person for what its means could find, and `ask` only what the means can't find, so a turn that describes a findable need is told its means instead of turned into a card.
3. **The prompt** (`HOW_YOU_WORK`): before asking a person, find what you can, ask only for what only they can give, state an assumption when something stays unclear, and a secret always through `request_secret`.
4. **Codex and the web**: computer brains list our tools through the bridge (`bridgeToolsFor`, the gateway's own list), and the core `web` source has no scope, so Codex and Claude Code turns get `web_search` and `web_fetch` with the browser's tools. The production run predates this ADR's web source; no runner change.
5. **Measured**: autonomy scenarios S59–S62 (fake provider) and three `eval:resilience` cases (`ada-external-api-key`, `ambiguous-one-question`, `secret-never-in-chat`, graded on `request_secret` and on the questions that reached the person).
6. **A secret through the controller**: the turn-end judge has a `secret` verdict (the reply asks for a key, a token or a password in the chat, or needs one and hasn't used a secure request). Such a reply is neither posted nor made a question card: the run reads `SECRET_NUDGE` once (`request_secret` when it has it, otherwise say which key and where it is set up) and its next reply ends the run as it is. A routine's or an agents' DM run ends as `ask_elsewhere`. Scenarios S63–S64; `eval:resilience` fails a reply that asks for the key in the chat.

## Addendum (2026-11-03): no stop on a person-only step

§4's blocker line ("a real blocker is only something a person must give: a code, a sign-in…") is replaced: a step only a person can do is handed to them with its request, then the agent goes on, and `untried` covers a stop on it while the means can hand it over. See ADR 0097, addendum 2026-11-03.
