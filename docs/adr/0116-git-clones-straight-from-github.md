# 0116. Agents' git clones: straight from GitHub, apart from the request, two at a time, through a shared cache

- Status: Accepted
- Date: 2026-11-01
- Amends: ADR 0024 addendum (`git.sync`: fetches no longer have to go through the proxy; pushes still do)
- Code: `apps/server/runner/git.ts` (`directCredentialHelper`, clone jobs, `MAX_CLONES`, `CLONE_STALL_MS`, `fillCache`), `apps/server/runner/daemon.ts` (`gitCache`, `rootGitCache`), `apps/server/runner/supervisor.ts` and `worker.ts` (`clone.slot`, `cache.fill`), `apps/server/runner/agent-users.ts` (`ensureGitCacheUser`, `grantGitCache`), `packages/engine/src/git/machine.ts` (`directFetchTokens`, `checkoutsOnMachine`, `MACHINE_CLONE_WAIT_SECONDS`), `packages/engine/src/git/tools.ts` (`git_clone` on `cloning`), `packages/adapters/src/machine-protocol.ts` (`GIT_DIRECT_PROTOCOL` 35)

## Context

Agents cloned big repositories at about 100 to 130 KB/s: a 2 GB repository took hours, and several agents cloned the same ones. Every pack byte went through one Bun process on our app server (the git proxy, ADR 0024); each deploy (many a day) cut every clone in flight, and a clone never resumed; a fixed 30-minute deadline cut big clones anyway; partial clones later fetched blobs one request at a time through the proxy; and nine or more `index-pack` processes at once thrashed a 4-vCPU computer.

## Decision

1. **Fetch from GitHub, push through the proxy.** Where our GitHub App is installed for the repository and the agent was given it, a runner on protocol 35 gets, with each `git.sync`, a GitHub App installation token for that repository alone with `contents: read` (GitHub's tokens last one hour; the server's cache hands out one until 5 minutes before it ends). The checkout's `remote.origin.url` is `https://github.com/<owner>/<name>.git` and `remote.origin.pushurl` the proxy, so every push is still checked there (only `agentes/<handle>/…`, the agent's repositories). One credential helper, in the checkout's own config after the machine's are reset, hands the GitHub token (its own file, mode 600, in the runner's or the agent worker's private folder) only to `github.com` and our proxy credential to every other host. Each turn's sync and each `git_clone` hand over a fresh token, so the agent's own `git fetch` keeps working; an agent with an `owner/*` (or all-repositories) grant gets tokens for the checkouts the computer lists under its `repos/`, so those stay on GitHub too. No token goes to an archived, held or suspended agent (the proxy refuses those as well), and each token handed out is audited as a `git.fetch` with `via: github-direct`, since the fetches no longer pass us. The connection's own token (OAuth or pasted) never reaches a computer: without the App, fetches go through the proxy as before, and a sync without a token puts the checkout back on the proxy and deletes the token file left from before.
2. **A clone outlives its request.** The runner runs each clone as a job apart from the request: a socket that drops (a deploy) doesn't stop it. The server waits up to 10 minutes; past that the answer is `cloning` with git's last progress line, and `git_clone` tells the agent the download goes on by itself and to call it again when it needs the code. A later `git_clone` of the same folder waits for the same job and never touches the half-made folder; the sync before a turn doesn't wait for it (the repository shows as still downloading in the turn's prompt, not as not cloned). A clone GitHub refuses (a token that ran out while it waited for a slot or filled the cache, or github.com out of reach) tries once more through the proxy, and the next sync moves it back to GitHub with a fresh token. The fixed deadline is gone: a clone stops when git shows no progress for 10 minutes (with a 24-hour ceiling). An older runner keeps the 30-minute deadline.
3. **At most two clones at once per computer.** The others wait in order; the `git_clone` that started a waiting clone answers at once with "waiting for another download to finish". In single-user mode the runner's one process holds the slots; in system mode each agent's git runs in its own worker, so the worker asks root for a slot (`clone.slot` / `clone.slotted` / `clone.release` on the worker link) and root's process holds them all; a worker that stops gives its slots back.
4. **A shared read-only cache.** With a GitHub token, before a clone the repository is fetched into a bare repository in the cache (one fetch at a time per repository) with the requesting agent's own token, so it reaches only what that agent may fetch; then the checkout is cloned whole (no blob filter) with `--reference` to it, so only what the cache lacks comes over the network. The cache never prunes (`gc.pruneExpire=never`, cruft packs, no `--prune`), since checkouts borrow its objects, and nothing removes a cached repository yet. Without a token there is no cache: a full fetch through the proxy would cost the server more than the partial clone (`--filter=blob:none`) it replaces, so that clone stays as before.
   - Single-user mode: `<runner home>/git-cache/<connection>/<owner>/<name>.git`, no ACLs (every agent is the runner's user).
   - System mode: root's `/var/cache/agentes-git/<connection>/<owner>/<name>.git`. The worker sends its agent's token to root (`cache.fill`); root fetches from `https://github.com/<owner>/<name>.git` (a URL it builds, never one the worker names) as the system user `agentes-git` (made on first use), with the token only in that git's environment. The repository folder is `agentes-git`'s, mode 700, its contents readable by whoever may enter it (`--shared=all`); the folders above are root's, 711. Only when GitHub let that agent fetch does root add an ACL for the agent's uid (taken from the worker, never the frame) on that one folder (`setfacl -m u:<uid>:rx`), so an agent never let in can't read it, whoever filled it. Without `setfacl` the clone goes without the cache.

## Consequences

- The app server carries only pushes and what goes through the proxy without the App; deploys no longer cut downloads.
- A GitHub App token the agent's checkout can read reaches the computer: one repository it already has, read only, for an hour. The agent could read that repository through GitHub's API in that hour without our audit; it could already clone it.
- Reads straight from GitHub skip the proxy's checks on each request: archiving, holding or suspending the agent, removing its computer or taking the repository off its list stops new tokens at once, but a token already on the computer keeps working until its hour ends (at most an hour; the next sync deletes it when no new one comes).
- On the server's own computer, where each organization's runner has its own supervisor, each holds its own two slots.
- Removing a cached repository once no `objects/info/alternates` points to it isn't built.
- A clone killed with the runner leaves its folder; the next sync treats it as a checkout and fetches into it (git resumes no pack mid-way).

## Addendum (2026-11-08): GitHub's stateless tokens, protocol 53

Since 2026-10-02 GitHub mints only stateless installation tokens (`ghs_<app id>_<JWT>`, about 520 characters, with dots and dashes; GitHub changelog, "Stateless GitHub App installation tokens rolled out"). Runners up to protocol 52 take only the old 40-character kind and refuse a whole `git.sync` on any other, before writing its proxy credential: with the App installed, every sync failed (`git_clone`: "github is not a GitHub App token") and the computer's proxy credential ran out 6 hours after the last good one, so the agent's own fetches and pushes through the proxy were refused too.

- Both kinds match `GITHUB_APP_TOKEN` (GitHub's own pattern, `ghs_[A-Za-z0-9._-]{36,}`, at most 4096 characters), shared by the runner and the server. The server hands over only a token it matches, and only to runners on protocol 53 (`GIT_STATELESS_TOKEN_PROTOCOL`); older ones get none and fetch through the proxy. A person's token (`gho_`, `ghp_`, `ghu_`, `github_pat_`) never matches.
- The runner writes the request's proxy credential before anything else in the request can refuse it.
