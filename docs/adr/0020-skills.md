# 0020. Skills in Markdown (SKILL.md), loaded on demand, no code execution

- Status: Accepted. Amended 2026-10-30: Import (a GitHub link is read from the repository's archive, and a link that holds several skills lists them to pick from). Amended 2026-10-31: Import (a private repository is read through the workspace's GitHub). Amended 2026-11-03: updates from the link, agents improving skills, and the choice between the link's version and the agents'
- Date: 2026-10-14

## Decision

**Format.** Skills follow the Agent Skills layout: a `SKILL.md` with YAML frontmatter (`name`: kebab-case, at most 64 characters; `description`: at most 1024; other fields kept as `metadata`) and a Markdown body, plus supporting files. It is plain text, so it works with every model provider.

**Storage.** `skills` (org-scoped, unique `slug` per org, `version`), `skill_files` (per version: path, size, mime, status, blob location) and `agent_skills` (per agent, enabled). File contents go through the org's `BlobStoreResolver` like artifacts. Only text files we can show are stored (md, txt, csv, json, yaml, html, svg; binaries too since the 2026-11-03 amendment). Everything else, scripts first of all, is recorded as `ignored`: listed so people see it, never stored as content and never offered to the model as something to run.

**Import.**
- A zip of the folder: a small zip reader that checks the declared sizes before inflating (2 MB total, 200 files) and rejects path traversal.
- A GitHub URL: a folder through the contents API, or a single `SKILL.md`, raw. Only GitHub hosts, the SSRF guard on every request, no redirects, the same limits; scripts are not even downloaded.
- By hand.

*Amended 2026-10-30:* a GitHub link is read from the repository's zip archive at the link's ref (`github.com/{owner}/{repo}/archive/{ref}.zip`, which redirects to codeload.github.com), no longer through the contents API. Unauthenticated REST API calls share one limit per server address, 60 requests an hour (docs.github.com, "Rate limits for the REST API"), and the contents walk spent one per folder, so every workspace's imports drew on the same budget and one repository of a few dozen skills could spend it. The archive is one download outside the REST API, works with no GitHub connection (a self-host has none by default), and its central directory lists every path, so only the chosen skill's files are inflated. Signing the API calls with the workspace's GitHub connection was the alternative: it helps only workspaces that connected GitHub, spends a person's token on a read the server does for everyone, and still costs a request per folder. This download alone follows redirects, at most 3, each hop to a GitHub host through the SSRF guard. The archive may be up to 50 MB, and one past 65,535 files (whose count only a zip64 record holds) is refused, never read in part. A skill keeps its 200 files and its 2 MB, which binaries don't count toward: they are listed and never inflated. Symbolic links are left out. Each read of a link downloads the archive again, so a person may read 60 links an hour, listing, installing and updating from a link alike (`rate_limited` past that).

A link to a skill's folder installs it as before, and a link to a file, its `SKILL.md` included, installs that file's folder. A link to a repository or to a folder that holds several skills (folders with a `SKILL.md`, up to 6 levels below it, at most 100, one inside another skill's folder being a file of that skill) installs nothing and answers with them, by name and description from each `SKILL.md`, for the person to pick one or several (`POST …/skills/import` with `paths`). A link that holds one skill folder installs it at once. Of several, those that can't be installed (past the 2 MB or the 200 files, or a `SKILL.md` that doesn't parse) come apart in `skipped`, each with its refusal's code (`skill.too_large`, `skill.too_many_files`, `skill.invalid_description`, `skill.invalid_name`…), shown with why and never offered to pick. A skill found below the link records its own folder as its source, so updating it from the link reads that folder only. GitHub's refusals carry codes the apps translate: a private or missing repository (`github.repo_missing`, github.com answers 404), a branch, tag or commit the repository lacks (`github.ref_missing`, codeload answers 404 after the redirect), GitHub limiting the server (`github.limited`, a 429 with the minutes to wait from `retry-after` or `x-ratelimit-reset`, else one), and no `SKILL.md` at or below the link (`skill.no_skill_md`).

*Amended 2026-10-31:* a private repository is read through the workspace's GitHub. The link is still tried with no credentials first; when github.com answers 404, the server tries the workspace's GitHub connections in order: the GitHub App's installation token for that one repository (`contents: read`, only for an installation bound to this workspace), then the GitHub connector's token (OAuth, or a key pasted in Settings › Connectors). With a token the archive comes from the REST API (`api.github.com/repos/{owner}/{repo}/zipball/{ref}`, on that token's own limit), which redirects to codeload with a short-lived link of its own, so the token goes to api.github.com only, never to codeload, the browser or the phone. The API answers 404 alike for a ref the repository lacks and for a repository the token can't see, so a 404 for a named ref asks for the repository to tell them apart (`github.ref_missing`). A token GitHub refuses (401), an organization's SSO (403) or a 404 moves on to the next connection. An owner or repository name that isn't one GitHub allows, or a ref with a `.` or `..` segment, is never sent with a token, so no API path is built that climbs out of the repository. When none reads it, `github.repo_missing` says how the workspace's GitHub connection fared (`connection`: `none`; `refused`, a token GitHub no longer takes, or none to make; `ok`, one that works and can't see the repository) and whether the GitHub App is installed on some account for the workspace (`app`). The apps offer "Conectar o GitHub" whenever no connection works, to people who may manage connectors: with none (the app on other accounts only adds "add the repository to the app on its account, or connect GitHub") and with one GitHub refuses, where connecting again is the fix. It is the existing connect flow over the dialog: once connected (with a key in place, or signing in on GitHub and coming back to Skills with `?install=` and the server's `?connected=github`) the link is read again, and the flow goes on to what GitHub does and who uses it, as from Conectores, since a first connection is every agent's. A connection that works and can't see the repository gets access on GitHub instead: the apps never offer to replace, from a skills dialog, the token every agent uses. People who can't manage connectors are told whom to ask. GitHub not answering while a token is made (no answer, or a 5xx) is `github.unreachable`, to try again, never a repository missing or a connection gone. Reading through the workspace's GitHub is part of installing skills, so it takes `manage_agents` like the rest of the import, checked before any request, and reaches only what the connection really reaches (GitHub decides). The size and file limits are those of any link.

The skill remembers which connection read it (`skills.source_via`: `github_app` or `github`; null when none was needed), shown on its page while it is still the link's (an edit or an upload keeps it for updating, without the line). Updating it reads through that connection first, never without credentials first, then through the workspace's other GitHub connection, and keeps the one that read it: a skill never stays stuck on a connection the workspace moved away from (the repository taken out of the app's installation, the connection revoked while the app reaches it). `skill.connection_gone` says the workspace no longer has the connection that read it (no active GitHub connection, or no installation of the app on the repository's account), decided from the workspace's rows, never from a token request that failed, and only when the other can't read it either. Any other refusal is said as in the dialog. A skill read with no credentials is updated as it is installed (no credentials, then the connections). A second way in, when GitHub is connected: "Escolher do GitHub conectado" lists the repositories the connection reaches (`GET …/github/repositories`, ADR 0033, cached a minute per workspace and GitHub connection, so a connection made, replaced or removed shows at once), and the one picked is read with `list`, which answers with its skills to pick even when it holds one.

The alternative of offering the connected repositories only (no fallback for a pasted link) was left out: people come with links (a README, a colleague), and a link to a repository the connection reaches should just work. Trying the connections before the public read was left out too: a public repository costs no token and no API request that way.

*Amended 2026-11-03:* a skill keeps its images, PDFs and other binary files too, so its agents can read every asset its instructions point to (`references/diagram.png`). Binaries still don't count toward the 2 MB of text and scripts: they are kept in folder order up to 20 MB in all (`SKILL_LIMITS.assetBytes`), and the rest are listed only, never inflated, with a size that tells them apart from rows of older imports. `read_skill_file` returns text as text; a PNG, JPEG, GIF or WebP up to 3.75 MB as an image the model sees (`ToolOutput.images`, carried in the `tool_result` block to the Claude, OpenAI and Gemini APIs; OpenRouter and other companies' Anthropic-compatible endpoints say it isn't shown, since a text-only model there would refuse the request; the type comes from the bytes, never the name, and a request carries at most 15 MB of image base64, the oldest dropped first); and any other file, or an image for a computer brain (which sees pictures with its own tools), saved to `.skills/{name}/{path}` on the agent's computer, or described by name, type and size when there is none. Images count as about 1,600 tokens in estimates, never their base64 length, and drop out with their result when context gives way. A skill's files are workspace content, as before: nothing here changes how they are trusted.

*Amended 2026-11-05 (large skills):* published skills now come as design kits of about 1,600 files, 8 MB of text and scripts and 28 MB of images. A skill takes up to 3,000 files, 16 MB of text and scripts and 40 MB of binaries; the repository's archive stays capped at 50 MB, and a refusal says the skill's own count or size. So thousands of files stay workable: blobs are read and written 16 at a time and the rows inserted at once, `load_skill` names 100 files and folds the rest by folder (a `read_skill_file` path ending in `/` lists one), and `run_skill_script` copies a version to the computer once (`.skills/{name}/.copied-v{version}`) and only its scripts on every run after, so what runs is the skill's, never what was written over it there. Picks from a link are inflated one skill at a time.

Importing a skill whose name already exists in the org makes a new version; re-import from the source URL does the same.

*Amended 2026-11-03 (updates from the link):* updating from the link (`updateSkillFromSource`, the app's "Update from link", agents' `update_skill_from_source` and the daily job) hashes what the link holds (`skills.source_hash`): the same content again makes no version. New text and files that don't run apply as a new version that "Undo update" takes back to the version before, text and files (`skills.last_update`). An update that adds or changes a script, or a binary that isn't an image or a PDF (something a script could run), doesn't apply: it waits in `skills.pending_update` with those files until a person who manages skills applies it (only the content shown: if the link changed since, it waits again with what it holds now) or refuses it (the same content isn't raised again). "Update by itself" (`skills.auto_update`) reads the link once a day per workspace (job `skills.update`, queued hourly with the date in its dedupe key, each workspace at its own time within 6 hours) with the rights of the person who turned it on: an applied update is told to them, a waiting one to who manages skills, and a refusal once (`skills.update_error`) until an update works. GitHub limiting the server or the network failing is left for the next day. A skill whose link now holds several skills or another one is refused (`skill.link_holds_several`, `skill.link_renamed`), never saved as a different skill. Install, update, delete and per-agent changes are audited.

*Amended 2026-11-03 (agents improve skills):* agents change the skills people made, not only their own (ADR 0120, addendum of 2026-11-03). "Agentes melhoram as skills sozinhos" is a workspace setting (`organization_settings.agents_improve_skills`, on by default, `GET/PUT …/skill-settings`) with a per-skill override (`skills.agents_improve`, null follows the workspace; `PATCH …/skills/{id}` with `agentsImprove`), both changed by who manages agents and shown in Skills on the web and the phone. While it is on, `update_skill` changes a person's skill at once: its body and its text files (references, Markdown, data; `writeSkillChange`, the other files carried over), always a new version. A change to a file that runs (`runsCode`: a script `run_skill_script` runs, or a binary that isn't an image or a PDF) never applies directly: each one is a `skill` proposal for that file (`context_proposals.skill_path`, the whole new text, shown as a diff) that who manages agents accepts, applied only while the file is still what it was proposed against. The skill's author hears it (`skill_update` notice, `latest.statusTo` `edited`, one row per skill that gathers the agents' changes while unread), and Skills shows the agent's last change with Desfazer (`skills.last_update` with `agentId`, the same undo as an update from the link: the version before, text and files). An agent's change (or an accepted proposal) marks the skill `skills.edited_since_source` (migration 0197), cleared by any save of the whole skill: while its link holds the same, nothing happens (the link's hash is compared, not the skill's text); once its link changes, the update doesn't replace the agents' work by itself but waits like a script change (`pending_update.edited`, the notice's `latest.reason` `edited`), and who manages skills applies it (Desfazer then brings the agents' version back) or refuses it. Agents change one skill at most 3 times in a run and 20 times a day (all agents), and stop proposing while 10 of its changes wait (`SKILL_CHANGE_LIMITS`): past that `update_skill` is refused, so a loop of fixes can't churn a skill or its reviewers. A proposal for a file that runs is accepted only by who manages agents (`manage_agents`), as an update from the link that changes one; `review_memory` alone decides the text ones.

**Runtime: progressive disclosure.** The prompt lists only the agent's enabled skills (name and description) under "Skills disponíveis", with the rule to load a matching skill before acting. `load_skill(name)` returns the body and the file list; `read_skill_file(name, path)` returns a text file, truncated. Both are built-in tools with scope `skills:read`, granted by default (backfilled by migration 0024) and deniable through per-agent access. Loads are tool steps, so they show in "Ações recentes", and the tokens are counted by the Model Gateway like everything else.

*Amended 2026-11-03 (choosing between the link and the agents):* a waiting update is a choice the page shows in full, on the web and the phone. It keeps what its link holds (`pending_update.body`, `description`, and each file that runs with both texts, `files`, up to 64,000 characters a side, else only its name), and the skill keeps the text its link last wrote when an agent (or an accepted proposal) first changes it (`skills.link_base`, migration 0201, with when the link wrote it), cleared once its link writes it again. The skill's page (`GET …/skills/{id}`: `pending` and `changes`) reads it three ways, as tabs over the line diff the proposals use: what the agents changed (`link_base` → now), what its link changed (`link_base` → the link's), and now against the link's; with no `link_base` (changed before this), only the last; an update the agents didn't touch, what it changes. Who changed it and when comes from the agents' own receipts (`agent_actions` `skill.updated`, the last 20, an update from its link an agent asked for left out by `params.fromLink`; indexed on `org_id, target_id`). The choice is "Usar a versão do link" or "Manter a dos agentes" ("Aplicar atualização" or "Não aplicar" when only files that run changed), each with Desfazer: in the toast on the web and as a line on the page on both. Desfazer after keeping it makes the same update wait again (`POST …/update/reopen`, audited `skill.update_reopened`); after using the link's, it brings back the agents' version and the same update waiting, its hash, `edited_since_source` and `link_base` as they were (`last_update.waited`). The library marks such a skill "Link e agentes mudaram"; its notice reads "{name} mudou no link e com os agentes: escolha qual versão fica". The agents' changes are listed on a person's skill too, each opening its diff in place, with Desfazer on the newest while it is still the skill's version. Undoing an agent's change marks it undone in that history and puts `edited_since_source` and `link_base` back as they were before it, so undoing the agents' only change lets the link's next version apply without a person. An update that waited before its content was kept gets it at its next read, kept out or not.

## Consequences

- Skills can't do anything a prompt can't: no new permission path, and no code runs until the sandbox phase decides how scripts may execute.
- Anthropic's native skills (through their API) are left for later.
