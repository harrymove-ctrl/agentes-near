## Context

A customer's agent made an inbox through the MillionSend connector (an MCP server) and then tried to make a routine that runs on its mail. It was refused: routines read only mailboxes connected here (Gmail and Outlook through Composio, IMAP), and the agent couldn't say where a person connects one.

MillionSend's inboxes are Resend's Inboxes API plus its own fields: threads with folders and read state, received mail with screening and quarantine, drafts, replies and forwards that follow the inbox's own send rules, and webhooks signed the Standard Webhooks way. MillionSend has no IMAP: an inbox is read only through its API.

## Decision

1. **A fourth path, `via = millionsend`.** A mailbox row like the others (`provider = millionsend`, `external_account_id` = the inbox), so agents get it through the same grants, rules, approvals, untrusted wrapping and tools (`mail_<slug>_*`). No migration: the sealed secret is JSON (`{ apiKey, webhook? }`), bound to (org, mailbox) like an IMAP password.
2. **Connecting.** An admin gives a key and picks one of the inboxes it reaches (`POST …/mail/millionsend/inboxes`, then `POST …/mail/accounts/millionsend`). A key MillionSend refuses, or one that can only send, is `auth`. The workspace's MillionSend connector's key is offered when it holds one (a connection made with a key; a sign-in holds a token for MillionSend's MCP only, not for its API), and is read on the server only when the person keeps it chosen. The key never comes back.
3. **New mail.** Where MillionSend can reach the server (https, not a local or private host), connecting makes a webhook for that inbox alone (`inbox.email.received`) to `{PUBLIC_URL}/api/webhooks/millionsend`, signed with a `whsec_` secret we make and keep sealed. The route reads the inbox the body names only to pick whose secrets to try: nothing counts until one signs it (401 otherwise), within 5 minutes. A delivery signed by a disconnected mailbox's secret (its webhook outlived a delete that failed) deletes that webhook with the mailbox's key and is taken (202), running nothing: refused, MillionSend would keep mailing the team that its webhook fails. A key that may not make webhooks (one limited to an inbox) leaves the mailbox polled. Every MillionSend watch is also polled like IMAP's (`pollMailWatches`, `MAIL_POLL_SECONDS`): that catches what a webhook missed, and `mail_seen` keeps a message from running twice whichever brings it. A poll looks 10 minutes behind the newest message seen, never before its first check, and files each message by its thread's folder (each thread read once), as MillionSend does: a reply stays in its conversation's folder whatever its own spam verdict.
4. **Reading.** A message's id is `{thread}:{email}`, refused before it reaches a URL if it isn't two UUIDs. Search reads the inbox's thread search (MillionSend keeps bodies sealed, so only subjects, senders and recipients match). A line names the newest email that matched and describes that email, read when its thread has more than one message: the thread's own sender and date are its newest received mail's and its newest message's. A date-only `before` goes as the day before, since MillionSend's `end_date` takes in the day it names. Reading takes the plain part as sent, else MillionSend's `extracted_text` (hidden text removed), else the HTML as text. Folders, read state and the trash are the thread's there, so organizing one message moves its conversation, and the approval card and the move, mark, archive and trash tools say so. Attachments download only from MillionSend's own API. Held mail never comes out: MillionSend leaves it out of every list.
5. **Sending.** Replies and forwards go out in the thread, through the inbox's rules (MillionSend counts them as an agent's for any key). One the rules hold answers `202` with the draft: never reported as sent, the agent is told it waits in MillionSend's Needs review. The status decides, since a sent draft answers `200` with `object: "inbox_draft"` too. New mail goes out as the inbox through `POST /emails` (its address and sender name), where MillionSend runs the inbox's rules for any key: what they hold is refused there and leaves nothing behind, and the agent is told nothing was sent or saved and that a person can send it from MillionSend or change the inbox's rules. A reply draft written again updates the one MillionSend keeps per email. Our approval in the chat still comes first.
6. **Leaving.** Disconnecting deletes the webhook; deleting the workspace does too (`revokeGrants`, with the connectors' key wrappers). A key MillionSend refuses can delete nothing anymore, which counts as done. A delete that failed is done when the webhook next calls (3). A new key reconnects a mailbox that needs it, and makes the webhook the old key couldn't.
7. **Where to connect, said to the agent.** An agent that can't read any mailbox is told the web path (Settings › Connectors › Add connector › Email), the phone's (You › Connectors › MillionSend), each with its Portuguese, that a person does it, and that an inbox made at MillionSend isn't one here until connected. One that can read none of the connected ones is told where a person lets it (Who uses it). A mailbox the agent names is told apart the same way: not connected here (an inbox it just made at MillionSend, often), where a person connects it; connected but not its own, where a person lets it.
8. **The apps.** On the web and the desktop app, a MillionSend card in the Email group, MillionSend's own M (the connector's icon), its key step and the inbox, then the usual steps. A key that doesn't reach the inbox (another MillionSend team's) or a connector with no key says why, on the web and the phone. On the phone, an Email section in Conectores with the same card and a sheet of the same steps (what it does, the key and the inbox, its tools, who uses it); every connected mailbox is in the connected row (sign-ins still pending aren't), with who uses it and its tools.

## Considered and not chosen

- **Reading MillionSend through its MCP server with the connector's OAuth token:** its tools answer text for a model, not data, and never return a webhook secret.
- **A webhook per routine, like Composio's triggers:** MillionSend doesn't bill events, and a webhook per inbox is one row to keep and one to delete.
- **A column for the webhook:** the sealed JSON holds it with the key, and the route needs both.
- **Waiting with `GET /emails/receiving?wait=50`:** a held request per watched inbox on every replica.
- **New mail as a draft and its send (`POST /drafts/{id}/send`):** MillionSend counts a draft sent with a team-wide full access key, the key the screens ask for, as a person's approval, and skips every rule of the inbox (require approval, the send policy, the ramp, the loop and private-code guards, the daily cap).
- **Saving held new mail as a draft for a person:** MillionSend's screens list only drafts waiting for approval, which a team-wide key can't make, so it would wait where nobody sees it.
- **Reaching inboxes at `MILLIONSEND_API_URL`:** that is the transactional email's API, which a self-hoster may point at Resend, which has no inboxes and mustn't receive these keys.

## Consequences

- Self-hosted servers get it with no setting: `MILLIONSEND_INBOXES_API_URL` names the API (MillionSend Cloud by default, or a self-hosted MillionSend; `off` hides them), and a server MillionSend can't reach is polled.
- New mail the inbox's rules hold can't wait in Needs review: a person sends it from MillionSend or changes the rules.
- A message held by MillionSend and released after the poll's window reaches routines only through the webhook.
- A burst of more than 50 messages between two polls loses its oldest to the webhook alone.
- The catalog has two MillionSend cards, the connector (campaigns, contacts) and the mailbox (an inbox), told apart by their words.
