# 0123. Search filters

- Status: Accepted (built)
- Date: 2026-11-02
- Extends: ADR 0017 (search visibility), 0064 (the team's actions in search)
- Code: `packages/adapters/src/search.ts` (`MessageFilter`, `MESSAGE_HAS`, `after`/`before`, `sort`), `packages/engine/src/search.ts` (`searchForUser` with `channelIds` and `UserSearchFilters`), `apps/server/src/routes/app/knowledge.ts` (`GET …/search` filter parameters); client `lib/search-filters.ts` (parser, chips, API input, recent searches), `api/types.ts` (`SearchFilterInput`); web `components/search/SearchBox.tsx`, `HeaderSearch.tsx` (a DM's held to it: `inDmOnly`), `pages/SearchPage.tsx`, route `org.$orgId.search.tsx` (`?in=`); phone `features/search/SearchFilters.tsx`, `SearchScreen.tsx`; strings `searchPage.*`; migration `0177_search_filters.sql`

## Context

Search took words only: one box over the hybrid index (full-text and vectors, ADR 0017), grouped by kind. People asked for chat-app filters: who wrote it, where, what it has, who it mentions, when, newest or oldest first, and searching one conversation from its header. Some of that can't be words (a file, a pin), and a filter with no words ("everything Ada sent in #eng this week") must work too.

## Decision

1. **Filters live in the index's query, enforced where visibility is.** `SearchQuery` gains `after`/`before` (on the source's date), `messages` (a `MessageFilter`) and `sort`. Postgres checks a message filter with one `exists` on `messages` by the document's source id and its millisecond of `created_at` (so run-time pruning probes one partition; the document's date went through a JS Date and lost the microseconds); `pinned` first narrows to the pinned message ids: `from` (people's or agents' ids, any of them), `author` (person or agent), `mentions` (any of them, from `mentioned_user_ids`/`mentioned_agent_ids`), `has` (all of them: `link` = an `http(s)://` in the text, `file` = an attachment in `meta.artifacts` whose file isn't deleted, `image` = a GIF or sticker or an attached, not deleted file whose current version is `image/*`, `card` = a card's `meta` key), `pinned` (`message_pins`). A message filter searches message documents only.
2. **`in:` narrows visibility, never widens it.** The engine intersects the asked channels with the ones the person belongs to; an empty intersection returns nothing (not the whole workspace). Everything still passes `channel_ids <@ visible` in SQL, so no filter can reach a channel or DM the person can't read. Workspace-wide documents (wiki pages) are left out of a channel-scoped search.
3. **Sort.** `relevance` keeps the fused text and vector ranking. `newest`/`oldest` list full-text matches by date, or, with no words, everything the filters let through; no query embedding is paid for. A list by date is at most 100 hits (a "100+" count), no paging yet. Index `(org_id, kind, source_created_at)` (migration 0177) serves the by-date lists.
4. **API.** `GET …/search` takes `q` (now optional), `in`, `fromUsers`, `fromAgents`, `mentionsUsers`, `mentionsAgents` (comma-separated ids; malformed ids are a 400, never dropped, so a bad `in` can't turn into a whole-workspace search), `has`, `author`, `pinned`, `after`, `before` (ISO times) and `sort`. Hits carry `messageId` and `threadId`.
5. **Typed operators, one parser for web and phone** (`lib/search-filters.ts`). `from:@ana`, `in:#geral`, `in:"Ana Lima"` (a DM), `has:file`, `mentions:@dev`, `before:`/`after:`/`during:` with `YYYY`, `YYYY-MM` or `YYYY-MM-DD` (the person's local days; `after:` starts when that period ends, `during:` is the whole period), `author:agent`, `pinned:true`. English operator and value words work in every language; each language adds its own (`searchPage.words`, pt-BR `de:`, `em:`, `tem:arquivo`). Matching ignores case and accents. An operator whose value names nothing known stays as words. One chip per date operator and author type (the last wins).
6. **Web.** The box holds the chips; a space or Enter turns a complete operator into a chip, Backspace on an empty box removes the last. Empty and focused, it lists the operators (first four, then "Mais filtros") and the recent searches with Limpar; typing an operator opens its picker (people and agents with their faces, channels and DMs, kinds, a date field). Results: count, the filters with a way to clear them, sort, hits grouped by channel; a hit opens at the message (`?m=`): a channel's in the channel, a DM's in the DM route, a thread reply in its thread. The box's options and recent searches are picked with the arrows and Enter. Opened from a header, the `in:` chip is added once; removing it sticks. Without chips the old kind tabs stay (actions, messages, context). Every channel and DM header has a search button that opens the page with an `in:` chip.
7. **Phone.** The search tab reads the same operators: chips under the field, the picker while an operator is typed (faces, conversations, kinds; dates typed), the operators and recent searches while empty, and with chips the messages by conversation with the sort (relevance with words, newest without, as on the web), loading and error states and a way to clear the filters; a tap opens the conversation (a reply its thread) scrolled to the message when it is among the loaded ones.
8. **Recent searches stay on the device**, per person and workspace (web `localStorage` under the user and workspace ids; phone SecureStore by workspace, cleared at sign-out), written back with English operators so they read the same in any language. Nothing about searches reaches the server beyond the search itself.

## Consequences

- A future search backend must honour `messages`, `after`, `before` and `sort`; the visibility rule is unchanged.
- No paging past 100 hits by date; add a cursor (`source_created_at`, id) when people ask for it.
- `has:link` reads the text (a link a card shows without text in the body isn't found); the phone scrolls to a hit only when it is in the loaded pages (an older one opens at the end).
