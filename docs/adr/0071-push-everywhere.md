# 0071. Push in browsers: Web Push with the server's own key

- Status: Proposed
- Date: 2026-10-27
- Code: `packages/adapters/src/web-push.ts`, `packages/engine/src/push.ts`, `packages/engine/src/web-push.ts`, `apps/server/src/routes/app/push.ts`, `apps/server/src/start.ts` (`webPushSender`), `apps/web/public/sw.js`, `apps/web/src/lib/web-push.ts`, `apps/web/src/lib/push-open.ts`; the island (§9): `packages/client/src/lib/island.ts`, `apps/web/src/components/NoticeIsland.tsx`, `apps/mobile/src/features/island/NoticeIsland.tsx`
- Extends: ADR 0035 §4

## Context

ADR 0035 gave the phone app push through the Expo Push API. Browsers get nothing while the tab is closed. The desktop app already shows its own notifications through its realtime connection while it runs, even with its window closed (ADR 0066), so it doesn't need push. The self-hosted server must keep working with nothing but Postgres and no account anywhere.

Phone push changes (sending straight to Firebase and Apple, a push relay for self-hosted servers, sealed phone pushes, taking phone notifications down when read elsewhere) are left for a later revision of this record.

## Decision

1. **Browsers use Web Push (RFC 8030) with VAPID (RFC 8292).** The server makes its own P-256 key pair the first time it needs one and keeps it in `instance_push`, the private key sealed with the installation's key. `WEB_PUSH_VAPID_PUBLIC_KEY` and `WEB_PUSH_VAPID_PRIVATE_KEY` pin a pair (the server refuses to start with halves of two pairs); `WEB_PUSH=off` turns it off. No account with any push service is needed: Chrome, Firefox, Edge and Safari accept this standard as it is. The payload is encrypted to the browser (RFC 8291), so the browser's push service sees only ciphertext; browsers always get the full text.
   - **The contact is one push services take.** The JWT's `sub` is `PUBLIC_URL` when it is https on a public name, else `mailto:` the `EMAIL_FROM` address when its domain is public, else the project's site: never `http:` or a local name (`localhost`, a LAN name), which push services refuse, so a server tried on one computer or reached over Tailscale still gets its pushes through.
   - **A stored key is replaced only when it can never be opened** (another `AGENTES_SECRET`: the local key fails to authenticate it). A key service that doesn't answer, or a key wrapper the process lacks, is an error to retry; a pair another server made in the last 10 minutes is never replaced either, so two servers with different secrets can't take turns wiping every subscription. Each process re-reads the row every minute, so all of them sign with the same pair.
2. **A browser is a push device like a phone.** `push_devices.platform` gains `web`; the subscription's endpoint is the `token` and its keys go in `web_keys`. The same route registers it, `POST /api/app/push/devices/forget` forgets it (the endpoint in the body: its encoded slashes in a path don't survive every proxy), and the same rule (`PUSH_KINDS`, `pushWorthy`, once per group) decides what pushes. A 404 or 410 from the push service deletes the subscription. A 401 or 403 (the signature refused) keeps it: a subscription made for a replaced key answers so, but so does every subscription when the server's own key or contact is wrong, and deleting on it would wipe every browser over a setting; the server logs it, and the page subscribes again with a new key on its next load. Endpoints on our own network are refused and dropped, as for every address a person gives the server; DNS that doesn't answer is a failure to retry, never a reason to drop one. The page's service worker (`/sw.js`) only shows notifications and opens them; it caches nothing.
3. **The page asks once, on a click.** "Notifications in this browser" is a switch in the account menu, next to the theme, the language and the sounds. Since nobody finds a switch they aren't looking for, a dialog of ours comes first, as the phone app's sheet does (`WebPushAsk`, rules shared in `@agenteschat/client/lib/push-offer`): three example notifications, "Ativar avisos" (the browser's prompt, from that click) and "Agora não", opened by itself once when the workspace has agents and once more at the first request waiting on the person, never over someone typing nor in a focused flow (the web's home is a channel); using the switch ends it. A prompt the browser keeps quiet (Chrome's crossed-out bell) says where to allow it. Never the browser's prompt on load, never inside the desktop app (it has its own), and not in Safari on iPhone or iPad unless the site is installed (the phone app exists). The page refreshes its subscription on each load, so the server keeps it and moves it to whoever is signed in.
   - **A browser belongs to the session that turned it on** (`push_devices.session_id`, deleted with the session). Signing out there or everywhere, a password reset or the session running out stops its pushes, which matters on a computer people share; signing in there again subscribes it anew. Phones keep ADR 0035's rule until its revision.
4. **A click opens the notification itself.** The push carries the notification's id and its deep link data; a click opens it where the inbox would (`useNotificationOpener`), in an open tab of the app when there is one, else in a new one at the inbox.
5. **No push for what the person is looking at.** A push that isn't waiting on the person waits 45 seconds while they have the app open somewhere, and then goes only if it is still unread. What waits on them (an approval, a question) goes at once. This applies to phones too. While a window of the app is focused, the service worker shows the notification silently and closes it at once: a push that shows nothing makes Safari end the subscription and Chrome show its own notice.
6. **Read in the app, gone from the browser.** What is read, done or snoozed in an open tab closes the browser notifications it still shows for it; a page coming back to the foreground asks `POST /api/app/push/stale` with the ids it shows and takes down what it returns.
7. **An agent's answer tells the person who asked.** Asking an agent and closing the tab is the common case, and nothing told them it was done: its replies in a DM were "the conversation itself", and in a channel or thread nobody heard them. Now an agent's message to the person behind its run (`humanBehindRun`; not a routine's, not one they stopped, not when it mentions them) is an `agent_reply` notification, one per conversation (`agentReplyGroup`) that later answers merge into, so it pushes once until read, on phones, browsers and the desktop app. Reading the conversation resolves it (`markChannelRead`), and the web marks a conversation read only while its tab is in view, so an answer arriving in a background tab still pushes.
8. **Each person chooses what notifies them.** Notification kinds come in eight categories a person reads (`notice-prefs.ts`: waiting on you, agents' replies, mentions and DMs, threads, tasks, routines and missions, computers, reactions), each on or off per person in each workspace (`organization_members.notice_prefs`, only the categories changed are stored; the defaults are what pushed before: threads, tasks and reactions off). They decide the pushes to phones and browsers (`pushWorthy`) and the desktop app's banners (the realtime event's `alert`); the inbox keeps everything either way. Anything waiting on the person is `waiting`, whatever its kind. The web shows them in Configurações › Notificações, a "Você" group above the workspace's own sections, with where they arrive (this browser's switch, whether a phone gets them, the Mac app); the phone app in Você › Notificações, under its own switch (dimmed while it is off: they still decide the other devices); `GET`/`PUT /api/app/organizations/{orgId}/notification-prefs`.
9. **While the app is open, notifications show in the island.** Push is for when the app is away; in front of it the web showed only a toast for the budget, and the phone the system's banner, with nothing to do in it. Now what reaches the person (a `notification.upserted` they keep on, `alert`, point 8) shows in one dark pill at the top of the screen: over the work area on the web and in the desktop app, growing out of the camera's island on iPhones that have one (dropping from the top elsewhere). It has the face of whoever called and the line; resting the pointer on it or a tap opens it with the whole text and the answer right there: reply (`useNotificationReply`), an agent's suggested answers, "Revisar" for an approval (its dialog on the web, its sheet on the phone, where approving keeps its hold), "Abrir". What isn't waiting on the person leaves after 6.5 seconds (time stops while it is looked at or an answer is typed); what is (an approval, a question, a browser) shrinks and stays until decided. Swiping it up, or Esc, puts it away. The rules live in one place, `@agenteschat/client/lib/island` (`raisesIsland`, `createIsland`); each app draws it its own way.
   - **Nothing for the conversation on screen**, whether a channel, a DM or one of its threads (the web's `holdOnScreen`, the phone's `holdOpenConversation`): its message already shows there. On the web only a tab in view shows it; a tab in the background has the browser's notification (points 4 and 5).
   - **Whatever leaves the island stays in the inbox**, unread unless it was answered or opened there. What is read, done or snoozed elsewhere leaves it.
   - **On the phone it replaces the banner while the socket is live** (`setIslandLive`), so nothing shows twice; with the socket down the system's banner is still there.

## Consequences

- Browser push works on any self-hosted server with no setup and no third party besides the browser's own push service, which can't read it. That service sees the server's public key and its contact (point 1).
- Changing `AGENTES_SECRET` (or the pinned pair) makes a new key: push services refuse the old subscriptions until each page subscribes again on its next load; those never opened again go when their session ends.
- A browser where nobody opens the app while its session lasts (a week unused, Better Auth's default) stops getting pushes until someone signs in there again.
- A browser's notifications aren't taken down while no tab of the app is open; they are the next time one is.
- The desktop app's own notifications aren't taken down when read elsewhere.
- Left for later: phone push without Expo and through a relay for self-hosted servers, sealed phone pushes, clear on read for phones, a manifest so the site installs on iPhone.
