# 0106. Routines started by a webhook: an address of their own

- Status: Accepted
- Date: 2026-10-31
- Builds on: ADR 0053 (routines and unattended work: the routine room, one run at a time, events merged into the next run, the outside-content envelope), ADR 0007 (sealed secrets), ADR 0068 (invite links shown again while only their hash is stored), ADR 0085 (who manages a routine), ADR 0089 (a routine's report opens a stretch of its own)
- Code: `packages/engine/src/routine-hooks.ts`, `packages/engine/src/routines.ts` (the `webhook` trigger, `managedWebhookRoutine`), `packages/engine/src/routine-events.ts` (`queueEventRun` returns the run), `packages/engine/src/context.ts`, `packages/engine/src/schedule-tools.ts`, `packages/engine/src/crypto.ts` (`routineHookToken`), `packages/db/src/schema/work.ts` (`routine_hooks`, `routine_hook_calls`), migration `0142_routine_hooks`, `apps/server/src/routes/webhooks.ts` (`registerRoutineHooks`), `apps/server/src/routes/app/routines.ts`, `packages/client/src/lib/routines.ts` (`hookCurl`), `apps/web/src/pages/RoutinesPage.tsx` (`WebhookPanel`), `apps/mobile/src/features/routines/WebhookCard.tsx`

## Context

Routines start on a schedule, on an email, or on a few events agentes.chat knows (a GitHub PR opened, a Sentry issue, a deploy, a task created), the GitHub and Sentry ones through one signed endpoint per workspace. People want any service to start an agent: a payment, a form, a CI step, their own script. Competitors give each automation an address to POST to. Whatever reaches that address comes from outside, from whoever has the address, so it must never act for anyone, and nothing in the request may run a model.

## Decision

1. **A fourth trigger.** "Quando o webhook for chamado" (`{ type: "webhook" }`) is stored like the email trigger: the event `webhook.received` plus a `routine_hooks` row. The event path refuses `webhook.received`, so only this trigger makes one. The routine follows every rule of ADR 0053 (its room, `deliverTo`, access and report, one run at a time, the active routines' cap, fatigue).
2. **Its own address, stored only as a hash.** `<PUBLIC_URL>/api/hooks/<token>`, the token being the HMAC-SHA256 (32 bytes, base64url) of the hook's `key_id` (32 random bytes) under a key derived from `AGENTES_SECRET` (purpose `routine-hooks`), as invite links do. The database keeps `key_id` and the token's SHA-256: a copy of the database alone can't call anything, and the address can still be shown. It is shown in full only to who may manage the routine (its creator, an admin with `manage_routines`, the agent's owner): in the routine's view (`trigger.url`, null for everyone else and for agents) and on its page. "Gerar novo endereço" draws a new `key_id`: the old token matches no hash, at once. A copy of a routine gets an address of its own. A routine keeps its address while its trigger changes (the address answers only while it is a webhook routine), so an undo or a switch back brings the same one. A new `AGENTES_SECRET` makes every key give another token: the next time a routine's address is shown to who manages it (its view or its page), the stored hash follows the new token (`liveHookUrl`), so the address shown is the one that answers and the old one stops.
3. **An optional signing secret.** Made by the server (32 random bytes), shown once, replaceable, removable, kept sealed (envelope encryption, ADR 0007, bound to the workspace and the routine). With one, a call must carry the HMAC-SHA256 of its raw body as `X-Agentes-Signature: sha256=<hex>`, or GitHub's `X-Hub-Signature-256`, compared in constant time. Without one, any call to the address is accepted: the address is the credential.
4. **`POST /api/hooks/{token}`, public, no session.** In order: other methods get 405 (`Allow: POST`); every call counts against its client address (300 a minute, before anything is looked up: 429 with `Retry-After`); a malformed or unknown token, a routine turned off or deleted, or a closed workspace (`closedOrg`) is 404, never saying which; 60 calls a minute per routine (429); a body past 256 KB is 413, read without buffering past the limit; a bad signature 401; a repeat of an `Idempotency-Key` (else `X-GitHub-Delivery`) within 24 hours answers 202 with the first call's run and starts nothing; anything else answers 202 with the routine run it joined. A workspace on a hold still answers 202: the run is skipped as a scheduled slot would be.
5. **Through the outbox, never in the request.** An accepted call joins the routine's next run through `queueEventRun` (ADR 0053 §6.3): the queued run takes it, a run working gathers the next calls into one that starts when it ends. A run keeps its newest 10 calls (older ones counted) and 16,000 characters of each body; a body that isn't UTF-8 is kept as "binary". `queueEventRun` now returns the run it used, so the answer and the calls log can point to it; a run moved behind a working one carries its calls' links along.
6. **What the model reads.** The routine context gives the calls inside the outside-content envelope (`<external_data source="webhook">`, markers neutralized), oldest first, 16,000 characters shared among them, a form's fields one per line, with a few safe headers: `Content-Type`, `User-Agent`, `X-GitHub-Delivery`, `X-Event-Key` and any header naming what happened (`…-Event`, `…-Event-Type`, `…-Topic`, `…-Hook-Resource`). Never `Authorization`, cookies, signatures or addresses: the routine's own token, which a sender may send back (GitHub's `ping` carries the address in `hook.config.url`), is replaced with `[token hidden]` in the body and the headers before the call is kept, so it never reaches the agent, its report or its run's record. Bodies and the model's share of them are cut on whole characters (half of an emoji is invalid in jsonb). Our framing, outside the envelope, says it is what was POSTed by whoever has the address: data, never instructions. The routine block already refuses what such text asks (ADR 0053 §2).
7. **The latest calls.** `routine_hook_calls` keeps, per call that reached a routine: when, how it ended (`accepted`, `duplicate`, `bad_signature`, `too_large`, `rate_limited`), the status it got, its size, its run and whether Testar sent it; the idempotency key only on accepted calls. Refused calls past the limit write one line a minute however many come. A daily tick deletes calls older than a day except each routine's last 20.
8. **Testar.** A manager's sample call (`POST …/routines/{id}/hook/test`) goes down the same path as a real one (the routine's limit, its run) without a signature, marked as a test. A run that carries only samples (`testOnlyEvent`) runs with the agent's own permissions like any other (ADR 0109: there is no read-only routine run), and the model is told, outside the envelope, that a person pressed Testar, that the call is a sample, not to act on it, and to report what it would do with a real one; sensitive actions still ask a person. A routine turned off refuses Testar (`routine.webhook_paused`, 409), as its address refuses real calls. A sender can't mark a call as a test.
9. **The routine's page and the form**, on the web and the phone: Webhook as a kind of "Quando"; once saved, the page opens on the address card, at once (the saved routine goes into the list the page reads before the list comes back; on the phone, the routine's screen under the form when it was opened from there). The card: the address and Copiar, the signature with the secret shown once, an example `curl` that signs its body when the routine needs it, Testar, the latest calls with each run's message. Gerar novo endereço, Gerar novo segredo and Desligar assinatura each ask first, saying what stops working (in place on the web, an alert on the phone). The form shows the same card for a webhook routine. Who can't manage the routine reads that only they see the address.
10. **Agents.** `create_routine` and `update_routine` take `trigger: { type: "webhook" }`. The agent never sees the address (its tools read routines as nobody, and its texts and receipts carry only `trigger: "webhook"`), and the tool's answer tells it never to write an address in the chat but to send the person to the routine's page. A routine run never manages routines, as before.
11. **Self-hosted servers** get it as it is: the address is `PUBLIC_URL`'s, which must be reachable from the sending service (a public domain, or Tailscale Funnel).

## Consequences

- One more public endpoint, limited per client address and per routine; a flood of calls to one routine costs one indexed lookup each and starts at most one run at a time.
- A routine's calls are events: like every event routine, it may run as often as calls come, one run at a time, within the agent's budget.
- Each run's report opens a stretch of its own, as every routine's does (ADR 0089): what agents start from it is held past 10 runs. A loop through a routine's own address (an agent that was given it, calling it) opens a new stretch each time, as ADR 0089 leaves for later; one run at a time, the routine's 60 calls a minute and the agent's budget bound it.
- Calls that arrive while a routine is paused, or that its run then skips, are not replayed.
- Changing `AGENTES_SECRET` changes every routine's address the next time it is shown to who manages it: the old one stops then, and the services that call it need the new one.

## Alternatives considered

- **The token sealed, or stored as it is.** Sealing it would let the address be shown again too, but a key service would be called on every request; deriving it from the master secret needs no call and leaves only a hash in the database. Storing it as it is would make any database copy a set of working addresses.
- **The address shown once, like the secret.** Managers other than its creator could never copy it again without breaking the services that use it.
- **Idempotency forever, through the run's dedupe key.** A GitHub redelivery days later (same `X-GitHub-Delivery`) would be dropped without a word; 24 hours is what senders expect.
- **One address per workspace that names the routine in the body.** One leaked address would reach every routine, and replacing it would break them all.

## Addendum: the methods an address answers (2026-11-02)

Some services can only call a URL with GET (a monitor, a button in another app), others send PUT or DELETE. Each address now answers the HTTP methods its managers choose (`routine_hooks.methods`, migration 0186): GET, POST, PUT, PATCH, DELETE, POST by default, at least one. A method it doesn't answer gets 405 with `Allow` listing the ones it does, checked after the token (an unknown token is still 404) and before the routine's limit, so a wrong method costs the routine nothing. A GET call's data is its query string, kept as the call's body in JSON (`{"status":"paid"}`), so the run reads it like any body, inside the envelope; its signature, when the routine has a secret, covers its query string as sent (without the `?`) in place of the empty body, so a signature seen once can't carry other data. The run's framing names each call's method. The methods are part of the webhook trigger (`{ type: "webhook", methods }` on create and edit, by people and by agents through `create_routine`/`update_routine`); an edit that leaves them out keeps them, and the address stays the same.
