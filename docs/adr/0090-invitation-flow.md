# 0090. Bringing a teammate in: a link asks with a password, invitations keep their link

- Status: Accepted (built: the server, the shared client, the web and the phone app)
- Date: 2026-10-31
- Revises: ADR 0068 §4 and §5 (an approval also makes the account a proven ask chose a password for), ADR 0072 §2 and §6 (for an address with no account, the code that proved the request is what confirms the new account)
- Code: `packages/engine/src/invite-requests.ts` (`askToJoin`, `approveJoinRequest`, `claimJoinRequest`, `suggestPerson`, `listMySuggestions`, `cancelSuggestion`, `renewInviteLink`, `noticeInvitationAccepted`), `packages/engine/src/organizations.ts` (`sendInvitation`, `createInvitation`, `inviteMany`, `invitableChannelIds`, `setInvitationRoles`, `resendInvitation`, `listInvitationsWithStatus`, `previewInvitation`, `invitationState`, `acceptInvitation`, `holdsInvitation`, `spentClaimHash`), `packages/engine/src/crypto.ts` (`invitationToken`), `packages/engine/src/email.ts` (`queueInvitationEmail`), `apps/server/src/auth.ts` (`hashPassword`, `mintUserSignIn`), `apps/server/src/routes/app/invites.ts`, `management.ts`, `account.ts`, `packages/db/migrations/0139_invitation_flow.sql`; the screens: `apps/web/src/pages/InvitePage.tsx`, `apps/web/src/pages/MembersPage.tsx`, `apps/web/src/components/invite/` (the invite dialog, the address chips shared with the onboarding, the link panel, the arrival card), `apps/web/src/components/WelcomeCard.tsx`

## Context

Bringing someone into a workspace took too many steps and had dead ends:

- Through the workspace's link (ADR 0068, 0072) a person typed a name, an email and a code on one screen, asked, waited, then got a second email ("Approved: one step left") with a new 7-day invitation, typed their name again, chose a password, and got a "confirm your email" message for an address they had proven twice. The password came last, after approval.
- An email invitation's link changed every time it was sent again, so the copy in the person's inbox stopped working, and the Members list could copy a link only right after sending it.
- Pasting addresses from a mail app (`Ana <ana@x.com>`) made invitations nobody could accept.
- A dead invitation link said "expired" whatever happened to it, and an invitation to a paused or full workspace let a person make an account before refusing them.
- Invitations added people to #general only, with no word from the inviter; the inviter never heard that someone joined; members who couldn't invite had no way to bring anyone.

## Decision

1. **A link asks with a password.** Signed out on a server that sends email, the page asks one thing per screen: the email, the code from it (on a screen of its own), the name, a password, an optional note. The ask (`POST /invitations/{token}/requests`) carries `password`; the server hashes it as Better Auth does (`hashPassword`) and keeps the hash on the request (`organization_join_requests.password_hash`). No account exists until someone approves: a link still never signs anyone up (ADR 0068 §5).
2. **Approval makes the account.** Approving a proven request for an address with no account makes it (`makeAskedAccount`): that address, confirmed, with the name and the password the person chose, written as Better Auth writes one, then the sign-up hooks' work (`onUserCreated`, `user.signed_up`). It joins at once and is told by email ("You're in", with a link that opens the workspace). The hash goes from the request into the account, and from the request when it is denied, closes, runs out (the daily tick) or its link is turned off. An account someone made for the address while the approval ran (a sign-up a moment before) is never written over: the approval takes it as an account that was already there. An address that already has an account keeps ADR 0072's path: a confirmed one joins and signs in as always, an unconfirmed one gets an email invitation. This is the one place a code confirms an account (ADR 0072 §2 keeps it from confirming an existing one): the new account is the request's, the address was proven by its mailbox, and an admin approved the person.
3. **The page that asked signs in.** The ask answers a `key` (`{requestId}.{secret}`, only the secret's sha256 kept as `claim_hash`). The page checks every 15 s (`POST …/requests/claim`): `pending`, `in` once, for an account the approval made (a one-time sign-in the page trades at `/api/auth/sign-in/one-time-token`, as the phone's, after which the key is spent), `denied` with the reason, or `closed`. A key that can sign in no one is spent, not dropped, so its page still reads `closed` instead of waiting on: it is kept marked (`spentClaimHash`, `spent:` and the hash of its hash), which no key's hash can equal, so even someone who saw the live hash can't hand it in. An approval that made no account spends the key, whoever the request names (a page that took over an account's request included): no page signs in to an account that was already there. Trading it for the sign-in spends it, and so does joining another way (an email invitation accepted meanwhile), which closes the request and drops its password. A key works for a day after the answer (the page checks every 15 s while open); the daily tick then forgets it, and it matches nothing.
4. **Invitations keep their link.** An email invitation's token is an HMAC of its id under `AGENTES_SECRET` (`invitationToken`, as the workspace's link, ADR 0068 §9), so the Members list copies it at any time and sending it again keeps it, only with 7 more days. A link that leaked is therefore stopped by cancelling the invitation and inviting again (a new invitation, a new link), not by sending it again. An invitation sent before this gets a derived link the next time it is sent. The invitation email's key is per sending (its expiry), so sending again sends again.
5. **One dialog invites,** a step at a time, the workspace's first agent asking each one as on the invitation page: addresses as chips, read the way mail apps and spreadsheets paste them (`addressesIn`); their role, the same for all or one each; channels they also join (`channel_ids`: the workspace's own, not archived, public or one the sender is in, else `invitation.channel`; a private one is joined on accepting only while the sender is still in it, so leaving it, or the workspace, takes it back); a note in the email (`note`, made inert like any typed text; subjects keep only fixed words), shown in the email as it arrives; then what became of each address. The workspace's link is a screen of its own, the only one on a server that sends no email. The batch takes exactly one of `invites` (each address with its roles) or `emails` with one set of roles as before. The roles of a pending invitation change without sending it (`PATCH …/invitations/{id}`), only while it still works and the workspace may invite, and a link gets 30 more days without changing (`POST …/invite-links/{id}/renew`).
6. **The invite page asks only what is missing.** The preview says how the invited address signs in (`account`: an account, a password, which social sign-ins) and whether the workspace is full (`full`), and an invitation to a paused workspace reads as closed, all before anyone makes an account. A dead email invitation says what happened (`GET /invitations/{token}/state`: accepted, with the workspace to open, or expired, with who to ask); a cancelled one says only that it doesn't work, as one that never existed. The token alone proves no mailbox: admins see and copy the link (§4), and whoever they hand it to can open it. So the invitation's own email adds what only the message carries: its link is the copyable one plus `?mail=`, an HMAC of the invitation's id under its own purpose of `AGENTES_SECRET` (`invitationMailProof`), and the join answer of an approved ask carries the same. Accepting with it (`POST …/accept?mail=`) confirms the address; accepting with the link alone joins the workspace and confirms nothing. Likewise a sign-up sends no "confirm your email" only when it carries both, the token in `x-invitation-token` and the proof in `x-invitation-mail` on `POST /api/auth/sign-up/email`, for an invitation to that same address that can still be accepted (`holdsInvitation`). Any other sign-up of an invited address, a copied link's included, gets the message as always: otherwise anyone with a copied link could hold a confirmed account at someone else's address, which a Cloud workspace's creation trusts.
7. **Members suggest.** A member who may not invite suggests someone (`POST …/join-requests/suggest`): a request with no link and no proof, from them (`suggested_by_user_id`), that the people who may invite answer as any other. Its notice says who suggested whom (`latest.suggestedBy`), not that the person asks, and its author sees their suggestions waiting and can take one back. Nobody at that address asked, so it gets no answer: approving it sends the email invitation itself, denying it sends nothing, and a denied suggestion isn't the person's (it doesn't keep them from asking through a link, nor shows on that page). Suggestions wait apart from the asks, so neither crowds out the other: at most 20 in a workspace and 5 from one member (`join.full`), besides the 50 asks. A person who asks through the link while a suggestion for them waits makes it their own ask: answered to them, and their page signs in.
8. **The inviter hears who joined.** Accepting an email invitation leaves its sender a notice (`invitation_accepted`, the person as actor) that opens a conversation with them. Inbox only: no category, so no push.

## Consequences

- An account can now be made without Better Auth's sign-up endpoint, by an approval: its policy gate (`isSignupAllowed`) doesn't run, on purpose, as an invitation's doesn't.
- A guessed code (ADR 0072's limits: 5 tries a code, 10 wrong a day per address) plus an admin's approval would make an account for someone else's address. The approval is the second check: admins see the address and the note before saying yes.
- Phone builds from before this ask without a password and get ADR 0072's invitation after approval, as before; the batch still takes `emails`.
- Links already emailed before this keep working until sent again, when they change once.
- Someone who accepts through a copied link gets the usual "confirm your email" and confirms there. Phone builds from before this pass no proof on, so the same goes for them.
- On the phone, Members is one page (`apps/mobile/src/features/members/MembersPage.tsx`) and opens for everyone, so a member can suggest someone; inviting is a pushed screen (`InvitePeople.tsx`), and the steps of a link and of an email invitation live in `apps/mobile/src/features/auth/` (`LinkSteps.tsx`, `AskWaiting.tsx`, `EmailSteps.tsx`). A phone keeps one waiting request at a time: asking through another link replaces the wait, and the first account's password still works once it's approved.

## Alternatives considered

- Making the account when the person asks: the link would open sign-up again (ADR 0068 rejected it), and every leaked link would leave accounts behind.
- Keeping the password for after approval, without asking the name again: one more email and one more visit for every person, which is what this replaces.
- Signing an existing account in from the page that asked: the code would then sign in to accounts it never made.
