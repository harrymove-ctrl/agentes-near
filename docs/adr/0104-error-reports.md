# 0104. Error reports to a Sentry-compatible server

- Status: Accepted (built: the server, the web app, the desktop app and, since 2026-11-07, the phone app's JavaScript)
- Date: 2026-10-31
- Code: `packages/adapters/src/error-reports.ts` (the reporter), `packages/adapters/src/error-scrub.ts` (what a report may carry), `apps/server/src/logger.ts`, `apps/server/src/start.ts`, `apps/server/src/workers.ts` (`logJobFailure`), `packages/engine/src/outbox.ts` (`JobContext.failed`), `apps/server/src/auth.ts` (`onAPIError`), `apps/server/src/realtime/ws.ts`, `apps/server/src/http/errors.ts` (`routeOf`, `isExpectedError`), `apps/web/src/lib/error-reports.ts`, `apps/web/src/lib/error-sdk.ts`, `apps/web/src/components/ErrorScreen.tsx`, `deploy/deploy.sh`

## Context

An error people hit was seen in the server's log at best. A web page that broke showed the router's own "Something went wrong!" screen with the raw error, and nothing reached whoever runs the server. A run that kept failing gave up on its last attempt without throwing, and a sign-up hook that failed only wrote a line. agentes.chat Cloud wants each of these seen at once, and a self-hoster may want the same with a server of their own. The server is AGPL with no contributor license agreement, so Cloud-only behavior is public code switched on by env vars (ADR 0002).

## Decision

1. **Sentry's SDKs and protocol, to any Sentry-compatible server, off by default.** `SENTRY_DSN` is the server's, `SENTRY_WEB_DSN` the web and desktop apps' (handed to browsers in `auth-config`'s `errorReports`, public like any browser DSN), `SENTRY_ENVIRONMENT` their environment (`production` by default). Without a DSN nothing is sent and the SDK is never loaded: the server imports `@sentry/core`, and the web app loads `@sentry/browser`, only then.
2. **Errors only.** No traces sampled, no sessions, no replays, no profiling. The SDK drops a report repeated back to back and holds reports back while the server rate-limits.
3. **What a report carries** (`scrubEvent` and `scrubBreadcrumb`, which every SDK applies before sending): the error and its stack, its causes included, the release, the environment, the route as a pattern, the request id, the HTTP method and status, a job's kind and attempt, internal ids as tags (`org_id`, `user_id`, `agent_id`, `run_id`, `machine_id`), and breadcrumbs reduced to where a request or a navigation went and how it ended. Never emails, names, IP addresses, cookies, auth headers, request or response bodies, message or mail content, tool inputs or outputs, prompts, model output, file contents, keys or tokens. `sendDefaultPii` is off, the user is its id alone, a request keeps its method, its URL as a pattern and its user agent, console lines are dropped, and free text (an exception's message, a breadcrumb, a tag) has emails, IP addresses (IPv6 in any form), JWTs, bearer and basic credentials, known key shapes and long tokens masked. A failed query's message keeps its SQL and never its values (Drizzle puts them after `params:`). A path's pattern has its ids, its tokens and the names people chose (the segment after `wiki`, `pages`, `files` and `secrets`: a wiki page's slug, a skill file's path, a secret's name) as `:id`. Internal ids are pseudonymous, and needed to find a case: the id tags are kept as they are (a person's id is 32 random characters, which the token mask would take).
4. **The server reports what it logs as an error.** `createLogger(level, errors)`: an error line that carries what was thrown (`error`) is reported, tagged with its id fields. That covers unhandled exceptions and rejections (marked unhandled), a boot that fails (reported before the process ends), the HTTP app's and the operator API's 500s (with the pattern `routeOf` reads and the request id also sent as `X-Request-Id`), Better Auth's own 500s (sign-up, sign-in, OAuth callbacks, password reset), which it answers itself (`onAPIError`), a WebSocket upgrade that fails, socket handlers that fail (with whose socket it was), background loops, sign-up hooks and a shutdown that fails. Every failed attempt of an outbox job is an error line with its kind, attempt and ids, never its payload, except a worker handing it back, an expected refusal (what `domainErrorResponse` answers: a 4xx, a computer that can't take it now) and a failure its code marks transient that will be tried again. One that runs out of attempts is reported, transient or not. A handler that gives up without throwing says so (`JobContext.failed`) and is reported as a failed job: a run on its last attempt (`gave_up`), and a run whose request the provider rejected, unless the refusal is the account's own (401, 402, 403, 429: its key, credit, access, quota), which the person sees. So is a job whose lease ran out on its last attempt: its worker died or hung on it. A request Hono refuses (a body that isn't the JSON it claims to be) is a 400, not an error. Reports on their way get 2 s before the process exits.
5. **The web app.** The root route's error component is the product's own screen (`ErrorScreen`): a short message, Recarregar, and the first 8 characters of its report's id ("Se pedir ajuda, informe o código …"), which is also the report's `error_id` tag, once the report is on its way (the SDK took it, past its own dedupe, in `beforeSend`). Without reports, or before the server said where they go, there is no code. In the desktop app it lifts the app's cover, as the root does: a first screen that breaks never mounts the root. React's root reports what its boundaries caught and what none did, the SDK reports the page's errors and unhandled rejections, and errors from before `auth-config` answered wait for it, 20 at most. Reports carry the route's pattern (`/org/$orgId/c/$channelId`) and the ids of the workspace and the person. The desktop app shows the server's web app, so it reports the same way.
6. **The release is `APP_VERSION`, else the server's package version**, also `version` in `/api/instance` and `/api/health`. `deploy/deploy.sh SHA VERSION` sets it in the image (`ENV APP_VERSION`), so a rollback to that image, or a restart by hand, keeps its version. Without one it deploys as before. A date version reads `2026.10.31.4`: the UTC date and the deploy's count that day.
7. **Not the phone app.** `@sentry/react-native` depends on `@sentry/cli`, which is FSL-1.1 (source-available), and `check:licenses` allows no such license.

## Consequences

- A self-hosted server reports nothing unless its owner sets a DSN, and then only to the server they chose. SELF_HOSTING.md says what is sent and what never is.
- Browsers send their reports straight to the DSN's server, which sees their addresses as any server they reach does.
- The web app's stacks stay minified unless that server reads the source maps the build serves. Uploading them would take a token at deploy.
- The first deploy with this change runs without a version: the script already on the server hands over to the new one without passing it.

## Alternatives considered

- Reporting from the private Cloud repository only: nothing private runs in the server process (ADR 0002 §5), and the web app is built here.
- `@sentry/bun` or `@sentry/node`: OpenTelemetry instrumentation and request data to strip again. `@sentry/core` with a fetch transport is the SDK without them.
- Reporting every warning: noise. An error line is where the code already says something went wrong.
- Reporting only a job's last failure: one that is not transient would be seen hours later, after up to 8 attempts and their backoff.
- The phone app with Sentry's SDK on JavaScript alone (`@sentry/core`): no native crashes, and the SDK the platform documents is the one above.

## Addendum (2026-11-02): learning's failures

Learning (ADR 0120) fails where nothing logs an error: the turn-end judgment asks again without its `learn` question, the `context.learn` job's model call is refused, or queueing the job fails. These go to the reporter directly (`reportLearnFailure`, `ContextDeps.errors`), tagged `cause` (`judge_learn_question`, `learn_call`, `learn_queue`), `org_id`, `agent_id`, `run_id` and the call that failed, never with what the conversation said. The learning call names its `provider`, `model` and `account` (`plan_sign_in` or `api_key`). The judge's names `judge` and the model call it made (`judge_provider`, `judge_model`, which the judge puts on the error it throws: with Jev on and failing, the error reported is the fallback's), and the agent it judged sits apart as `agent_brain`, `agent_provider`, `agent_model` and `agent_account`, so a plan sign-in that was never part of the failing call isn't mistaken for it. At most one report per workspace and cause an hour, held in each process's memory, so a broken provider can't flood the server. A rate limit or an overload on the learning call isn't reported: the outbox tries it again.

## Addendum (2026-11-07): the phone app

The phone app reports with the server's own reporter (`createErrorReporter` from `@agenteschat/adapters/error-reports`, `@sentry/core` with a fetch transport, scrubbed by `scrubEvent`), which is MIT, so §7's license problem doesn't arise: what it gives up is native crashes, as the alternative above says. `auth-config`'s `mobileErrorReports` says where: `SENTRY_MOBILE_DSN`, a project of its own, else `SENTRY_WEB_DSN`, else nowhere and no reporting code loaded. The release is the app's (`mobile@<version>`), tagged with the phone's `os`, the workspace's and the person's ids. It reports what nothing caught (the global handler, before the system's), what a screen's error boundary shows (`ScreenError`), and a view of an agent's screen that never opened (`reportStuck`: `view` computer or card, `agent_id`, whether the page said `ready`, and its last state), since that one throws nothing. Errors from before the server answered wait for it, 20 at most (`apps/mobile/src/lib/error-reports.ts`).
