- Date: 2026-10-24

## Context

People want to see everything an agent does on its computer, not only its browser, to take control at any moment, and to open a terminal on the agent's computer to run commands themselves. ADR 0040 covers the browser (its JPEG live view and its handoffs); ADR 0031 §6 planned one virtual display per agent on connected Linux computers. Self-hosters run this on their own Linux machine; the Cloud runs the same code on its machines.

### Measured (a 4-vCPU, 8 GB VPS; Debian 13, kernel 6.12, TigerVNC 1.15, XFCE 4.20, Bun 1.4.4)

| What | Result |
| --- | --- |
| Desktop start: Xvnc listening / desktop drawn | 0.2–0.3 s / 2.6–4.9 s |
| Memory (PSS) | Xvnc 42–68 MB, XFCE 108–120 MB (150–190 MB idle); with a headed Chromium and two tabs, about 780 MB |
| Stream open on the machine: connect and VncAuth / ready | 8–13 ms / 28–51 ms |
| Bandwidth per viewer at 1280×800 | idle 4 KB/s, typing 34 KB/s, a page load 300 KB/s, scrolling or video up to 2.3 MB/s; RFB's pull model adapts (110 KB/s on a 1.5 Mbit/s link, no backlog) |

| CPU per viewer | Xvnc 0.7% of a core idle, 24–55% while the screen moves; the relay 3–4% |
| View-only by password | a pointer event on a view-only connection is ignored; on a full one it moves the pointer |
| PTY | `Bun.Terminal` exists from Bun 1.3.5; first output in 54–106 ms; a resize is seen by `tput`; 24–37 MB/s |
| Typing accents | keysyms dropped `ê` and `õ`; the clipboard and a paste delivered `Olá, ação: êõú ç — 日本` exactly |

### Alternatives considered

- **Xvfb + x11vnc**: two processes, and view-only is an option of the server, not a property of each connection.
- **Relaying frames, like the browser's live view**: no flow control of its own and more CPU on the machine.
- **Streams on the machine socket**: a busy screen would delay tool results and heartbeats.
- **A VNC gateway on the machine (websockify) or Guacamole/WebRTC**: an inbound port, or another server to run.

## Decision

### 1. One desktop per agent: Xtigervnc and XFCE, started when first needed

- One `Xtigervnc` per agent display (X server and VNC server in one process): `:N -geometry 1280x900 -depth 24 -rfbport -1 -rfbunixpath <session folder>/vnc.sock -rfbunixmode 0600 -SecurityTypes VncAuth -PasswordFile <file> -AlwaysShared -AcceptSetDesktopSize=0 -FrameRate=30 -UseBlacklist=0 -auth <Xauthority> -nolisten tcp -s 0`. Never `-ac` or `-nopw`.
- No TCP listener: a loopback port can be taken first by another agent's process, which would then show a fake screen to the people watching and read what the person in control types.
- `DESKTOP_SIZE` is 1280×900 (inside the screen layer's image limits, ADR 0054): the agent's Chrome, maximized above the dock (§15), shows a page of 1280×753 (1280×786 under XFCE's default panels), close to the 1280×800 of the headless Chrome the screen layer was measured on (§7). Viewers scale it and never resize it.
- An XFCE session (`dbus-launch --exit-with-session xfce4-session`), restarted up to 3 times in 10 minutes. Its own ssh-agent is off (the session's settings, written once into its `HOME`): it daemonizes and would outlive every desktop. So is its gpg-agent (added 2026-10-26, for homes new since): before any of its programs, the session restarts it and waits for both commands (`gpgconf --kill gpg-agent`, then `gpg-agent --daemon`), and gpg starts its own agent when something uses it. Each start's line in the runner's log says where its time went: `the desktop of ada started on :20 in … s: room and its user … s, prepared in … s, its screen in … s (the look in … s meanwhile), its session in … s` (added 2026-10-26). XFCE then starts its programs one priority after another, each once the one before has registered with the session (8 s at most): xfwm4, xfsettingsd, the panel (and docklike's own process, `wrapper-2.0`), Thunar's daemon, then xfdesktop, whose wallpaper is the picture a viewer waits for. At the first sweep at least 15 s after a start, a second line says when each of them started from the session's own start, and the CPU time its processes used by then, read from `/proc`: `the desktop of ada: its session started xfwm4 at … s (… s of CPU), xfsettingsd at … s (… s of CPU), xfce4-panel at …, wrapper-2.0 at …, Thunar at …, xfdesktop at …`; the gap before one is the one before it registering, and one that used seconds of CPU worked them (a cache it built, say) where one that used none waited. xfwm4's vblank is off (`vblank_mode`, set in its settings file before every start, since xfwm4 writes all its settings there on its first start): its compositor shows a change only at the next vblank, and Xtigervnc's vblank clock ticks once a second while no viewer is connected, so with nobody watching what an app drew reached the screen, and the agent's screenshots (ADR 0062), up to 2 s late (from a desktop's second start on: on its first, in a new home, xfwm4 didn't wait). Measured: a key's echo reached the screen 0.2–1.0 s after the terminal drew it with no viewer connected, 3–15 ms with one, and within 1 ms with the vblank off and no viewer. The price is CPU while something on the screen moves: the compositor now paints as often as the apps draw, watched or not, where an unwatched desktop painted about once a second (and a watched one 30 times). A window repainting at 60 fps (200×200 or 1000×700) took Xtigervnc and xfwm4 together 0.14–0.31 s of CPU a second with nobody watching, against 0.05–0.10 s with the vblank, about what a desktop with one viewer costs either way (0.12–0.35 s); an idle desktop costs under 0.02 s. The packages go in with `--no-install-recommends` (otherwise a screen locker nobody can unlock, more daemons and eight folders in each home): `tigervnc-standalone-server xauth dbus-x11 xfce4-session xfwm4 xfce4-panel xfdesktop4 xfce4-settings thunar xfce4-terminal adwaita-icon-theme elementary-xfce-icon-theme fonts-noto-core`. Then `fonts-noto-cjk` where apt has it (about 91 MB on Debian 13 and Ubuntu 24.04): without it Chinese, Japanese and Korean text, in the agent's browser among others, shows as empty boxes.
- Started the first time it is needed: the agent uses its screen or its browser, a person opens it (a viewer too: `stream.open` with `start` starts it, never for a held agent), or a person is asked to help on it. Then it stays on: nothing stops it for being idle (ADR 0065 §2), only its agent leaving the computer or its workspace being suspended. The agent's Chrome on it closes after 15 unused minutes, its sign-ins kept.
- Room, not a count, bounds them (ADR 0065 §2): before a desktop or a headed Chrome starts, `MemAvailable` must leave 1.5 GiB free (and a desktop needs a free display), and the runner parks desktops for it, least recently used first, among those nobody watches, their agent doesn't use and nothing touched for an hour. With nothing to park, `desktop_busy`. Brain turns start under the same floor (ADR 0025 §5, admission).
- A runner restart leaves desktops running (`KillMode=process`, `setsid`): the new runner takes them back after checking each pid's command line.
- The session's `HOME` is `<agent folder>/.agentes/home` in single-user mode (XFCE's files stay out of the agent's work), the agent's own home in system mode.
- The session folder (the cookie and the socket) is `<runner home>/desktop/<id8>/` in single-user mode, since a socket's path has at most 107 bytes and an agent's folder can be deeper; in system mode `~/.agentes/desktop/` of the agent's own user. Each agent keeps its display (`:20` to `:69`, `slots.json`); a display another process holds is skipped.

### 2. Raw RFB relayed as bytes, one data socket per stream

noVNC in the web app ⇄ `wss /api/desktop` ⇄ the server ⇄ one data WebSocket the runner dials for that stream (`/api/machines/stream`) ⇄ the agent's Xtigervnc over its Unix socket. The server never parses RFB, and RFB's pull model is the flow control. A terminal takes the same path with xterm.js and `wss /api/terminal`. The server replica that holds the machine's socket holds its streams; a viewer on another replica gets 4503 until streams cross replicas.

### 3. VNC security ends on the machine

- The runner logs in to Xvnc with the view-only password for a watcher and the full one for the person in control, then offers the viewer security type None over our own authenticated channel. Xvnc enforces view-only itself.
- Two random 8-character passwords per desktop start; they never leave the machine. In system mode the password file is root's (`/run/agentes-desktop/<uid>/passwd`, `root:<agent group>` 0440, in a 0750 folder under a 0711 parent): Xvnc reads it on every connection, so an agent that could write it would swap the two passwords and turn its watchers into controllers.
- A 16-byte MIT cookie per display, written with `xauth … source -` (never in an argument), in a home only its user reads.
- `-UseBlacklist=0`: TigerVNC counts attempts, not failures, so a burst of reconnects after a deploy would lock everyone out; behind a 0600 socket the blacklist protects nothing.
- TigerVNC sends the clipboard only to connections allowed to cut text: watchers never get the controller's clipboard.

### 4. Who may watch, take control and open a terminal

- **Watch**: the browser's rule, `requireBrowserAccess(…, "desktop")`: admins, the agent's owner, the person a request went to, and whoever is behind the agent's live work; also whoever passes the control rule below, who can see all of it anyway.
- **Control and the terminal** are one rule, because a desktop in control has a terminal and "Run Program": who may run commands as the OS user the desktop runs as.
  - System mode (each agent its own OS user): org admins and the agent's owner.
  - Single-user mode (the runner's own OS user, which holds every agent's folder, every account folder of ADR 0041 and the machine's token): only the person who paired the computer. The machine switch is no boundary there, since the agent's own code runs as that user too.
  - A computer nobody paired (a server's own computer): nobody, until it runs system mode.
  - The server applies the rule from the mode the runner reports in `hello` (`mode: "system"`); a runner that reports none is single-user. In single-user mode the agents' own code runs as the runner's user and could send any `hello`, so system mode is believed only from a computer's first `hello` after pairing, and from one that has said so ever since.
- `desktop_ask_person` asks only people who pass that rule: the agent's owner when they do, else everyone who does (the person who paired the computer; the admins in system mode). When nobody does, the tool says so to the agent.
- Nobody turns a desktop on or off (ADR 0065 §2): whoever may watch it starts it by opening it, and it stays on.
- Access is checked again every 30 s on open streams; an open control stream also keeps its holder's control alive, and when it closes the 2 minutes of grace start. In a suspended workspace (ADR 0056 §8) nobody has a stream, as every permission check refuses there; on hold (or with the agent held), people still watch a desktop that runs, while taking control, opening a terminal and starting a desktop that isn't running are new work, refused like the agents' own.
- In control or in the terminal a person can do whatever that OS user can do: that is the point, and why the rule is narrow. X11 has no input isolation: while a person is in control, any process of that user with the cookie (the agent's tasks, a brain's shell) can read the screen and the keys. The take-control text says so.
- On agentes.chat Cloud the take-control line has an ⓘ: the screen's text may be checked for abuse (ADR 0076).

### 5. Control is a handoff on the `desktop` screen

- ADR 0040 §6's handoffs, kept per screen (`browser_handoffs.screen`): one person in control per screen; the other viewers' streams close with 4409 ("Ana está no controle · tela oculta"); "Devolver" with a note tells the agent who had control, for how long and the note, and the agent must look again (`desktop_read`); control is kept 2 minutes after the controller's view drops.
- A handoff stays on the screen it was asked for: the phone app keeps answering the browser's requests ("log in for me") over CDP, which drives a headed Chrome as well.
- An agent whose Chrome runs on its desktop shows the same window on both screens: an open handoff on either blocks a take over of the other and the agent's tools on both, and hides both views (the browser card's frames and the desktop's streams). The server counts the two as one window whenever the agent has `desktop:use` and its own computer serves desktops, whether or not its Chrome is there at that moment.
- The agent's running brain turns and tasks go on; its screen and browser tools wait (with §4's limit on input).
- Superseded by §16. When control starts, the desktop's keyboard layout becomes the controller's (`setxkbmap` as the agent): noVNC sends key codes, and the desktop's layout turns them into characters.

### 6. The terminal

Superseded by ADR 0065 §1: the apps have no terminal view (in control, the desktop's own Terminal app is there). What follows stays on the runner and the server until a later change removes it.

- A `Bun.Terminal` PTY with the login shell as the agent's OS user, never root (system mode: `systemd-run --scope --slice=agents-<uid>.slice -- runuser -u ag-<id8> -- bash -l`). Its folder is the agent's; its environment has none of the agent's secrets and `TERM=xterm-256color`.
- A resize is a text frame. Output beyond a 1 MB backlog is dropped, followed by `[output skipped: too fast]` (`Bun.Terminal` can't pause).
- Closed after 30 idle minutes, and after 12 hours at most. No history is kept, and reconnecting opens a new shell: nobody types into a shell they didn't see start.
- Where session screening is on, the server refuses the terminal socket (ADR 0076).

### 7. The agent's browser on its desktop

- For an agent with `desktop:use` whose browser runs on its own computer, when that computer serves desktops, the runner's Chrome runs headed on the agent's display; the desktop starts first. `agent-browser` still attaches over CDP, on an OS-assigned port. On a mission's other computer the browser stays headless: the desktop people watch is the one on the agent's own computer. In system mode the agent's worker runs its Chrome there too, as the agent's own user, on the display the supervisor gives it (§14, added 2026-10-24; before that it stayed headless in system mode).
- The server says so on each request that may start Chrome (`desktop: true` on `browser.act` and `browser.batch`); the runner follows it only while its own desktop switch is on.
- The flags (ADR 0133 replaced `--test-type=gpu` with `--test-type` on Google Chrome): `--start-maximized`; `--test-type=gpu` (`--test-type` hides the bar a headed Chrome shows for the automation flag, and the value `gpu` the one Chrome for Testing shows about being only for automated tests: both take the page's height, and people see them); `--ozone-platform=x11`. Its environment is the runner's on the agent's `DISPLAY` and `XAUTHORITY`, without the runner's own Wayland display and session bus, so nothing it opens lands on the screen of the person running the runner.
- Chrome draws its own frame only when a window manager runs as it starts, and a desktop that just started gets its window manager a moment later: the runner sets Chrome's own frame in the profile (`browser.custom_chrome_frame`) before a headed start, so the window is the same either way.
- Signing in to Chrome itself is off in the agent's profile (added 2026-10-26): before a headed start the runner sets `signin.allowed_on_next_startup` to false (Chrome's own "Allow Chrome sign-in", which it reads as it starts), so no chip ("Sign in to Chromium?", which stayed about 20 s at the top right of a new window) or bubble asks a person to sign in to the browser. Signing in to sites stays as it is: people sign the agent in to them on purpose. Chrome 147 (at least) to 155 show that chip whatever the setting, so every launch also has `--disable-features=SigninPromoOnAvatarPill` (no such feature from 156 on).
- Pages see `prefers-reduced-motion: reduce` (`--force-prefers-reduced-motion` on every launch, headless or headed; added 2026-10-26), so an animated page holds still. Measured on a 4-vCPU Debian 13 computer: the agent's Chrome on agentes.chat's animated landing page took about 30 s of CPU every 15 s, two of its four cores, whether anyone watched or not (next to nothing on a blank page), and a person watching its desktop received about 10 Mbit/s. The switch is in Chrome for Testing from 140 to 156 at least.
- A Chrome in the other mode (the desktop came or went, the switch or the scope changed) starts again in this one at the next command that may start Chrome, on the same profile and the same page; never while someone watches it (the browser card, or the desktop it is on) or a person's turn is open. A desktop that can't start leaves Chrome headless, tried again after 5 minutes.
- The desktop and its Chrome know each other: a desktop isn't parked (ADR 0065 §2) while its Chrome is in use (a command within 15 minutes, the browser card's viewers, a person's turn), and a Chrome isn't idle while its desktop is watched (a person may be working in it without a command). A desktop that ends takes Chrome with it; the next command starts both.
- **Browser on the desktop** (added 2026-10-25). The dock's and the apps menu's Browser (§15) runs `agentes-runner desktop-browser <socket>`, which asks the runner, over that desktop's own socket, for the agent's own Chrome there: the Chrome and profile its commands drive, so a person in control who signs in to a site there signs the agent in, and the agent keeps that session. The runner owns that Chrome (its debugging port, its pid in `chromes.json`, the profile's lock), so a click never starts a second Chrome on the profile: Chrome starts headed on the desktop when it isn't running; one running headless moves there, on the same page, even while someone watches it or a person's turn is open (a person asked, from that desktop); one already there comes to the front (Chrome's `/json/activate` on its most recent tab, or a blank tab in a window of its own when none is left). That last one only for a click that reaches the runner: the apps menu's Browser, a middle or Shift click on docklike's Browser (docklike runs its launcher for those), or the panel's own launcher where docklike isn't installed. A plain click on docklike's Browser while Chrome has a window there never reaches it: docklike raises that window itself, or hides it when it is the active one (it runs a launcher only for an app with no window). A click never runs Chrome headless: a desktop that can't take it (the computer short of memory, say) fails the click with its own reason. The runner answers a click that starts Chrome once its window is on the desktop (added 2026-10-26; it used to answer as Chrome's debugging port opened, about 2 s before the window showed, so a person saw nothing for 3 s): Chrome answers its debugging endpoint's list only once it is done starting, which shows its first window, and lists that window's page; half a second more lets Chrome draw it. One whose window doesn't show within 20 s is stopped and the click fails ("Something went wrong"); one that closes meanwhile fails it too. When the answer takes more than 0.3 s (a second before 2026-10-26), a small window on the desktop says the browser is opening ("Opening the browser…"), and, as soon as the runner says so, that `agent-browser` and Chrome for Testing install first, before the agent's first browser ("Getting the browser ready…"): an xfce4-terminal with Browser's icon, closed once Chrome's window is up and over it, so there is no moment with neither on the screen. It has a window class of its own (`agentes-wait`, whose hidden desktop entry gives docklike's dock Browser's icon for it): with Browser's, docklike showed it on Browser, where a second click only hid it (docklike runs a launcher only when its app has no window), and now that click reaches the runner and is told `busy`. Each click that reaches the runner goes in its log, the agent's handle and how long it took, never an address: `Browser on the desktop of ada: opened in 3.2 s`, `already open: brought to the front`, or `already open; it didn't come to the front` (Chrome's endpoint didn't take it), and why when it didn't open; docklike's own raise of an open Chrome leaves no line (corrected 2026-10-26: this said a click on Browser with Chrome open logged `brought to the front`). When the browser can't open, a window says why until it is read, in plain words for the error's code (the runner's log keeps its own reason); it has a window class of its own (`agentes-note`, whose hidden desktop entry gives the dock its icon), so a click on Browser tries again rather than bringing that window up. A click is refused, with why, while the machine's `browser` or `desktop` switch is off or the computer is paused.
  - The socket is `browser.sock` next to the desktop's password file, open while the desktop runs (and again when the next runner takes the desktop back): in system mode root's, in root's folder for the agent (`/run/agentes-desktop/<uid>/`, 0750 `root:<agent group>`), mode 0660 with the agent's group, so no other agent reaches it and the agent can't swap it for its own; in single-user mode the runner's, in `<runner home>/desktop/<id8>/`. It takes one word, `open`, and answers `installing`, then `ok` (Chrome's window is up) or `error <code>`: no address and no flag, so a click widens nothing the browser reaches. One click is answered at a time, until its window is up: one that comes meanwhile is told `busy`, starts nothing, and its launcher shows nothing (the first one's shows what happens). It holds 4 connections at once: the agent's own code can connect too, and each connection is one of the runner's open files (root's, in system mode).
  - In system mode root starts the agent's worker when it isn't running and tells it (`browser.show` on their link, answered with `browser.showing` and `browser.shown`); while it answers, root lends it the desktop for its Chrome (`desktop.ensure` with `use: "browser"`), as during a command the server put there, and also between two of the worker's sessions (they follow the server's connection), so a click goes on across a reconnect. A click its worker hasn't answered in 16 minutes, the launcher's own wait, fails, and root stops lending the desktop for it: the agent's own code can stop its worker. A worker's ask for the desktop that gets no answer gives up after 2 minutes, so it never holds the agent's browser commands behind it.
  - The agent's own code runs as the user the socket lets in, so it can send the word too: it gets its own browser on its own desktop, where its commands could put it already, and nothing else.
  - A person may browse anywhere in it, as in control of the desktop before; the agent's reads still check the page against its site list first (ADR 0040 §4).
  - The agent's Chrome on its desktop has the dock's Browser's window class (`--class=agentes-browser`), so the dock shows its windows on Browser.
- Measured (Chrome for Testing 156, 1280×900, XFCE): a page of 1280×786 with `navigator.webdriver` false and no bar, maximized under the panel, its own frame even when started 2 s after a new desktop; the browser card's live view keeps working.
- **The browser card shows this screen** (added 2026-11-05). Where the agent's Chrome runs on its desktop, the browser card (in the conversation, on a computer's page, and the phone's card) shows the agent's whole screen, scaled into the card in its own shape and never cut, instead of its browser's frames: the browser is a window there, and the person sees everything else the agent opened beside it. Only while all of these hold: the desktop status says so (`browserOnDesktop`, true only where the desktop can be shown; an older server leaves it out, which the apps read as false), the desktop runs (a card never starts one), this person may watch it now (`desktopStatusState` is null: nobody else in control, not held while stopped), they hold neither the screen nor the browser (whoever holds the browser drives it on its frames, whose watch keeps their control alive: Take over in the card flips it back to frames in control), and the card's view hasn't given up for this status. Otherwise the card shows the frames, as before. While it shows the screen it watches no frames (no `browser.watch`), so the computer's screencast stops once nobody else watches.
  - The card's view is its own kind of desktop stream: `GET /api/desktop?…&preview=1&mode=watch` (400 with `mode=control`; `switch` is ignored). It never starts the desktop (`stream.open` without `start`, and no `desktop.session.start` after a `desktop_off`: the card goes back to frames), never warms the browser, is never switched to control (so no control audit and no session screening), takes at most 3 of the 4 viewers of a desktop (`viewersPerDesktop` − 1), and yields to a person opening the screen itself: the agent's oldest card view closes with 4429 `preview_yield`, and the opening one asks the computer again once, 500 ms later, if it still counted that view. Its audit row is the usual `desktop.watched`, with `preview: true`.
  - It opens only while the card is on the person's screen (the web) or open with the app in front (the phone), stays 10 s after it leaves, and is tried again at most 3 times after drops; any other close (busy, hidden, forbidden, ended…) puts the card back on frames at once. The desktop status is asked every 30 s while the card shows, and again when the computer's state changes (`machine.*`, `agent.computer`), so the card goes back to frames by itself when the browser moves off the desktop, the computer goes offline or its switch off, the person loses access (403, or the 30 s recheck's 4403), the desktop stops, the viewers are full, or someone takes control. A card that gave up tries the screen again once the status changes, or after 2 minutes.

### 8. The scope: `desktop:use`, always together with `sandbox:run`

- One built-in scope, `desktop:use`: outside "all tools" (`NOT_IN_ALL`), on by default for new agents (`DEFAULT_AGENT_SCOPES`), revocable by admins and the agent's owner. Desktop computer use (the agent's own tools on this desktop) uses it and adds no scope of its own.
- Driving a desktop runs commands as the agent's user, on any site (a terminal window, "Open Terminal Here"). So the desktop's tools are offered, and allowed on each call, only while the agent also has `sandbox:run`, the org's sandbox setting allows it, and the machine has both its `commands` and its `desktop` switches on.
- Migration 0096 grants `desktop:use` to the live agents that already have both `browser:use` and `sandbox:run`, and to no other.
- Routines (ADR 0053): its own internal area, `desktop`, allowed in routines that act and refused in read-only routines (a run nobody is behind may use it since ADR 0053's addendum of 2026-10-31). `desktop_ask_person` speaks in the run's own conversation, like `browser_ask_person`.

### 9. Switches and availability

- Two machine switches, `access.tools.desktop` and `access.tools.terminal`, turned on at the machine (`agentes-runner tools enable desktop terminal`): off by default on a personal computer, on in the Cloud. The server can only turn them off.
- `hello.desktop` and `hello.terminal` say whether the runner can serve them, and why not: Linux, the runner on Bun 1.3.5 or newer (`Bun.Terminal`), and for the desktop the packages above. A runner on Node says so with the fix. Mac and Windows get no virtual desktop (the browser stays headless with its own live view); a Mac command-line runner on Bun 1.3.5 or newer serves the terminal.
- The runner's installer runs it on the computer's own Bun when that has `Bun.Terminal`, else on a pinned Bun it downloads and checks against its SHA-256 (Linux and macOS, x64 and arm64); on Node.js 22+ or an older Bun only when that can't be had, saying what that runner lacks. `agentes-runner status` prints both availabilities, with the reasons.
- A paused computer (ADR 0036 §6) still shows a desktop that runs; starting one, taking control and a terminal are new work and wait for the resume (`isNewWork`).

### 10. OS users: single-user and system mode

- **Single-user** (the self-host default): the runner's OS user runs every agent, its desktop and terminal included (ADR 0030 level 1); the docs say so.
- **System mode** (`install.sh --system` on Linux; the Cloud; ADR 0057): a root supervisor and one unprivileged worker per agent, as the agent's own user `ag-<id8>` (uid 20000–29999 by default), in `agents-<uid>.slice`, which shares the computer's memory and CPUs with the other agents' within the limits of all of them together (ADR 0057 §2).
  - Everything done for an agent runs as that user: commands, tasks, brains, files, its browser, its desktop, its terminal. The supervisor runs no agent code: until a worker serves an agent's requests, the root runner refuses them. Workers start on an agent's first request.
  - The desktop and the terminal are the supervisor's ops (`desktop.session.*`, `stream.open`), since a stream's data socket needs the machine token, which no worker holds, and the password file is root's: it starts Xtigervnc, the session and the shell through the agent's launcher.
  - The runner is updated by its installer, never by itself.
  - Chrome's debugging port and `agent-browser`'s stream port have no authentication of their own. System mode assigns each agent a fixed pair, guards the full configured uid range with `inet agentes_runner` before workers start, and prevents another agent from binding that pair with a verified systemd socket-bind policy. Arbitrary local listeners still use the two-second `ss` scan and retain its race window (ADR 0057).
  - Chrome's sandbox needs unprivileged user namespaces (on by default in Debian 13): hardening must keep them.

### 11. Protocol 18

```ts
DESKTOP_SIZE = { width: 1280, height: 900 }
RunnerInfo (hello): desktop?: { available; reason?; width?; height? }; terminal?: { available; reason? }; mode?: "system"
RunnerTools (switches, absent = off): desktop?: boolean; terminal?: boolean
MachineRequest (each carries `agent`):
  { op: "desktop.session.start" }    // idempotent: starts it, or only marks it used
  { op: "desktop.session.stop" }
  { op: "desktop.session.status" }
  { op: "stream.open"; streamId; kind: "desktop"; mode: "watch" | "control" }   // an older server's `keyboard` is ignored (§16)
  { op: "stream.open"; streamId; kind: "terminal"; cols; rows }
MachineReplies:
  "desktop.session.start": { display; width; height; startedAt; started }
  "desktop.session.stop": { stopped }
  "desktop.session.status": { running; startedAt?; lastUsedAt?; streams }
  "stream.open": { opened: true }    // once the data socket got `stream.ready`
MachineErrorCode += desktop_unavailable | desktop_off | desktop_busy | terminal_unavailable | too_many_streams
```

- **Data socket** (runner → server): `GET /api/machines/stream` as a WebSocket; a request with an `Origin` is refused. The first text frame, within 10 s: `{"type":"stream.hello","token":"agm_…","streamId":"<43 base64url>"}` (the machine's token, which every runner process that opens streams holds, and the 32 random bytes of `stream.open`). The server answers `{"type":"stream.ready"}` or closes: 4400 not a hello, 4401 a bad token or another machine's stream, 4404 an unknown stream (ended, or served already), 4408 too late. Then binary frames are the bytes and text frames are control (`parseStreamControl`): `{"type":"resize","cols","rows"}` towards the terminal, `{"type":"exit","code"}` back. Both sides ping every 30 s. The runner answers `stream.open` only once it got `stream.ready`; when the data socket closes, the viewer's closes too (1000 when the runner closed it so, else 4503). The runner closes it with 1000 when the stream is over for good (the shell ended, after its `exit` frame; a viewer that broke the RFB handshake), and with another code when the viewer should open it again: 1011 when the desktop went away (the next open learns whether it still runs), 1001 when the runner's connection ended.
- **Viewer sockets** (web → server): `GET /api/desktop?orgId&agentId&mode=watch|control` (an older app's `keyboard` is ignored) and `GET /api/terminal?orgId&agentId&cols&rows`. Before the upgrade, like `/api/ws`: 401 without a session, 403 for a foreign `Origin` or a non-member, 400 for bad parameters. After it, close codes the panel turns into states (`STREAM_CLOSE`): 4400 bad request (a frame too big, too fast, or not the stream's) · 4403 forbidden, or access lost · 4404 no such agent, no computer, or an agent without `desktop:use` · 4408 the computer didn't open the stream in time (retry) · 4409 hidden (someone else is in control) · 4410 control ended, or never this person's (open again as a watcher) · 4429 too many streams, or too many opens · 4502 the computer refused (the reason is the error code, or `machine_paused`, `runner_outdated`, `not_allowed` for a switch that is off, `desktop_unavailable`, `terminal_unavailable`) · 4503 the computer is offline or on another replica (retry) · 1013 too slow · 1001 the server restarts (retry). What a viewer sends before its stream is ready waits for it (up to 1 MB).
- **REST** (`/api/app`): `GET …/agents/{agentId}/desktop` (availability, running, who controls, viewers, what this person may do, and the terminal's availability) and `POST …/desktop/start`; the screens' routes `…/desktop/handoff`, `…/desktop/takeover`, `…/desktop/stop`.
- **Limits** (`STREAM_LIMITS`): 4 viewers per desktop; 3 terminals per agent and 10 per machine; 30 stream opens a minute per person; a viewer's backlog 8 MB and the runner's 4 MB; a viewer's frames up to 1 MB and 512 KB/s; a terminal's size 20–400 × 5–200.
- **VncAuth** (test vectors): DES-ECB of the 16-byte challenge with the password as the key, each key byte's bits reversed: `password` and `00…0f` give `b866924125c8eebb9debc1db61c538e2`. TigerVNC's password file is each password encrypted with VNC's fixed key, bit-reversed `e84ad660c4721ae0` (`password` → `dbd83cfd727a1458`): the full password first, the view-only one second.

### 12. Audit, nothing stored

Handoff rows record control. `audit_log` rows `desktop.watched`, `desktop.controlled` and `terminal.session` keep the machine, the seconds and the bytes. No frames, keys or terminal output are stored, and nothing is recorded (ADR 0040 §8). On agentes.chat Cloud with session screening on, the screen's text is read during control and held in memory for up to 20 minutes, never stored (ADR 0076). A click on Browser on the desktop (§7) stays on the computer, in the runner's log: the server never hears of it. An audit row for it (`desktop.browser_opened`, by the person in control of that desktop then) would need a runner frame that says so, a protocol change.

### 14. System mode: the agent's Chrome on its desktop (added 2026-10-24)

§7 holds in system mode too. There the agent's worker (ADR 0057) runs its Chrome, as the agent's own user and in its slice, and root runs its desktop (§10):

- **The display.** A command that may start Chrome is a request from the server, so the worker asks the supervisor for the desktop while that command runs: `desktop.ensure` on their link with `use: "browser"` (the frame ADR 0062 §3 added for desktop use, which says `use: "desktop"`). Root answers only while that worker serves a `browser.act` or `browser.batch` the server sent with `desktop: true`, with the machine's `desktop` and `browser` switches on (desktop use keeps `desktop` and `commands`), and only with the desktop of that request's agent, the worker's own: its display, the path of its cookie file (in the agent's own home) and the home. Never the VNC passwords. The agent's own code runs as the worker's user, so it could send the frame too; outside such a request it gets nothing and starts no desktop.
- **The move.** As in §7: a Chrome running headless moves at the next command that may start one, on the same profile and page, never while someone watches it or a person's turn is open. A desktop that can't start, root's refusal, or a desktop that goes away while Chrome starts on it (in either mode) leaves Chrome headless and the command goes on; the desktop is tried again after 5 minutes.
- **In use, across two processes.** While its Chrome on the desktop is in use (§7: a command within 15 minutes, the browser card's viewers, a person's turn), the worker says so on the link (`browser.desktop`) after each change and every 30 s, and root doesn't park that desktop (ADR 0065 §2) within 90 s of the last one. Root tells the worker how many people watch or control the desktop (`desktopViewers` in `worker.state`, sent whenever one comes or goes), and the worker's Chrome isn't idle, or moved off, while anyone does. The agent's own code could send `browser.desktop` as well: that keeps only its own desktop up, inside the limits all agents share.
- No protocol change: the server already puts these agents' browser commands on the desktop (§7), and root and its workers are the same runner.
- Measured (`install.sh --system --desktop` on a 4-vCPU, 8 GB VPS, Debian 13, Chrome for Testing 156, a throwaway agent and a stand-in for the server): the agent's first command (its user, its worker, `agent-browser` and Chrome for Testing fetched) 29 s, headless; its first command on the desktop, which started the desktop and moved Chrome there, 7.7 s; a new desktop and a new Chrome together 2.0–3.9 s over 13 starts; moving a running Chrome off a running desktop or back 2.0–2.1 s; a command there afterwards 0.13 s. Chrome ran as the agent's user in its slice, maximized under the panel: a page of 1280×786, `navigator.webdriver` false, a normal user agent, no automation bar. The browser card's live view kept working, and desktop use read Chrome's window as the agent browser's one line; a command off the desktop while someone watched it left Chrome there. With a person's turn open and no command, the desktop stayed up 19 minutes past its own last use; once the turn ended, the worker closed the idle Chrome and the desktop stopped 2 minutes later. In one desktop start of 19 the X server exited 0.8 s after starting, while Chrome started on it (the desktop then started again by itself): that command failed, which the fallback to headless above now covers.

### 15. The desktops' look (added 2026-10-25; its third version the same day, its fourth and fifth 2026-10-26)

XFCE's defaults (a top panel and a launcher bar, four workspaces, icons on the desktop, a grey theme) made every agent's desktop look like a stock Linux machine. Each one now has the agentes.chat look, laid out like Windows 11's centered taskbar and the macOS dock (`apps/server/runner/desktop-look.ts`). Its third version (`LOOK_VERSION` 3) adds Browser (§7), shows each app's windows on its own launcher where docklike is installed, gives the apps menu short names with nothing listed twice, and puts the agent's name in the terminal's prompt. The fourth (4) puts a mark under each app with windows on docklike's dock (the third's never showed) and gives that dock its rounded right end. The fifth (5) gives Browser the icon theme's globe (`applications-internet`, at every size in elementary-xfce 0.16 to 0.21) in place of its web browser's (`org.xfce.webbrowser`, a link to `web-browser`), which has a mouse pointer drawn into the globe and read as a stray pointer on the dock; XFCE's Internet menu, there once another network app is installed, had that same globe, and gets the theme's network sphere (`preferences-system-network`, purple, at every size in the same versions) from a directory file of the look's that takes the place of XFCE's (`~/.local/share/desktop-directories/xfce-network.directory`):

- **What.** The wallpaper: one frame of the brand's pixel sky (`startSky`, the landing's engine), seeded, with the expanded logo at the bottom left on its pale band, below where maximized windows end; rendered at exactly `DESKTOP_SIZE` and shown 1:1. Its ".chat" is in the sprites' solid navy with Doto's heaviest dots: the computer dialog shows the desktop at about 0.6, where the app's lighter ink and 600 weight faded below 2:1 against the band. The dock: one floating panel at the bottom center (48 px, 32 px icons): the mark (the favicon) opens the apps menu, then Browser, Files and Terminal, each with a short bar under it while it has windows (8 px, the ink at 65%), a longer, solid one under the active window's app (16 px, on a pale square) (where the panel's own plugins make the dock: a button for each open window after them instead, with the same bars); maximized windows end 60 px above the bottom (xfwm4's `margin_bottom`: a floating panel reserves no room). No top panel, one workspace, no desktop icons; new windows centered (xfwm4's `placement_ratio` at 100: by default it centers only windows under a fifth of the screen and fits the others into its corners), their buttons on the right; Noto Sans (`fonts-noto-core`, already installed); a dark terminal, its 16 colors from the design system's dark tokens (the shell's prompt prints in them). The apps menu is XFCE's own in a layout of ours (`~/.config/menus/xfce-applications.menu`): Browser, Files and Terminal first, the look's own desktop entries (`~/.local/share/applications/agentes-*.desktop`: top level only, named in English, as the desktop session runs in `C.UTF-8` and a translated name would never show); then the menus of whatever else is installed, then Settings, so no separator stays alone at the end when there are none; without XFCE's first and last groups (Run Program and About aren't installed, Log Out is hidden), which left a separator alone at each end. XFCE's generic Terminal Emulator and File Manager are hidden (Terminal and Files replace them), and Thunar, its bulk renamer and XFCE's own terminal leave Accessories and System, which listed Thunar in both: with nothing else in them, those menus don't show. Log Out leaves the apps menu (it ends the session: the runner would start it again and drop everyone watching), and so do XFCE's web browser and mail reader, which open nothing here. The dock's own right-click menu keeps XFCE's items (Properties, Move, Remove, and Panel ▸ Add New Items, Panel Preferences, Log Out): XFCE turns those off only for the whole computer (its kiosk file in `/etc/xdg`), which the look never touches; desktop use refuses an agent's click on that Log Out by name, as with the default panel. Orchis's light theme (GTK and xfwm4) where `orchis-gtk-theme` and gdk-pixbuf's SVG loader are installed (its window buttons are SVG files), else GTK's Adwaita and xfwm4's Default. Everything in it is ours or Debian's packages: no outside art.
- **The terminal's prompt.** bash's own prompt and window title show the agent's system user and the computer's hostname (`ag-01a142cb@vmi1234567:~$`). The desktop's terminal runs bash on the look's own startup file, `~/.local/share/agentes/bashrc` (xfce4-terminal's `custom-command`, `bash --rcfile`), in place of `~/.bashrc`: it reads `~/.bashrc` first, then shows the agent's name instead, green, in the prompt and the title (`Ada:~$`). Debian's and Ubuntu's bash read the computer's `/etc/bash.bashrc` before it themselves, `--rcfile` or not, so the file doesn't read it again. The name is a variable the prompt expands, never part of the prompt's own text, so none of its characters runs anything or takes a prompt escape. It changes the desktop's terminals only: the agent's own shell files stay as they are, and a single-user runner whose shell isn't bash keeps that shell and its prompt.
- **Where it is written.** Only into the desktop session's HOME (§1: `<agent folder>/.agentes/home` in single-user mode, the agent's own home in system mode): XFCE's xfconf files, the panel's launchers or docklike's settings, `~/.config/gtk-3.0/gtk.css`, the menu's layout in `~/.config/menus`, entries in `~/.local/share/applications`, and the images and the terminal's startup file in `~/.local/share/agentes`. Never the runner user's own settings, nor `/etc/xdg`: a self-hosted computer's own desktop doesn't change. A shell script run as the agent (through its launcher, like the prepare step, after it, while the screen server starts: XFCE reads those files and Xtigervnc none, so only the session waits for it, and a start that fails before its session ends only after it, so the next start's prepare never renames a file under it; since 2026-10-26) writes each file through a rename: as the agent's own process it writes nothing the agent couldn't, so a link the agent left in its home leads only to its own files. The files come on its stdin, never as arguments: in system mode `systemd-run --scope` names the agent's scope after its command line, which the journal logs at every start (it would be about 28 KB). It removes what sits at a temporary name first and reads only a plain file as its marker, so a pipe the agent left in its home can't hold the start; and both steps run as the agent before its session (the prepare, the look) are stopped after 10 s (a hung disk): a look stopped leaves the desktop as its HOME has it, a prepare stopped fails that start, where it used to wait forever and hold the agent's browser with it. When the look fails, the desktop starts with what its HOME has.
- **Versioned.** `~/.local/share/agentes/look` names the look written there: its version (`LOOK_VERSION`), its theme and dock, and a hash of every file it writes, which covers the HOME it was written for (the settings name the images by their full path, and single-user mode moves an agent's folder when its handle changes), the agent's name (the prompt) and how Browser reaches the runner. A new desktop gets the look; one whose marker names another gets it again, once, at its next start (desktops from before this section and from earlier versions included): a new version, Orchis or docklike installed or removed, a moved HOME, a renamed agent; one whose marker matches is left alone, so what a person changed there stays until then. A desktop that is running gets it in place (added 2026-10-26; it used to keep the look it started with until its next start, a reboot or a parking away, which on an always-on computer meant for good): none is restarted for a new look, since what a person left open there stays (ADR 0065 §2). See **A running desktop** below. The prepare step goes on managing what it did (the session's ssh-agent and gpg-agent off, xfwm4's vblank off): the look's xfwm4 settings have the vblank off too.
- **A running desktop** (added 2026-10-26). The runner records in the desktop's state file (`<runner home>/desktop/<id8>.json`) the look its session shows, at its start and when it takes a newer one; a desktop from an earlier runner has none recorded. Its sweep (every minute) brings a desktop whose look is another (a runner updated, Orchis or docklike installed since, the agent renamed) up to date once nobody watches it, its agent's browser isn't in use there and no request touched it for a minute, and once this runner knows its agent as it is now (the server's list of the computer's agents, sent at each connection and change, or a request for it): a single-user agent's folder is found by its handle, and the one an earlier runner saved may be out of date, the folder since moved to a new handle: as the agent, with the desktop's display, it runs the look's script in its live mode (once more asking, right before, whether anyone came to watch while the flags below were set). The files go in as at a start, all but the marker (it comes last, below); then the look's xfconf settings go through the session's own xfconfd (`xfconf-query`, one call a setting, on the D-Bus of its session or panel on exactly that display, found in their environment: in system mode only the agent's own processes can be read, and in single-user mode, where one user runs every agent's desktop, the display tells them apart), since xfconfd holds its channels in memory and writes them over the files: a file alone would be lost. xfwm4, xfsettingsd, xfdesktop and the terminal follow what xfconfd says changed, so the wallpaper, the window theme and margins, GTK's theme, icons and fonts and the terminal's colours change at once, and the windows open there stay. xfconfd says nothing of a value set again as it was, and xfdesktop loads its image again only when it hears that setting change, while a new look's wallpaper keeps its path: the wallpaper's setting is unset right before it is set, so a run stopped part-way doesn't leave the screen with no wallpaper. Then the panel restarts, since it reads gtk.css and docklike's settings only as it starts (XFCE 4.16 to 4.20): the dock disappears for a moment and comes back with the new look. That is the panel's own D-Bus `Terminate` with its restart on, the call `xfce4-panel --restart` makes, sent with `dbus-send` (in dbus-bin, which dbus-x11 depends on in Debian 12 and 13 and Ubuntu 24.04; in dbus on Ubuntu 22.04), so the panel restarts from its main loop. Not SIGUSR1: XFCE 4.16 to 4.20 handle it in a plain signal handler (`signal()`) that talks to the session manager and quits GTK's loop right there, which can leave a frozen dock that the session won't start again, as its process still runs. Not `xfce4-panel --restart` itself either: when its call fails it opens a dialog on the agent's screen and waits for a click. Only once the panel took it does the marker name the new look: a run stopped part-way (a setting refused, the time up) leaves the marker as it was, so the desktop's next start writes every file again over what xfconfd wrote back (a marker written before the settings would keep a half-changed look for good). A marker that already names the look means the session shows it (it started with it, or took it in place), so nothing is set again and what a person changed there stays: a desktop that an earlier runner started with this look has no look recorded, and only its record is set. The settings go in while the old panel runs and it only then restarts: a panel quitting saves only what its plugins hold that changed (XFCE's own plugins and docklike save each setting as it changes), and the look's settings never remove one under it (the launcher plugin deletes the files of items it loses). What can't change in place: a terminal already open keeps its prompt (bash read its startup file as it started; new terminals name the agent), and in single-user mode a desktop whose agent's folder moved (a new handle) keeps its look until its next start, as its session has the old HOME. The runner tries once per desktop: what fails (no session found on its display, a setting refused, the panel not restarted, more than a minute, six times a step's limit since the settings take seconds on a busy computer) is in its log with why, the desktop keeps the look it has, and the next runner tries again. Several desktops take it one after another: each sets 56 settings (69 with the panel's own dock), an `xfconf-query` each. Nothing of it runs as root: a runner running as root with no launcher for its agents (a home that isn't system mode's, under `sudo -E` say) leaves running desktops as they are and says so in its log, as it starts none either.
- **The dock.** Where `xfce4-docklike-plugin` is installed (Debian 13, Ubuntu 25.04 or newer), the dock is its plugin: Browser, Files and Terminal pinned (`~/.config/xfce4/panel/docklike-7.rc`), and a running app shows on its own launcher, as a dock does, where the panel's own plugins showed Terminal twice (its launcher, and its window's button). docklike matches a window to its launcher by the window's class: the look's entries name it (`StartupWMClass`), and the agent's Chrome on its desktop has Browser's (§7). A click on an app with windows brings them up, or down when it is the active one; a middle click opens another window (docklike's default closes them all), but on Browser it reaches the runner, which brings the agent's one Chrome to the front (§7); the dock's glass shows behind its icons (docklike draws in a window of its own process inside the dock, styled in gtk.css). The marks under its launchers are the look's gtk.css, from the classes docklike gives a launcher (`open_group` while its app has windows, `active_group` while one is active): docklike's own (its `indicatorStyle`, off since the fourth version) are drawn at the very bottom of its buttons, inside the margin the look gives them, which GTK leaves out of what a button draws, so they never showed. That window fills the dock's right end inside its 1 px frame, and the dock's own drawing never shows under a window of another process (its pixels are that window's, glass and all): so it draws the dock's end itself, its right corners at the dock's radius less the frame (15 px), the frame's hairline around them as a 1 px ring outside its box (only the corners fall inside the window; the dock draws the straight edges), and the glass's top light. The ring lies on the wallpaper, where the frame lies on the glass, so its colour is the hairline over the glass as one (the ink at 0.18 over white at 0.88: `rgba(205, 210, 217, 0.9)`); the ink alone made the corners' arcs darker than the edges they meet. Before, its square corners stood about 9 px past the dock's rounded frame, with no hairline at that end. gtk.css names that window as the panel's wrapper for a plugin that runs in a process of its own, and GTK's CSS can't tell one such plugin from another: one a person adds to the dock gets the same corners. That process isn't one desktop use (ADR 0062) reads: with docklike, the agent's look of the dock has the mark's apps menu only, so it opens apps by name (`open`) or from the apps menu and focuses windows by their own lines; a window minimized there is out of its look (a window's line needs it showing) until it clicks that app on the dock's image or opens it again. Elsewhere (Debian 12, Ubuntu 22.04 and 24.04) the dock is the panel's own plugins, as before, read as before: `toolbar "Panel"` with "Applications", "Browser", "Files", "Terminal" and each window's button (`[window]`), and the session-ending refusals unchanged. There a pinned app always opens a new window, and each open window has a button of its own, with its bar, right after the pinned apps: no gap between the two, since a separator there also stands in the empty dock, off its center.
- **In the runner.** The images ship inside the one-file bundle as base64 text (`assets/*.png.b64`, imported `with { type: "text" }` like the desktop helper's Python), about 29 KB with the settings: Bun's `text` loader mangles a PNG's bytes, its `file` loader writes a second file, and a Bun macro that read the PNGs is skipped by Bun's runtime transpiler in some import chains, which left the runner run from its source, and its tests, with `base64 is not defined`. Their source is `docs/design/desktop/` (`render.sh`: the wallpaper with headless Chromium from `wall.ts`, the mark with `rsvg-convert` from the favicon, then each PNG's base64 text); the committed PNGs are what ship, and a test checks that their base64 text decodes to them. A desktop of another size needs the wallpaper rendered again (a test checks the size).
- **Packages.** `install.sh --system --desktop` installs `orchis-gtk-theme librsvg2-common` after the screens' packages, in an apt call of its own: where apt has no Orchis (Ubuntu 22.04) the install goes on without it. On Debian 13 that is 8 packages and 42 MB (Orchis 13 MB, with gnome-themes-extra and GTK 2's theme engines); Ubuntu 24.04's Orchis alone is 84 MB, every color variant of it (only Orchis-Light is used). They stay out of the runner's install hint, which must work on every release, and out of what it checks: without them only the theme changes. Then `fonts-noto-cjk` (§1) and `xfce4-docklike-plugin`, each in an apt call of its own, so a release without one still gets the others: Debian 13 has docklike 0.4.3 (106 KB, 519 KB installed; the libraries it needs come with XFCE's panel), Ubuntu 25.04 and 25.10 have 0.4.3 and Ubuntu 26.04 0.5.1 (universe; 0.5.1 reads the same settings file with the same option values), and neither Debian 12 (nor its backports) nor Ubuntu 22.04 or 24.04 (any pocket) has it, so their desktops keep the panel's own dock. docklike stays out of the hint and the checks too. The runner itself installs no package: a computer installed before the installer had docklike gets it from `install.sh --system --desktop` run again (or `apt install xfce4-docklike-plugin`), and its desktops take it as the runner starts again (the installer restarts it), in place (**A running desktop**).
- Measured with the look's second version (Debian 13, XFCE 4.20, Chrome for Testing 156, `desktop-check` and the agent's own desktop use, in both modes): the agent's Chrome maximized shows a page of 1280×753; a terminal and Thunar opened at the screen's middle; the empty dock's icons sit 3 px off its center (7 px with a gap before the windows); ".chat" reaches 6.2:1 at its darkest dots at 0.6 scale (1.9:1 before); writing the look into a new home took 0.21–0.26 s as the agent, and a start whose marker matches spends 13–21 ms on it; desktop use read the dock's buttons by name, with `[window]` on those of windows that show, clicked a minimized window's button to bring it back, opened the menu from the mark (no Log Out) and refused the session-ending entry and keys as before. A self-hoster's own `~/.config` stayed as it was. A renamed agent's desktop (single-user mode) got the look again with its new paths. With a pipe at a look file's temporary name and the marker gone, the desktop started in 0.4 s with the look written; with one at xfwm4's settings, that start failed after 10 s and the next one, the pipe gone, started.

### 16. Keys, the clipboard and full screen in control (added 2026-10-26)

- **No keyboard layout.** Xvnc acts on keysyms: without `-RawKeyboard` (off by default in TigerVNC 1.12 to 1.15, and the runner never passes it) it zeroes the key code noVNC sends, so a key types what the person's own layout made, whatever the desktop's layout is. The picker, the control stream's `keyboard` and `setxkbmap` are gone (§5's last bullet, §13's keyboard bullet); an older app's or server's `keyboard` is ignored, so the protocol stays 22. The stream also no longer waits for a layout guess before it opens.
- **In control the keys go to a text field nobody sees, over the screen,** and are replayed on noVNC's canvas, so noVNC keeps its own key logic (the Mac's Cmd as Alt, Windows' AltGr, which keys are down). Only an editable element gets a paste in every engine (WebKit bug 75891: Safari and the Mac app), and only there do dead keys and input methods compose (noVNC issue 350, where they arrived bare). Composed text is typed as characters; an emoji, which noVNC can't type, goes as a paste. Cmd+V or Ctrl+V pastes the person's own clipboard: the text goes to the computer's clipboard, then Shift+Insert is pressed with their held modifiers let go and held again (Shift+Insert pastes in every window there, a terminal too, as §13 found). Cmd+C on a Mac sends Ctrl+Insert, which copies in terminals, GTK and Chrome there; Ctrl+C, Ctrl+Shift+C and Ctrl+Insert elsewhere go as they are, so Ctrl+C stays an interrupt. A phone or tablet raises its keyboard with a Keyboard button. Leaving the page while in control asks first (outside full screen Ctrl+W closes the tab).
- **The person's clipboard** is read only in a paste they made, and written only with what the computer copies within 2 s of their copy keys, started in that keydown (the only moment Safari lets a page write it). This reverses §13's "never written from the desktop": only their own copy keys write it, and nothing the computer copies by itself crosses; where the browser refuses the write, the line under the screen offers the text with Copy until it is copied, another copy comes or control ends (in the dialog: a modal dialog takes no clicks outside it, and a press on a toast would close it, which hands control back; the design system's dialog now ignores presses on toasts, and toasts take their own clicks). A paste is at most 256 KB as noVNC sends it (UTF-8, each line break as CRLF, and a NUL at the end), the size Xvnc's `MaxCutText` counts, which drops a larger one without a word; it is refused before anything is sent. Xtigervnc runs with `-SendPrimary=0`, so only a real copy reaches the person, never a selection; `SetPrimary` stays on for Shift+Insert. A desktop already running gets it in place (added 2026-10-26; it used to wait for its next start): TigerVNC lets a running server change a few of its parameters through its VNC extension, those of `AllowOverride` (in 1.12, 1.13 and 1.15 by default desktop, AcceptPointerEvents, SendCutText, AcceptCutText, SendPrimary and SetPrimary; the runner never changes that list), so at its first sweep the runner sets the flags of that kind a desktop's Xtigervnc started without (its command line says) with `tigervncconfig -set SendPrimary=0`, as the agent on the desktop's display and cookie, and reads it back, as tigervncconfig exits 0 even when the server refuses a set. `tigervncconfig` comes with `tigervnc-common`, which `tigervnc-standalone-server` depends on in Debian 12 and 13 and Ubuntu 22.04 and 24.04, so the installer adds no package. It changes nothing on the screen, so it doesn't wait for a desktop nobody watches. The state file records it. Any other flag still waits for a desktop's next start; none differs from what desktops have started with since §1.
- **Full screen** on the agent's screen shows that screen alone, scaled to the display on its own dark ground (1280×900 pixel for pixel at 1440×900), with the dialog's head as a bar that hides itself 2.5 s after the pointer last asked for it. In control only a tap on a touch screen brings all of it back, or the pointer resting 0.5 s at the display's top edge the head alone: the pointer stops there on its way to the computer's own top bar, which the bar would cover. A request's banner or a copy waiting for the person keeps it, and so does focus put in it with keys, not the focus a click leaves on a button. A cover over the screen stays under it. The page stays the full-screen element (§13). In control on Chromium, Keyboard Lock applies: Esc goes to the computer, and holding it leaves full screen; starting or leaving full screen gives the keys back to the computer, whatever button was clicked. The agent's page, a cover and the wait keep the dialog's own full screen. The screen is never resized to the display: agents' computer use (ADR 0062) and the desktops' look (§15) depend on 1280×900.

### 17. The handshake in one trip, and control on the same sockets (added 2026-10-31)

Taking control was slow: the first keys and clicks took seconds to reach the computer, the later ones the usual round trip. Measured with the runner's own stream code through the server, a fake Xvnc and a proxy adding 120 ms round trips on the person's leg and 90 ms on the computer's (Brazil and Europe to a server in the US), from Take control:

| To | Before | Handshake in one trip | And control in place |
| --- | --- | --- | --- |
| noVNC connected | 1165 ms | 529 ms | 223 ms |
| The first key on the desktop | 1271 ms | 636 ms | 330 ms |
| The first picture | 1376 ms | 740 ms | 434 ms |

A first click came later than a first key: the cover over the screen took clicks until the first picture showed (about 540 ms in the last column, by the table, not measured). Control's cover now lifts as noVNC connects (below), so a first click goes with a first key. Opening the screen to its first picture went from 1245 ms to 611 ms. On a real network each new socket also pays its TCP and TLS handshakes, to Cloudflare and from Cloudflare to the server, and a first picture travels on connections that start slow: neither shows with the fakes, so the gain of keeping the sockets is larger there.

- **The handshake in one trip.** The runner sends its whole side of the RFB handshake at once (the version, the security types, the result) with the desktop's ServerInit right behind it (its own ClientInit, shared, goes to Xvnc at once). Waiting for each of the viewer's answers cost a round trip between the person and the computer through the server, three of them before noVNC connected, on every open: watching, taking control, handing back, each reconnect. Each step is a frame of its own: noVNC 1.7 reads no further than the version in the frame that brings it (its version step ends its pass), and each later frame takes it as far as its bytes go. The viewer's answers are checked as they come (RFB 3.8, None), and until they checked out Xvnc gets nothing of the viewer's: no request, so no screen.
- **Control on the same sockets (protocol 30, `DESKTOP_SWITCH_PROTOCOL`).** Taking control closed the watching stream and opened a control one: a new socket from the browser through Cloudflare to the server, a new data socket from the computer, and a new handshake. Where the viewer asks (`switch=1` on `/api/desktop`) and the computer can (protocol 30), the server now tells the viewer `{"type":"mode","mode"}` as the stream becomes ready, before any of the computer's bytes, and when control changes hands (`createDesktopControl`, on every replica) it switches the holder's own streams instead of closing them: watching to control as they take it (one still opening once it is ready), control to watching as it ends. Everyone else's still close (4409), and so does a control stream that can't switch (4410).
  - The server checks the new mode as an open would (`reauthorizeStream`: `streamAccess` on the computer the stream runs on; control never for a held agent, and it starts its holder's grace again). Control refused leaves the stream watching, and the recheck closes it if the person may not even watch; watching refused closes it. What ran until the switch is a stream of its own for the hooks: its audit row (`desktop.watched` or `desktop.controlled`, its seconds and bytes), a control part's screening (ADR 0076) and grace; the new part starts for them.
  - On the data socket the server sends `{"type":"mode","mode"}`. The runner checks it as `stream.open` does (the desktop switch; control is new work, never on a paused computer), sends nothing more of the old login's, logs in again with that mode's password, sends the same frame back where the old session's bytes end, then the new session's handshake. A login that fails closes the stream (1011), and the viewer opens it again in its new mode.
  - On the viewer's socket the server passes that frame on. The viewer's noVNC session ends there; the viewer answers the same frame where its own old bytes end, and a new noVNC session starts on what follows (`DesktopLink` in the web app gives noVNC a channel of its own for each session on one socket). The server drops what the viewer sends between its switch and that answer: it was the old session's.
  - In the web app the last picture stays, frosted under "Assumindo o controle…", from the take control until noVNC connects in control (it drops keys, clicks and pastes until then), then clear until the control session draws, the pointer going through it to noVNC; a hand back keeps it until the watching session draws, as before. A stream that changes in place and isn't switched within 3 s of the mode changing opens again in the new mode. With no picture held (a screen opening), the cover takes the person's clicks until a picture shows, so the screen is looked at every 50 ms (it was 200: a first click waited up to that long more).
  - An older app, server or computer: as before, the stream closes and opens again.
- **Unchanged:** each mode is its own Xvnc login, and Xvnc still enforces view-only; the server still never parses RFB (it passes text frames on by their type and drops binary ones by when they come).
- **Left as it is:** TigerVNC's congestion control starts each login at a 16 KiB window and goes back to it after any pause longer than twice its round trip, growing it only as its fences come back, so a new session's first second gets about one screen update per round trip; a switch is still a new login. Between the server and Cloudflare, a Linux server's TCP also starts slow again after a pause (`net.ipv4.tcp_slow_start_after_idle`, on by default).

## Order

1. This ADR, protocol 18, the switches and the scope.
2. The server's stream broker and endpoints; the runner's desktop sessions.
3. The runner's data sockets and RFB proxy; the terminal.
4. Taking control and the desktop's REST; the agent's browser on its desktop.
5. The web panels; the self-host docs.
6. System mode (ADR 0057): the install and its service, agent users and the launcher, per-agent workers, the loopback guard.
7. End to end on a real Linux machine, in single-user and in system mode.

## Consequences

- People see everything an agent does on its computer and can take over any app, not only the browser; desktop computer use builds on the same session and scope.
- A person in control, or in a terminal, acts as that computer's user: on a personal computer only the person who paired it gets that.
- Screens need Linux and Bun 1.3.5 or newer on the runner; runners on Node and Mac or Windows desktops keep the browser only.
- About 0.2 GB per idle desktop and 0.8 GB with Chrome: desktops stay on, and only memory pressure parks the least-used (ADR 0065 §2).
- Every viewer is a stream through the server, up to about 2.3 MB/s each way while the screen moves: the server's bandwidth is what to watch, and screens need a single server replica for now.
- Agents share one OS user in single-user mode, as before; separation between agents is system mode.
