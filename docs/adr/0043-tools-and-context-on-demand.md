# 0043. Tools and context on demand, chosen per run by the judge

- Status: Accepted (2026-10-20)
- Date: 2026-10-20
- Extends: ADR 0015 (Tool Gateway), ADR 0032 (computer brains), big connectors as a directory (`packages/engine/src/tools/directory.ts`)
- Out of scope for now: provider-native tool search (Anthropic `defer_loading`, Claude Code's own ToolSearch), changing the list in the middle of a run, Claude Code's own floor (`apps/server/runner/brain.ts`)

## Context

Every run listed every tool the agent was granted, and the prompt repeated each one with a description. An agent with the default scopes and two connectors had 105 tools. One run of a Claude Code agent read ~1M input tokens over ~15 steps, because every step resends the whole base (~48k). Memory and wiki pages also went in as full text whether the message needed them or not.

Big connectors already became a directory (`<prefix>_find_tools` + `<prefix>_use_tool`), provider-neutral, through the gateway. Letting the judge pick which connectors go in whole was evaluated on 222 real runs: the judge alone at ≥ 0.3 got 92% of connector uses, and with "always load what was used in the channel in the last 6 hours", 77/77.

Requirement: provider-neutral. The same mechanism must work for the API (any provider), Claude Code and Codex.

## Decision

### 1. Tool groups, a core, and one directory for the rest

- A tool's group is its scope's prefix (`browser:use` → `browser`, `github:repo.read` → `github`); each custom connector is its own group (`toolGroupKey`).
- The core is always listed: the conversation (scope `""`), `context`, `memory`, `skills`, and `read_wiki_page` / `search_wiki` (the prompt points at them).
- `presentTools(tools, sensitive, loaded)`: with `loaded`, the core and the loaded groups go as they are (big connectors still as their own directory); every other tool goes behind `find_tools` (BM25 over names, descriptions and inputs, no model call) and `use_tool` (runs one by its real name). Without `loaded`, everything is listed, as before.
- The gateway runs `use_tool` as the real tool (scope, schema, call checks, approval, steps, chip), exactly like a big connector's directory. A tool on demand called by its own real name also runs: the gateway knows every granted tool.
- `find_tools`'s description names every group with its count, so the model knows what it can reach.
- `find_tools` also ranks the tools already listed, in the same BM25 pass: those that outrank every other match open its answer, to call directly and not through `use_tool`; one that matches less keeps its rank, marked the same way, so it never comes before a better match. A model that searched for a tool it already had otherwise read the unrelated matches as all there was, and said it couldn't.
- `find_tools` also ranks, in the same pass, this server's tools the agent may not use (every source's tools for the workspace, the agent's grants decide; the browser's and the desktop's give theirs without a grant, with no machine lookup). Those among the best close its answer, after the usable ones and never in their place, by name and one sentence, never their input: "Not allowed for you yet", grouped by the permissions `request_permission` offers for them (the same list, `missingPermissions`, so what the agent asks for is what the card grants; the computer's scopes, which "all tools" never covers, with what they give), and "Turned off for you by an admin" for a `deny:<tool>`, without `request_permission`. A tool that works only with another (`ToolDefinition.needs`: the desktop runs commands, so it needs `run_code`) is listed and run only with both, and names each permission it lacks: `desktop:use` and `sandbox:run`, or the one left. A permission `request_permission` doesn't offer (a mailbox's, a database's, one more scope of a connector the agent already has some of) isn't named, nor a tool the run's policy would refuse anyway; a run that can't call `request_permission` is told a person can turn them on. `use_tool` with the name of one answers as its direct call does: refused, saying why. A missing permission otherwise read as a missing capability: the agent said it couldn't, never that a person could turn it on.
- Last, `find_tools` names the connectors of "Adicionar conector" (`connectorListing` and the mailboxes this server offers, `missingConnectors`) that the query names, by every word of a label or of an id, and the agent has no tool of, with how to get each: not connected in the workspace (an admin connects it in Configurações › Conectores), connected but not given to the agent (an admin gives it on the agent's page, Ferramentas e acesso), not available on this installation (whoever runs the installation turns it on), or, for a mailbox that stopped working, connected but needing a reconnect (an admin clicks Reconectar on its row: connecting it again fails as already connected). A connection none of whose tools is listed (its server down, not reviewed yet) is left out: nothing says the agent lacks it. A server connected by address named after a mailbox's service ("Gmail") counts as that service. When nothing matches, the groups to search again still come first. Catalog names and states only, never a connection's label, account, address or key. An agent asked to set up Google Drive otherwise searched, found nothing, and said there was no such connector. "What you can do" says to guide the person to connect an app instead of saying it doesn't exist.

### 2. The judge picks the groups once per run

- `chooseToolGroups`: one calibrated `noul` per group not kept (below), in one judge request. State: the agent (name, role, instructions), the message, and the last 6 messages where it answers. A group loads at ≥ 0.3.
- Kept without asking (`keptToolGroups`): the groups of the agent's previous run in the same thread (the thread's list only grows, so a computer brain's live session and the prompt cache aren't reset by every message), and the groups of the tools the agent called in the channel in the last 6 hours.
- Calibrated only (`calibrated: true`): without Jev, on a 1.5 s timeout or an error, the run gets the core and the kept groups. A wrong guess costs a `find_tools` call, never a capability. The judge never grants anything.
- The choice is saved on the transcript (`toolGroups`) and in the run's `context` step (groups, scores, source, kept). Every turn of the run, its resumes after approvals and the runner bridge read the same list (`ToolContext.loadedGroups`).
- On by default in the server (`toolsOnDemand`); the engine's tests list every tool unless they turn it on.

### 3. A shorter "What you can do"

Tool names only, by group (the description is already in each tool's schema), plus one line for what is on demand. Guidance tied to a tool (browser, schedule, PDFs) is still there when the tool is reachable on demand, and tools it names that aren't listed run through `use_tool`.

### 4. Context on demand

- Wiki: pages the message names and the best match go in, up to 1,500 characters each; other matches are one index line each, read with `read_wiki_page`.
- Memory: at most 3,500 characters; an item over 240 characters is cut with "[more with expand]" (pinned items keep 600).

## Consequences

- Smaller base per call on every brain, with the biggest gain on the API (schemas of the core and the chosen groups only). On Claude Code, which already hides MCP tools behind its own ToolSearch, the gain is the shorter prompt now; a short MCP list also makes the runner's `alwaysLoad` cheap, removing its extra ToolSearch call.
- One more judge call at the start of a new run (p50 ~245 ms in that eval), in front of the first model call.
- The model sometimes needs one `find_tools` call before acting. To verify with a behavior eval on real models before tuning the threshold or the core.

## Addendum (2026-10-31): no dead end between a directory and a computer brain's list

An agent on Claude Code got read access to a custom connector of 56 tools between two turns of its kept-alive process. The next run loaded the connector, listed as its directory (`vega_find_tools`, `vega_use_tool`, though its tools are `vega_crm_*`), and `find_tools` said both were already in the agent's list, "call them directly, not through use_tool". The process still had the list it started with, so the agent ran `use_tool` with `vega_find_tools`; `use_tool` only knew real tools, refused it as no such tool, and the agent told the person the tools didn't exist for it. Three causes: the bridge's MCP process announced a new list only from its 60-second refresh, which compared against a list a call had already refreshed, so the change was never announced; `use_tool` couldn't run a directory's own tools; and the directory took the first word of its tools' names for its prefix.

- **One prefix.** A big connector's directory is named after the prefix its tools have: its label as the connector source writes it into their names (`Vega CRM` → `vega_crm_find_tools`), else the first word they all share (a catalog connector's id: `drive_` for Google Drive), else the label. The names of before keep working for a conversation that learned them: the first word's directory (`vega_find_tools`, `vega_use_tool`, when only one directory had it) and tool names after it (`crm_listar_departamentos` through its `use_tool`).
- **Any `use_tool` runs any tool by its name.** A directory's own, one already listed, another directory's `find_tools` or `use_tool` (unwrapped, up to three deep), a tool of the connector written without its prefix, and any tool of the sources the agent may not use, which is refused as its direct call is. A harness's prefix (`mcp__agentes__`) is no part of a name. A name nothing has gets the exact name when one is a word away (one missing or extra, as in `vega_` for `vega_crm_`; never another word in a word's place, since `get` for `delete` is another tool) or the same name with words before it or without them (three at most), with the directory that runs it when it isn't listed, else where to search. A direct call by an unknown name answers the same way.
- **What exists, plainly.** A tool of a connector the agent holds with less access than the tool needs is refused as existing: "exists, but this agent's access to Vega CRM doesn't cover it (it needs write access). Only an admin can change that, on the agent's page in Tools and access", since `request_permission` only offers what the agent has nothing of. `find_tools` names those tools in their own section ("Beyond your access to their connector"), by name and one sentence, never their input. A tool turned off by name says only an admin turns it back on.
- **`find_tools` says what the harness may lack.** Its "Already in your tool list" adds that `use_tool` runs them too if the list doesn't show them yet.
- **The bridge follows the list (ADR 0032).** Any tool name goes to the server, which decides, not only the cached list's (a background task outside a mission keeps its prompt-only check). Every change the MCP process sees, whichever ask saw it, sends `notifications/tools/list_changed`. It asks every second while the daemon answers by itself: between turns (idle), and for the same run, whose list the daemon keeps 30 seconds (`LIST_MEMO_MS`); so a turn's new tools are announced within a second of its start and the server is asked once per run and then every 30 seconds. Against a daemon that doesn't keep lists, every 60 seconds during a turn, as before. Claude Code (2.1.316, from its binary) re-lists on the notification and swaps the new tools in between the tool calls of a turn; a turn's first model request may still carry the old list, and the rules above leave nothing out of reach meanwhile. Codex (0.165.0) doesn't follow the notification (its `mcp_tool_list_changed` feature is under development and off): each `brain.turn` carries the names of the run's tools (`mcp.tools`), and a kept-alive app-server whose thread opened without one of them starts again, resuming the thread (a dropped name stays listed: the server answers a call to it).

## Addendum (2026-11-02): the token trim

A greeting cost about 16k tokens, most of it fixed: tool definitions, guidance said twice, and per-turn text in the system prompt that kept the history out of the prompt cache. The trim cuts and reorders what the model reads without changing a word of the autonomy rules (`HOW_YOU_WORK`, finish what you start, long work, the reply rules about reactions, `ask_user`, blocks, approvals, the team). `test/turns-eval.test.ts` holds that line: scripted turns (greetings, long work, a correction, a choice, a block, a follow-through after a tool result, a computer task, an approval) must still list what they need or reach it with one `find_tools` search, every autonomy rule word for word, a DM "oi" under a size ceiling, and the cached start of the tool list the same whatever group loads. `bun run eval:turns` replays the same turns against a real model.

- **Kept groups (§2).** A run keeps, without asking the judge, only the groups of the tools the agent's previous run in the same conversation called (the thread, or the channel's or DM's main timeline), not every group used in the channel in the last 6 hours and not the thread's whole list. A greeting after computer work no longer carries the computer's tools; a miss costs one search.
- **A rarely used group (§1).** Of the core groups, `propose_instruction_change`, `send_sticker`, `read_skill_file`, `find_agent`, `get_my_usage`, `set_status`, `add_agent_to_channel`, `update_thread` and `cancel_follow_up` form a group of their own (`more`), loaded on demand. "# Your team" follows the granted `find_agent`, so the team block stays. Never deferred: what an agent reaches for unasked (`react`, `ask_user`, `request_permission`, `remember`, `save_how_to`, `update_memory`, `forget`, `update_skill`, `search_context`, the web, `ask_agent`, `tell_agent`, `follow_up`, `work_in_background`, `post_message`, `send_dm`, `post_update`, `show_block`, the skill and wiki readers).
- **"What you can do" (§3).** The groups by name only (each tool's name and use are in its definition); a connector by label and count. The sections on how to use a group (routines and reminders, scheduled actions, files as PDF, the network note for commands, sharing files) and "# Writing to the wiki" come with the group loaded, not while it is on demand: the wiki tools' own descriptions say "only when a person asks". `show_block` carries a short description (when and why, unprompted); the blocks' manual comes back from a call without `html`.
- **The prompt's order.** The rules first (the same for every agent with the same tools), then the organization's block with a breakpoint (shared by its agents), then the agent's own; the per-turn blocks and what was found for the trigger follow the trigger's text in its message under "# This turn" (as a computer brain reads them), with a breakpoint on the trigger's text when history comes before it, so the next run reads this run's history from the cache. With history, that breakpoint takes the organization's slot (4 at most); the lookback still finds the organization's entry written by a run without history.
- **History.** A history cut at its oldest end starts at an anchor message (`historyStart`), so its start stays put for several runs instead of moving by one every message. Messages before the last 8 that are longer than 1,500 characters read as their first 600 and the id `expand` reopens them by.
- **Waiting less.** The quiet window (ADR 0112) ends 1.2 s after the message when the person isn't typing; the apps send a typing frame on a new message's first keystroke and the server lets two through every 2 s, so "oi" then "preciso de uma coisa" is still read as one. Meanwhile a model brain on Claude's API pre-warms the first call (`maxTokens` 0 through the gateway, recorded like any call).
- **Computer brains (Claude Code, runner).** Our MCP tools sit behind Claude Code's ToolSearch except those always listed (`ALWAYS_LOADED`: `react`, `ask_user`, `ask_choices`, `request_approval`, `remember`, `search_context`, `follow_up`, `work_in_background`, `post_update`, `post_message`, `send_dm`, `show_block`, `web_search`, `web_fetch`, `find_tools`, `use_tool`, the permission prompt), and Claude Code's own WebFetch and WebSearch are off: ours mark what they read as outside content (ADR 0117). `--tools` keeps `ToolSearch`: without it Claude Code lists every MCP tool (measured on 2.1.316). Runner only, no protocol change. Measured: a DM "oi" 50.2k → 37.6k characters on the API brain, 76.5k → 54.3k in Claude Code's request.

## Addendum (2026-11-03): one prefix per agent on Claude Code

A new Claude Code session of an agent wrote almost its whole prefix to the cache again (median 38k tokens), even when another session of the same agent had just written the same rules. Two parts of the prefix changed from session to session: the tool list, which comes first and sits before both of Claude Code's system breakpoints, and the appended system text, which Claude Code sends as one block with one breakpoint at its end. Nothing the agent reads is cut: every rule stays word for word, and every tool stays reachable.

- **One tool list per agent (F1).** A new run of an agent on Claude Code (with tools on demand) lists every tool the agent has, sorted by name, with `find_tools` / `use_tool` last (`EVERY_TOOL` in `toolGroups`), instead of the groups the judge picks: Claude Code already keeps our tools behind its ToolSearch, except `ALWAYS_LOADED`, so a granted tool is one ToolSearch away, a step fewer than `find_tools` then `use_tool`. The tool-group judge isn't asked for these runs (one model call fewer). `find_tools` keeps a description that is the same in every run (the groups the agent has, no counts) and still names blocked tools and how to ask for them, and searches a big connector's own tools. `ask_choices`, `work_in_background` and `post_update` are listed in every such run; where one doesn't apply (no person behind the run, a routine's work, background work already) the call says why and what to do instead, and the prompt's lines about them still follow whether they apply. "What you can do" names every granted tool, so the sections on files, routines, scheduled actions and the wiki come from what the agent has. Codex, Cursor and OpenCode keep the judge: they list every MCP tool in full, so one list there would cost more than it saves. The browser's pre-warm, started when the judge loaded the browser, doesn't run for these runs. A run that thinks with another brain after all (the model brain standing in, a mission's Codex) goes back to the core tools with the rest behind `find_tools` (`toolGroups` `[]`): only Claude Code defers them itself.
- **Agent-level system text, per-conversation text in the session (F2).** The blocks that hold for one conversation (`ContextBlock.conversation`: "# Your team", which follows the requester; "# Where this thread comes from"; a mission's brief; an issue's brief; a routine's block and what it delivers; the thread's summary; the `ask_choices` line, now its own block with the same text under "# Options to pick from", so it isn't read as part of the section before it) leave a computer brain's system text and come as "# This conversation" (`conversationText`), with "# Your code" after them. The model brain reads them where they were. From runner protocol 40 (`CONVERSATION_PROTOCOL`) a Claude Code `brain.turn` carries them in `conversation`: the runner writes `system.txt` without them and without the checkout's CLAUDE.md and AGENTS.md (moved back by the next addendum), and puts both at the head of the first message of a new session, again on the first turn after the CLI compacted its history (`compact_boundary`), and again on a resume whose kept first text is gone (it may have begun under an older server, with them in the system text). A resumed session doesn't get them again. An older runner, and Codex, Cursor and OpenCode, get one text, the system with the conversation after it (`systemWithConversation`). The system text adds one line: "# This turn" and "# This conversation" come from agentes.chat, not from a person. `promptKey` is unchanged.
- **Measured before touching the always-loaded set (F3).** The runner forwards a turn's `num_turns` (`calls`) and the largest uncached input of one of its API calls (`maxUncached`, from the `--verbose` assistant lines, once per message id) on the `usage` event; the engine keeps both on the turn's `model_call` step (no migration), with how many `ToolSearch` calls the turn made (`toolSearches`: Claude Code's own tools have no step). The question for F4 (keep each agent's habitual tools loaded) is whether uncached input grows with the tools a session loaded or only with more calls per turn:

```sql
-- Claude Code runs of the last 24 h: uncached input per turn, by how many lookups the run made.
with turns as (
  select s.run_id, count(*) as turns, sum((s.data->>'calls')::int) as calls,
         max((s.data->>'maxUncached')::int) as max_uncached
  from agent_run_steps s join agent_runs r on r.id = s.run_id
  where s.kind = 'model_call' and r.brain = 'claude_code' and s.data ? 'calls'
    and s.created_at > now() - interval '24 hours'
  group by s.run_id),
-- ToolSearch is Claude Code's own call (no step: counted on the model_call step), find_tools / use_tool are ours.
lookups as (
  select run_id, sum(case when kind = 'model_call' then coalesce((data->>'toolSearches')::int, 0) else 1 end) as n
  from agent_run_steps
  where run_id in (select run_id from turns)
    and (kind = 'model_call' or (kind = 'tool_call' and data->>'name' in ('find_tools', 'use_tool')))
  group by run_id),
uncached as (
  select run_id, sum(input_tokens) as uncached from usage_records
  where run_id in (select run_id from turns) and billed_to = 'plan' group by run_id)
select least(coalesce(l.n, 0), 4) as lookups, count(*) as runs,
       round(avg(u.uncached::numeric / t.turns)) as uncached_per_turn,
       round(avg(t.calls::numeric / t.turns), 1) as calls_per_turn,
       percentile_cont(0.5) within group (order by t.max_uncached) as median_max_uncached
from turns t left join lookups l using (run_id) left join uncached u using (run_id)
group by 1 order by 1;
```

Measured on the test fixture (an agent with conversation, memory, issues, Drive, schedule and wiki tools; a DM from the owner, then a channel message from another person after which the judge would load Issues): the always-loaded tools were 17,617 and 17,605 characters sharing 16,485, now 17,593 in both, byte for byte; the system text was 18,276 and 18,369 characters sharing 15,916, now 20,145 in both (every granted tool named in "What you can do"), with 824 characters of "# This conversation" in each session's first message. A follow-up turn's message stays 728 characters. Tested in `token-trim.test.ts` (same tools and system text across a DM and a channel thread with other requesters and groups; every granted tool listed; the refusals; "# This conversation" once and not on a resume; the rule lines of system plus conversation against a snapshot taken from the system text before the change; `calls` and `maxUncached` on the step), `claude-code-brain.test.ts` (the request by protocol) and the runner's `brain.test.ts` (the same `system.txt` in two folders; the conversation and CLAUDE.md on the first turn, after a `compact_boundary` and after the kept text expired, never on a resume; the parser's calls).

## Addendum (2026-11-03): the checkout's instructions back in the system text

Production after the addendum above (Cloud 2026.11.03.17, runner protocol 40): a new session's single-call first turn, when the same agent had another session in the past hour, wrote a median 23.2k tokens to the cache and read 25.3k. The real CLI (2.1.317) against a fake API, launched with the runner's exact flags, shows why part of it was avoidable. Claude Code puts its cache breakpoints after "You are Claude Code…" (`system[1]`) and after its base text plus our appended file (`system[2]`, the last one sessions share), then on the last message. Everything in the messages is written again for each new session: its own reminders (git status, attribution, the Environment block, the deferred tool names, the MCP instructions, the date) and our first message. The checkout's CLAUDE.md and AGENTS.md, which protocol 40 had moved into that first message, are the largest part that is the same for every session in one folder (up to `REPO_INSTRUCTIONS_MAX`, about 5.7k tokens). The rest of the first message is the conversation's own: "# This conversation", the turn, what was found, and the conversation so far, which accounts for most of production's 23k.

- **Decision.** A Claude Code session's appended system text is the agent's text with the folder's CLAUDE.md and AGENTS.md at its end (`repoInstructions`), as before protocol 40. The conversation still opens the first message (`turnPrompt`), on a new session, after a `compact_boundary`, and on a resume whose kept text expired. The kept first text (`sessionSystem`) is keyed by folder already, so a resume still sends the bytes its session began with. No protocol change: the server sends the same `brain.turn`; this is the runner's choice.
- **A session kept by a protocol-40 runner of before** has a kept text without the instructions. It keeps that text, and its next first-message head after a compaction carries the instructions again (`repoInFirst`: the kept text has no "# Repository instructions" heading).
- **Another folder shares only the tools and `system[1]`, before and after this change.** `system[2]` already differed between folders: Claude Code's auto-memory section names the project's memory folder, which is per working directory. `--exclude-dynamic-system-prompt-sections` moves that section (about 2.3k characters) into the first user message and makes `system[2]` the same in every folder, but it is a flag the runner doesn't pass yet, and older CLIs may not know it (seen in 2.1.314–2.1.317), so the runner would need a version check before passing it. With the instructions in `system[2]` it would help only between folders whose instructions are the same (none at all, say), so it is left out for now.
- **Left as they are.** The attribution and git status reminders can't sit before the breakpoint: Claude Code puts them in the first user message. Turning them off would change what the agent knows and writes (no co-author lines, no starting git status) for about 0.3k tokens.

Measured with the real CLI 2.1.317 and the fake API (`--setting-sources ""`, the 26 always-loaded and 59 deferred agentes tools, a checkout whose CLAUDE.md reaches the 20,000-character cap, a 7.9k-character agent text). For a second new session in the same checkout, with another requester, the cached prefix it can read went from 39,772 to 59,846 characters (about 11.4k to 17.1k tokens at 3.5 characters per token), and what it writes went from 28,149 to 7,505 characters (about 8.0k to 2.1k tokens). A new session in another checkout reads 25,665 characters in both (the tools and `system[1]`). Tested in the runner's `brain.test.ts`: two new sessions in one checkout get the same launch arguments (apart from their own files and session id) and the same system text, CLAUDE.md included; another checkout gets the same agent text with its own CLAUDE.md at the end; the conversation opens the first message without the instructions, and again after a compaction; a kept text without the instructions gets them back after a compaction.
- **A compaction outlives its process.** The parser's `compacted` flag belonged to the process: a CLI that compacted during a turn and then closed as idle (or crashed) left a resumed process whose kept text made it not `opening`, so "# This conversation" (and, for a `repoInFirst` session, the instructions) never came again and the agent worked from the CLI's summary alone. The flag is now kept with the session's state, as `<kept text>.compacted` next to its kept system text in the runner's private `sessions` folder (`compactedMark`), written when the CLI compacts (so a runner that dies mid-turn still knows), at the end of every turn and when a process closes, and read by a resume of that kept text. Tested in `brain.test.ts`: compacted, closed as idle, resumed: the conversation opens that turn once; closed again without a compaction: not sent.

## Addendum (2026-11-03): old tool calls and results read cut, reopened whole (B12)

B9 cuts long channel messages older than the last eight. A run's own tool steps had no such cut: every model call of the API brain resends each result whole, and a computer brain that starts a new session mid-run (`flattenContent`) reads them inline in "The conversation so far". The owner's condition: trim only where it doesn't affect intelligence, and anything trimmed stays reachable whenever the agent needs a specific piece.

- **What is cut (`cutOldToolSteps`, a view: the transcript keeps everything).** Tool steps (an assistant message with calls, and the results that answer them) older than the last `KEEP_TOOL_STEPS` (4). A result over `LONG_OLD_RESULT` (1,500 characters) reads as its first 500 and last 100 characters (an `<external_data>` envelope keeps its closing marker) with `[…]` between them and, after the end (outside an envelope, read as ours and not as the data's), `[Cut: N of this <tool> result's M characters, in the middle; expand <call id> reopens it whole]`; the call before it keeps its name and arguments. Arguments over `LONG_OLD_INPUT` (1,500) keep strings up to 300 characters, longer ones read as their first 200 with the same kind of note. Applied by the model brain (`ModelBrain.request`, also its pre-warm) and by every computer brain's text view (`brainTurnOf` `messages`), only when the turn lists `expand`.
- **Never cut.** The last 4 to 7 steps; errors (`isError`: a refusal, an expiry, a failure the agent reacts to); results where a person decided or answered (`ask_user`, `ask_choices`, `show_block`, `start_poll`, `request_approval`, `request_permission`, `request_secret`, `browser_ask_person`, `desktop_ask_person`), another agent's answer (`ask_agent`) and a skill's instructions (`load_skill`, followed for the rest of the run) (`keptWhole`); short results; every text people and the agent wrote; images. The turn-end controller, the stuck detector and the follow-through evidence read the transcript, not this view, so their inputs are unchanged. The context budget (`fitContextWindow`) measures this view, what the model reads, and removes the results it picks from the transcript: a result the view already cuts is not lost to a placeholder for room it never took.
- **Reachable.** `expand` takes a tool call id too: it reads the run's own transcript (`agent_runs.transcript`, org and run checked), or an earlier run's of the same computer session (same agent and `brain_session_id`: a session started mid-run read the cut in its first message, and later runs of the conversation resume it; never another session's), and answers the call whole, `Tool call <name> <arguments>` and `Result: <content>` exactly as the model first read it. A "Continuar" run carries the transcript, so its ids still open.
- **Byte-stable.** The cut is a function of the messages alone, and its boundary moves in steps of `TOOL_STEP_ANCHOR` (4): the same history gives the same bytes on every build, a resume sends what it sent before, and the API brain's cached prefix changes once every four steps, not on every one.
- **What it does not reach.** A channel's history carries no tool calls (`toTurns` builds it from messages), so a new Claude Code session's "The conversation so far" has calls only from its own run's earlier model steps or a continued run; the rest of that message is B9's.

Measured on the token-trim fixtures: a run of 14 steps of 3.6k-character results, messages 57,631 → 43,443 characters (computer view 55,468 → 41,265), with the 6 most recent steps, an error, an answer and a loaded skill whole; a fixture run of 9 log reads of 4.8k characters then an `expand`, 50,190 → 33,822.
